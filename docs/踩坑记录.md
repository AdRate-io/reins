## 2026-09-14 以为"敏感数据只在录像里"，按值查全历史才发现真实广告主 id 散落在 10 个文件、72 个提交（来源：E4 录像脱敏）

### 现象
发前清单一直写"源录像 `patrol-disable.jsonl` 含真实 id，发布前换脱敏版或改写历史"。动手时按 E2 的 id 形态对全部提交做 `git grep`，
真实测试广告主 id 还出现在 examples/adrate 的 README、agent.ts、两份 smoke 脚本，eval 包的 `recording.test.ts`、fixture 的
`fixture.test.ts`，以及 DECISIONS / TASKS / 两份归档审查报告里；一个真实团队名与一个昵称还被单测拿来当样例。只删录像文件、
哪怕连历史一起删，公开仓库里照样能搜到。

### 原因
写代码与文档时把"测试广告主"当成了随手可写的常量：id 进了源码常量与 pin 文案，单测顺手抄了真实值当样例，文档复述任务时把 id
当作叙事细节。E2 定脱敏口径时只盯着录像这一个载体，没有回头按**值**扫一遍仓库。

### 修复
- 处置方式从"删文件"改为 `git filter-repo --replace-text`：用 `examples/adrate/scrub.ts` 产出的同一张别名表（先按 E2 在 patrol 上建表保证与
  fixture 同值同别名，S1 录像新值接着编号，236 条）在**全部 72 个提交的全部文件**里逐字替换；改写前先 `git bundle` 备份到仓库外，
  改写后按值扫全历史确认零残留，提交数不变，`docs/踩坑记录.md` 里引用的三个旧哈希按 commit-map 更新。
- 真实值移出源码：`local.ts` 从环境变量或 gitignore 的 `模型API测试信息.md` 读测试广告主 id / 冒烟计划 id；`recording.test.ts`
  改用编造值；`fixture.test.ts` 从"不含某真实值"改成"只剩别名形态"（真实值不能再写进仓库，只能按形态断言）。
- 原始录像挪到 gitignore 的 `recordings/raw/`，公开版由 scrub.ts 生成并重生成回放页面。

### 教训
- **脱敏要按值查，不按文件查**：先从源数据抽出全部敏感值，再拿这张表对全历史 `git grep -F -f`，载体是什么不重要。
- 真实 id 一旦被当常量写进源码，就会被单测、文档、pin 文案层层复制；本地专用值一开始就该走 gitignore 的配置读取。
- 按形态断言（"只剩 `7000000000000000\d{3}`"）比按值断言（"不含 758…"）更适合公开仓库：后者要求把真实值写进测试。
- 顺手踩的两个小坑：`.gitignore` 末尾没有换行，`>>` 追加的规则粘到上一行末尾，raw/ 目录被 `git add -A` 暂存；zsh 不对未加引号的
  变量分词，`for f in $files` 把整段输出当一个文件名，且本机 `grep` 是 ugrep 别名、`-Z` 含义不同——批量改文件用 Node 脚本最稳。

## 2026-09-13 按"token ≤ 字符"给 spill 定放行限额，40k 字符的中文技能照样被外溢成预览（来源：S1 发前安全审查复现）

### 现象
`skill_read` 首版声明 `resultPolicy: { maxTokens: maxReadChars }`，注释写"token 数不会超过字符数，spill 永远放行"。ASCII 用例（27.6k 字符 ≈ 6.9k token）全绿。
审查用 500 行 × 80 汉字（40,213 字符，正好在 Agent Skills 规范的 500 行内）的 SKILL.md 端到端过 `runLoop`：`tool_result.spilled` 有值，模型看到 40 行预览 + blob id，
再用 `fetch_blob` 取回来的正文是 `<untrusted source="tool:fetch_blob">`——同一份字节两条路两个信任级别。

### 原因
两个前提都错：core 的粗估是 ASCII 4 字 1 token、**非 ASCII 1 字 1 token**（`estimateTextTokens`），中文正文 token ≈ 字符，没有余量；
视图给每行加 7 个 ASCII 行号字符（≈ 2 token）与表头，比原文大 8%。另外软上限（带 `range` 不截、首行整行给）本身就能被 `range: [1, -1]` 与单行超长绕过，
"结果已按 maxReadChars 裁过"这句前提也不成立。

### 修复
视图给 skills 加 `enforceLimit` 硬上限模式（带范围也截、超长单行切开）；`resultPolicy.maxTokens = 2 × maxReadChars + 256`，推导写在代码注释里：
正文 ≤ maxReadChars token（全非 ASCII 最坏）+ 行号 ≤ 2 × (maxReadChars / 2) token（每行至少一字加换行）+ 表头。用例换成 500 行中文 + 缺省 spill。

### 教训
- **给另一个模块的阈值写"永远不会触发"之前，把两边的度量口径摆在一起算最坏情形**，用最坏的字符集（中文）而不是最顺手的（ASCII）写用例。
- "上限"要先问是硬的还是软的：软上限只能约束模型的缺省行为，不能当另一条机制的前提。

## 2026-09-13 两族真模型都不按截断提示续读技能：16k 字符上限把 AdRate 技能截掉 110 行，模型直接开工（来源：S1 examples/adrate 真跑）

### 现象
S1 首版 `skill_read` 缺省 `maxReadChars: 16000`（照搬 memory view）。DeepSeek 与 Claude 各真跑一次只读巡检：两族第一轮都先读了两份技能，
但 `adrate-ads`（24.5k 字符、355 行）只回了 1–245 行，末尾明明写着 `[Showing lines 1-245 of 355 … Use range, e.g. [246, -1], to read the rest.]`，
两个模型都没有再调一次 `skill_read({ range })`，直接开始调 AdRate。被截掉的是 "Keep Campaign writes server-owned" 等写操作契约——只读任务没暴露，Boss 的真实写任务会。

### 原因
截断 + 续读提示对 memory 文件成立：那是模型自己在分页读一份它知道结构的文件。SKILL.md 是"动手前先读完"的说明书，模型读到 245 行已经觉得"够了"，
续读提示在它眼里是可选项。机制正确（提示、range 都好用），行为却不是想要的——这正是"行为正确性只能用真模型验"那条教训。

### 修复
缺省 `maxReadChars` 提到 40000（Agent Skills 规范建议 SKILL.md ≤ 500 行 ≈ 40k 字符，规范内的技能一次读完）；`skill_read` 声明
`resultPolicy: { maxTokens: maxReadChars, overflow: "spill" }`，token 数 ≤ 字符数，spill 按工具限额永远放行，否则 6k 阈值的示例会把技能正文换成预览 + fetch_blob。
加 skills × spill 联装用例锁住；DeepSeek 复跑核对 `adrate-ads` 一次读到 355 行。

### 教训
- **给模型的"续读 / 取回"机制只在模型有动机时起作用**：它自己分页的内容会续读，被告知"还有一段"的说明书不会。凡是"读完才能动手"的内容，缺省上限要按内容规范定，不能照搬另一个模块的数字。
- 两个模块的输出都要经过 spill 时，先问一句"它们的限额谁大"——小的那个会静默改写大的那个的输出形态。

## 2026-09-13 AdRate `skills install` 落盘的 SKILL.md 是存根，正文只在 CLI 里（来源：S1 实施前核实 ③）

### 现象
按 Agent Skills 规范，`fsSkillSource("~/.agents/skills")` 应能直接接 AdRate 的两份技能。实际 `~/.agents/skills/adrate-ads/SKILL.md` 只有 686 字节：
frontmatter（name / description / metadata.version 等）+ 一句"Run `adrate --version` first … run `adrate skills read adrate-ads` and follow the returned instructions"。
正文 12k / 25k 字符只能从 `adrate skills read <name> [path]`（`--json` 给 `content`）拿。

### 原因
AdRate 把技能正文与 CLI 版本绑定（`minCliVersion`、`contentSha256`），落盘只是给会跑 shell 的 agent 一个入口。对没有 shell 工具的 reins agent，读到的是一句它做不到的指令。

### 修复
示例不用 `fsSkillSource`，启动时 `adrate skills list --json` 取 name / description、`skills read --json` 取正文，拼成 SKILL.md 喂 `inlineSkills`——这也正是 Workers 上"bundle 成字符串"的用法，`inlineSkills` 助手因此从"实施时定"变成必须提供。frontmatter 解析顺带确认要跳过缩进的嵌套字段（`metadata:` 之下）、去掉值两端的引号。

### 教训
- **接任何"符合规范"的目录前，先看一眼正文而不只看文件在不在**——规范只定了形状，内容可以是转发。
- 载体可插拔的价值就在这里：换一个 `SkillSource` 实现，模块与模型看到的东西不变。

## 2026-09-10 asTool 经 HTTP 续跑必 409：server 预校验把子代理审批当成本会话 pending（来源：发前 cursor / Grok 双审查）

### 现象
按 README 与 `Interruption(kind=subagent)` 文档回传 `POST { sessionId, resume, decisions: [{ toolCallId: "c1", sessionId: childSessionId, approved: true }] }`，
`createAgentHandler` 回 `409 unknown_tool_call`，一条日志不写。同一份结论走 `agent.run()` 正常——`as-tool.test.ts` 与 `examples/team` 全绿。

### 原因
runLoop 起步把 `decisions` 按 `sessionId` 分两路（本会话的校验并记事件，别的会话的原样转发给 `ToolContext.decisions`），
但 server 的预校验（为了"校验不过一条日志不写"提前做的那份）还是老逻辑：全部结论都对照**父**会话的 `pendingToolCalls`。
子的 `c1` 不在父的 pending 里，于是 409。两处实现同一个判定，只改了一处；覆盖它的用例全在进程内路径，没有一条穿过 handler。

### 修复
`handler.ts` 预校验对 `d.sessionId !== undefined && d.sessionId !== sessionId` 的结论跳过 pending 校验，原样下传；`decisions[].sessionId` 顺手走 `isValidSessionId`（与请求 sessionId 同一字符集）。
reins 包新增两条经 `agent.handler` 的用例：带 childSessionId 的结论 200 且跑到 done；不带 sessionId 指错 toolCallId 仍 409、子会话 id 带空格 400。

### 教训
- **同一个判定在两个入口各写一份，就必须有一条穿过两个入口的用例**——configHash、pendingDigest、这次的 decisions 分流，三次都是"改了循环忘了预校验"。
- 新公开路径（asTool 的 HTTP 续跑）落地时，验收剧本要沿**文档写给用户的那条路**走一遍，不能只在最方便测的入口验。
- 外部审查的价值在"独立复现文档路径"：两个互不相干的审查者按 README 走都撞上同一条，说明这类缺口靠自测很难暴露。

## 2026-09-10 一个 MCP HTTP 服务端传输只服务一个会话，第二个客户端 initialize 直接 400（来源：P1 examples/mcp 第一次真跑）

### 现象
`examples/mcp` 第一次真跑：第一次 run 正常，审批暂停后第二次 run（续跑）起步 `tools/list` 时 MCP 连接失败，
上游回 `400 {"code":-32600,"message":"Invalid Request: Server already initialized"}`，整个 run 在写日志前抛 `McpToolsError`。
同一套写法在单测里全绿——因为单测只连了一次。

### 原因
示例服务器用了一个全局的 `WebStandardStreamableHTTPServerTransport` 实例 + `server.connect(transport)`。官方 SDK 里这个传输
是**一个会话一个实例**：它记着"已 initialize"，第二个客户端（宿主按请求重建 `mcpTools()` 后 `close()` 再建，或另一个进程）
发 initialize 就被拒。多客户端 / 重连的服务器要用 `createMcpHandler(factory)`，每个请求（2026-07 修订按请求）/ 会话由工厂造实例。
顺带的第二层坑：工厂每次都造新 `McpServer`，服务器的业务状态（示例里的库存 `items`）必须放在工厂外面，否则每个请求各一份。

### 修复
- `examples/mcp/server.ts` 与 `spikes/edge-runtime-check/fake-mcp.mjs` 改用 `createMcpHandler(() => makeServer(items)).fetch(request)`，`items` 提到模块级。
- `packages/tools-mcp/src/http.test.ts` 同样改用 `createMcpHandler`，并加"第二个客户端先后初始化"断言锁住回归。
- 示例的 `buildAgent()` 改为按服务器配置 JSON 缓存 `mcpTools()` Socket（配置没变就复用连接，变了才换并关旧的），避免每次请求一次 MCP 握手；README 写明。

### 教训
"客户端能连上"不等于"服务器能被反复连"。凡是自己搭的测试 / 示例服务器，至少让**两个客户端先后**（或一个客户端 close 后再建）走一遍，
单客户端的绿灯说明不了会话管理是否正确。示例代码会被用户照抄，示例里的服务器写法必须是生产可用的形态，不能是"能跑通一次"的形态。

## 2026-09-10 模型瞄着字数上限写，却数不准自己写了多少字（来源：TASKS E3c / DECISIONS 2026-09-10 E3c 附 / examples/eval/results/2026-09-09-deepseek-v4-flash/e3c-claude-sonnet-5-report.md）

### 现象
E3b 复测里 claude-sonnet-5 有 5/9 格在调 `pin` 时撞上 500 字符上限被拒，白白多花一轮重写。
把 500 这个数字明确写进工具说明与 schema 的 `maxLength` 之后，E3c 第一轮 Sonnet 仍然 3/3 格越界，
写出 502 / 545 / 558 字符 —— 只超出几个到几十个字符，内容本身没问题。

### 原因
模型会瞄着声明的上限去写，但它数不准自己的输出字数。这不是提示词没写清楚（上限已在说明和 schema 里各写一遍），
是模型能力边界。差几个字就整条拒掉，等于用一次完整的模型往返去换几十个字符的额度。

### 修复
`pin` 的字数校验加**两成容差**：声明值仍是 500，601 字符起才拒（`overshootTolerance`，可设 0 恢复严格）；
报错信息里报的仍是声明值 500，不告诉模型真实阈值。不直接把上限放宽到 600，因为那样模型会改成瞄着 600 写、
再数错一次。第二轮复测撞上限从 5/6 格降到 2/6，剩下两条是 608 / 680 字符，超出容差，拒得对。

### 教训
凡是"给模型一个数值上限，让它自己控制"的校验，都要在声明值之外留一段模型数不准的容差：
对外声明严格值让模型往里凑，对内按声明值 × (1 + 容差) 判拒。判断规则是看越界代价 ——
越界只是多占一点上下文（可容差），还是会让请求 400 或产生错误结果（必须严格）。

## 2026-09-10 上游瞬断能掐死整格跑数，而 runLoop 从来没有重试（来源：TASKS「runLoop 对上游瞬断的有限重试」/ DECISIONS 2026-09-10 / e3 报告「模型侧的意外」）

### 现象
E3 对照跑数的 99 格里，DeepSeek 端口有 3 次在响应中途 "Connection error" 掐断。
特征是 pi-ai 报 `terminated`、该次请求输出 0 token —— 连一个字都没吐出来就断了。
当时 runLoop 对模型调用没有任何重试，这三格直接记 error 收场，整格跑数作废，必须人工补跑。

### 原因
循环层把"调一次模型"当成不会失败的原子操作，失败一律记 `core.error` 交给宿主。
但网络瞬断与真实错误（参数错、缺 key、被中止）性质完全不同，前者重试一次大概率就过去了。

### 修复
新增 `LoopConfig.retry`（`maxAttempts` 缺省 3、`baseDelayMs` 1000、`maxDelayMs` 8000，`isTransient` 与 `sleep` 可注入），
判定逻辑做成纯函数 `loop/retry.ts`：网络错误码 / `terminated` / 超时 / 过载 / 限流 / 5xx 算瞬断，4xx、缺 key、AbortError 不算。
抛异常与 `stopReason=error` 两条路都包。关键约束：**只在本次尝试尚未落任何模型输出时重试**，
落了半截再失败照旧记 error 并标 `partialOutput` —— 否则日志里会出现两份半截输出，回放和 eval 都得自己猜哪份算数。
每次将要重试的失败都记一条模型不可见的 `core.error(willRetry)`，等待期间宿主中止则 `paused(host)`。

### 教训
重试策略必须先问"重试会不会污染唯一真源"。在 append-only 的时间线上，只有"这次尝试一个字都没写进日志"时重试才是安全的；
一旦已经落了部分输出，重试就是让模型重说一遍，日志里留下两份互相矛盾的记录。判不出是不是瞬断时一律当非瞬断，
代价只是多挨一次同样的错误，反过来会把 4xx 变成重试风暴。

## 2026-09-09 只跑新的 compatibility_date 会高估 edge 兼容性，而 HTTP 200 也不等于探测通过（来源：spikes/edge-runtime-check/README.md / DECISIONS 2026-09-09 发布前核实）

### 现象
PRD 把"跑在任何 Web 标准运行时"当卖点，但从未在 edge 运行时上实证过。做核实脚本时先用当天推荐的
`compatibility_date = 2026-09-09` 跑，四层探测全过 —— 看起来结论成立。
另一边，`/live` 那层连续两回返回 HTTP 200，但产出内容其实是错误 JSON。

### 原因
1. Workers 较新的 compatibility_date **默认就带了一部分 Node 兼容**：2026-09-09 这档不加任何 flag 也能
   `import("node:fs")`，`process` / `Buffer` 都存在。在这样的环境里跑通，证明不了"纯 Web 标准可跑"。
2. 两回假通过：① `worker.mjs` 的块注释里写了含 `*/` 的路径 `packages/*/dist`，注释提前闭合，
   后面的中文被当代码，esbuild 报错；② 从《模型API测试信息.md》抓 baseUrl 的正则撞上了一句同样含
   "anthropic 协议 baseurl：" 字样的说明文字，抓到一个反引号，worker 内部报 `Invalid URL string.`
   却仍然正常返回 HTTP 200（worker 把错误包成 JSON 返回了）。

### 修复
判据改为取**最严档**：`compatibility_date = 2023-01-01` 且不加 flag，实测那一档 `process` / `Buffer` 均不存在、
`node:*` 一律 import 失败，四层探测（模块加载 / 本地假端点 SSE / DeepSeek 真打 / gpt-5.5 真打）× 三档配置 12 格全过，
结论"不需要 `nodejs_compat`"才站得住。两回假通过靠逐项核对产出内容抓出：`/fake` 要核对入参拼成
`{"city":"上海"}` 中文未乱、usage 与 stopReason 对上，`/live` 要核对真实 thinking 与 toolCallId。
块注释里不再写含 `*/` 的路径；baseUrl 正则改为要求 `https?://` 开头。

### 教训
运行时兼容性结论的强度由**最严格的那一档配置**决定，不是由"当前推荐配置"决定；
跑通之外必须同时记录那一档实际的运行时可用面（`process` / `Buffer` / `node:*` 各是什么），否则读者无法判断结论多硬。
探测脚本的通过判据永远不能是 HTTP 状态码 —— 必须逐项核对产出内容里的具体值。

## 2026-09-09 sessionId 里一个中文字符就把 400 变成 500（来源：TASKS「R6 顺带发现」/ DECISIONS 2026-09-09 R6 顺带 / commit 08e4a9e）

### 现象
Boss 提了一句"ID 应该没人用中文"。实测七种越界 sessionId：中文、emoji、CRLF、裸 LF、NUL、含空格、latin1 高位 `é`。
**前六种全部抛出未捕获的 TypeError 冒出 handler**，把一个本该 400 的请求变成 500。
意外的是第七种：`é` 其实能进 header 并正常回写 —— 所以上一个提交里写的"sessionId 必须是 ASCII"不准确，
真实运行时边界是 latin1。另外确认 CRLF 被 `Response` 构造器挡住，**不构成 header 注入漏洞**。

### 原因
sessionId 会被写进回写头 `X-Reins-Session`，而 header 值有运行时编码约束。
真正的判断依据不是"有没有人愿意用中文命名"，而是 **sessionId 是客户端可控输入**
（GET 从 query 取、POST 从请求体取），任何前端 bug 或恶意请求都能传进来，入口就必须校验。
原来的 `parseBody` 只查了"非空字符串"。

### 修复
`SESSION_ID_RE = /^[\x21-\x7e]+$/`（非空、可打印 ASCII、不含空格），POST 在 `parseBody`、GET 在解析 query 之后各校验一次，
越界回 400 `bad_request`。取比真实边界 latin1 更严有两个理由：一句话说得清、各处一致；且 header 值首尾空格会被 trim，
使回写的 `X-Reins-Session` 与客户端传入的不是同一字符串，这种静默不一致比直接拒绝更难查。
uuid / nanoid / hex / `user:42/sess-7` 照旧 200。3 个新用例，README 与技术方案里"必须 ASCII"的措辞一并纠正。

### 教训
凡是最终会进 HTTP header、SQL 标识符、文件路径的字符串，都要在**入口**按白名单正则校验，不要等下游库抛异常 ——
下游异常的类型和时机不受你控制，一个该 400 的请求会变成 500。
校验边界宁可比运行时真实边界更严一档：真实边界通常说不清（latin1 而非 ASCII）、各层还不一致。

## 2026-09-09 POST 的 sessionId 在请求体里，宿主在 principal 钩子里判会话归属根本做不到（来源：TASKS R6 / DECISIONS 2026-09-09 R6 / commit 424877e）

### 现象
`@reinsjs/server` 只有一个 `principal(request)` 钩子。审查时记的问题是"GET 读会话不绑 principal"，
真查下去发现比记录的更具体：分发处 `handleGet` **压根没收到** `principal`（只传给了 POST）；
而且 POST 的 sessionId 在**请求体**里，宿主想在 `principal` 里判归属就得 `clone()` 读一遍 body，
handler 随后还要再读一次 —— 对 POST 来说宿主**做不到**，光在 README 里写一句"请自行校验"挡不住任何人。
后果是：知道 sessionId 就能读走整条时间线。

### 原因
钩子的层级选错了。`principal(request)` 的职责是"谁在问"，它跑在 handler 解析请求体**之前**；
"他能碰哪条会话"需要 sessionId，而 sessionId 要等 handler 解析完 query / body 才有。
把两件事塞进一个钩子，就把一个后置判断硬塞到了前置时机。

### 修复
鉴权拆成两层：`principal(request)` 只解析"谁在问"，新增
`authorizeSession({ sessionId, principal, request, method, isNew })` 决定"他能碰哪条会话"，
在 GET 取出 query、POST 取出 body 的 sessionId **之后**、读写该会话任何日志**之前**由 handler 统一调用。
**只有显式返回 `true` 才放行**，`false` 与 `undefined`（漏写 return）一律回 **404** 而非 403 ——
403 等于确认"这条会话存在只是你不能看"，与外溢 blob"未被引用的 id 一律当不存在"同一规则；抛 Response 则原样返回。
GET 分支补上 principal 透传。缺省不检查（单租户与本地开发是主流），根 README 新增 Security notes 明示风险。
6 个新用例，其中"关口在读之前"用记账 log 断言 `reads === 0`。
连带：`SessionAuthzInput.request` 的注释一开始抄了 principal 的理由（"别在这里读 body，handler 随后要读它"），
方向恰好反了 —— authorizeSession 跑在 handler 读完 body 之后，宿主在这里**读不到**；注释已改正并用测试锁住这个时序。

### 教训
安全钩子的设计先问一句"做这个判断需要的输入，在这个时机拿得到吗"。拿不到就说明钩子的层级错了，
应该由框架统一解析好再回调，而不是让每个宿主自己去 clone 请求、争抢一次性的流。
布尔型安全钩子一律 fail-closed 到"只有显式 true 放行"，把漏写 return 当拒绝。

## 2026-09-09 同一轮注入的多条说明，归位之后前后颠倒（来源：TASKS「上线前全量代码审查与修复」④ / DECISIONS 2026-09-09 / commit 5b6bc34）

### 现象
Anthropic 中途 system 的归位逻辑，把同一轮里的多条 `system_note` 的顺序弄反了。
探针实测：感知说明与 pin 说明同轮注入，发到线上的请求里变成 pin 在前、感知在后；中段与末尾两个位置都反。
没有任何报错，请求照样 200。

### 原因
归位是"边算边 splice"：逐条计算这条说明该插到消息列表的哪个位置，然后立刻 `splice` 进去。
同一个落点的第二条插进去时会顶在第一条前面，于是同落点的多条整体逆序。
现有测试只断言了角色序列（user / system / assistant 的排列），没有查文本顺序，所以一直绿着。

### 修复
改成两步：**先算出每条说明在原始消息列表里的落点，按落点分组，再一次拼出**新的消息列表，不再边算边 splice。
补上断言文本顺序的测试。

### 教训
"边遍历边修改同一个列表"这类写法要默认怀疑顺序：改成先算索引、按索引分组、再一次性重建，索引就不会在遍历途中失效。
另一条同样重要 —— 断言角色序列的测试挡不住文本顺序 bug；测试断言的粒度必须覆盖到"这个字段错了会有什么后果"那一层。

## 2026-09-09 宿主中止在工具批中途不生效，剩下的工具照样跑完（来源：TASKS「上线前全量代码审查与修复」③ / DECISIONS 2026-09-09 / commit 5b6bc34）

### 现象
探针实测：一轮里两个并行工具，第一个正在执行时宿主 abort，**第二个照样执行**。
不止如此 —— 被中止那批里没执行的调用会被当成 pending，在下一轮开头一个一个继续执行，
直到全部跑完才真的暂停。对宿主来说，"我按了停止"之后系统还在动真格的写操作。

### 原因
runLoop 的宿主中止检查放在"补齐 pending 调用"**之后**。中止只跳出了当前这一批，
而补齐 pending 是循环下一轮的开头动作，它先于中止检查执行。

### 修复
中止检查**前移到"补齐 pending"之前**。工具批中途被中止后，余下的调用留作 pending 不执行，
下一轮开头直接 `paused(host)`，恢复时再补。

### 教训
中止的语义是"没执行的别执行"，所以中止检查必须放在**每一个会产生副作用的动作之前**，
而不是放在循环体的某个"自然位置"。写完中止支持后，验收要专门测"批量执行中途中止"和"暂停后恢复"两条路径 ——
单个动作的中止很容易对，批处理与恢复路径才是漏的地方。

## 2026-09-09 用户在工具结果回来之前插一句话，下一次请求就被 Anthropic 400（来源：TASKS「上线前全量代码审查与修复」② / DECISIONS 2026-09-09 / commit 5b6bc34）

### 现象
用户在工具还没返回结果时插话（续跑时带新 input、或进程死掉之后再发一条消息），
日志顺序如实记成 `[user_message, tool_call, user_message, tool_result]`。
实测模型的第二次请求就是这个形状，**Anthropic 直接 400**。

"tool_result 必须紧跟 tool_use"是厂商线协议的硬约束。而按宪法二，用户什么时候说的就该记在什么位置，
日志顺序不能为了迁就某家 API 而改。两者的冲突点被漏在了降级层没有处理。

### 修复

问题只是换了个地方。

### 教训
时间线是唯一真源，厂商线协议的排列约束属于降级层的职责 —— 凡是"某家 API 不接受这种顺序"的问题，
一律在降级层改形状并如实声明有损，绝不回头改日志的记录顺序。
判断规则：这个约束换一家模型还成立吗？不成立的就是降级层的事。

## 2026-09-09 网络端点原样接受任何事件草稿，伪造一条 approval_decision 就能绕过审批（来源：TASKS「上线前全量代码审查与修复」① / DECISIONS 2026-09-09 / commit 5b6bc34）

### 现象
上线前审查发现：`@reinsjs/server` 对客户端提交的 `input` 事件草稿**不做类型限制，原样写进日志**。
探针实测，客户端伪造一条 `approval_decision(approved=true)` 就能让 pending 的工具调用免审批直接执行。
同理还能伪造带 `system` 信任级别的 `system_note`（模型会当成系统指令），或伪造 `compaction` 把不想让模型看到的历史藏起来。

### 原因
"日志是唯一真源"这条宪法被单向理解了：只考虑了"什么都要能写进日志"，没考虑"谁有资格写哪一类事件"。
审批结论、信任标注、历史折叠这几类事件是**服务端权威**的，它们一旦可以由客户端伪造，
整个审批与信任体系就是纸糊的。

### 修复
两道白名单：
1. 循环层 `inputDraft` 只接受 `core.user_message` / `core.tool_result` / `core.system_note` / `ext.*`，
   其余在写日志之前抛 `RangeError`。
2. server 层更严，只放行 `user_message`（只取 content，actor / trust 由服务端定）与**客户端工具** pending 调用的
   `tool_result`（`toolCallId` 须 pending、工具须 `side:"client"` 或无 execute、name 取自 tool_call），其余 400 / 409。
审批结论只能走 `decisions` 通道（由 T10 的 HMAC 签名校验）。分两层是因为循环在进程内也可能被宿主拿不可信输入直接调用。

### 教训
凡是"事件 / 消息可由外部提交"的系统，都要按事件类型列白名单，并且区分"客户端能声明的字段"与"服务端权威的字段"
（actor、trust、审批结论、折叠记录一律服务端定）。
白名单要在**每一个信任边界**各设一道 —— 网络边界一道，库的公开 API 一道，因为进程内调用方也可能在转发不可信输入。

## 2026-09-09 replayTurns 按 actor 切轮，把模型自决的整理和 pin 切成了额外的轮（来源：TASKS E1）

### 现象
做 eval 指标时发现 `replayTurns` 重算出来的轮数不对：装了脑子模块的臂，
模型自决 `compaction`、模型 `pin`、`memory_op` 会让轮数凭空多出来，与实际请求次数对不上，
指标（每轮 token、轮数）跟着全歪。

### 原因
`replayTurns` 用 actor 切轮：模型输出的 actor 是 `model`，下一条非 model 事件就算一轮结束。

补一个回归用例。

### 教训
"谁做的"（actor）和"这是不是一次模型输出"（输出类型）是两个维度，不能互相代用。
凡是模型自决类机制会产生新事件的系统，任何按 actor 分组 / 切段的逻辑都要重新过一遍 ——
模型自决事件的 actor 天然是 model，会污染所有基于 actor 的判定。

## 2026-09-08 tsup 把 `node:sqlite` 剥成 `sqlite`，只有跑 dist 才暴露（来源：TASKS B11 ③ / DECISIONS 2026-09-08 B11 附 / spikes/edge-runtime-check/README.md）

### 现象
B11 dogfood 真实接入时，`@reinsjs/store-sqlite/node` 一跑就 `ERR_MODULE_NOT_FOUND`。
在此之前，vitest 与 `tsc` 全绿，源码路径跑过无数次，一点征兆都没有。

### 原因
tsup 8 缺省开启 `removeNodeProtocol`，会把 `node:` 前缀剥掉。
`node:sqlite` 不在 esbuild 的内置模块清单里，剥完就成了一个裸的包名 `sqlite` —— 一个并不存在的 npm 包。
vitest 与 tsc 走的都是源码路径（`tsconfig.base.json` 的 `paths` 指向源码、vitest 用 alias 指向源码），
从来没有加载过 dist，所以全绿掩盖了它。

### 修复
`tsup.config` 设 `removeNodeProtocol: false`，并把"**跑一次 dist 产物**"列入每个含 `node:*` 子路径包的验收项。
这条教训后来直接决定了 `spikes/edge-runtime-check` 的一条纪律：**一律打 dist，不打源码**，
因为验的是用户真正装到的东西。

### 教训
monorepo 里源码路径与 dist 路径是两套解析规则，测试全绿只证明源码路径是对的。
凡是打包器有"改写 import 说明符"能力的（`removeNodeProtocol`、externals、条件导出改写），
验收必须包含一次对 dist 产物的真实 import；`node:` 内置、可选依赖、子路径导出这三类最容易在这里出事。

## 2026-09-08 网关的 Claude 端点会改写请求，最后一条 user 之后的内容全被吞掉（来源：spikes/aireiter-gateway-check/README.md / DECISIONS 2026-09-08 B2 附带）

### 现象
B2 真模型实测里，模型两次在 thinking 里说"用户只发了一个句号"——
可我们发出去的请求里根本没有这条消息。感知说明注入的那一轮，模型完全没看见它。

### 原因
Boss 提议用 DeepSeek 直连做对照，用**暗号法**（把"暗号是 PINEAPPLE"放在请求的不同位置，只让模型回一行）
加上"逐条列出你看到的所有消息"，查明 aireiter 的 Claude 端点**会改写请求**，
不是裸的 Anthropic Messages API：模型顶着几千 token、非我们所写的身份提示与 `<budget:token_budget>`，
网关再前置一对 Human / Assistant 消息。而且**凡是排在"最后一条 user 消息正文"之后的内容全部丢失**：
末尾的中途 system（perception 的真实落点）、末尾的额外 user 消息、甚至同一条 user 里写在问题后面的文字。
历史中段的中途 system 被换成一条 user "Continue"；末尾 system 被换成 Assistant "OK" + Human "."
——"用户只发了一个句号"就是这么来的。对照组 DeepSeek 直连七种落点全部到达。

### 修复
Boss 决定**不为网关打补丁**（它只是测试用中转），降级层不改。
影响如实记录：经该网关跑 Claude 时 perception 说明当轮不可见、B1 的"落为中途 system、exact"这条不成立
（B1 测得的"注入不降命中"仍成立，丢掉的东西当然不影响缓存；compact 的规则提示走顶层 system，不受影响）。
**DeepSeek 直连列为当前唯一可信的 Anthropic 协议上游**，后续联网核实以它为主对照。
B11 dogfood 也改走 DeepSeek 直连 —— 该网关还有另一个毛病：对带工具结果的多轮请求两次掐断（20k / 60k 字符的单轮大请求反而都能过）。

### 教训
第三方"兼容端点"要先做忠实度体检再拿来做任何实测，方法是**暗号法 + 让模型逐条列出它看到的对话**，
而不是看请求有没有 200。判断规则：凡是模型的行为与"我们发出去的内容"对不上（thinking 里提到我们没发的东西），
第一嫌疑就是中间层改了请求，先做对照实验定位，再谈改代码。任何"经网关测得"的结论都要标注是在哪条链路上测的。

## 2026-09-08 装了带静态贡献的脑子模块，恢复续跑一律 409（来源：TASKS B6）

### 现象
B2 引入 Socket 静态贡献（`Socket.tools` / `Socket.systemPrompt`）之后遗留的问题，
到 B6 才被抓到：只要 agent 装了带静态贡献的脑子模块（compact、pins、memory 等），
审批暂停后再恢复，`@reinsjs/server` 的开流前预校验就判定配置漂移，回 409，续不回去。

### 原因
server 的恢复预校验在算 `configHash` 时**只用了宿主自己声明的工具表**，
没有并入 Socket 的静态贡献。而 runLoop 起步时是并入的 —— 两边算出来的哈希天然不同，
于是每一次带脑子模块的续跑都被误判成"工具集变了"。

### 修复
把静态贡献的解析抽成 core 的 `resolveSocketContributions`，server 预校验改为调用同一个函数，
两边口径统一。同一处还补了：静态贡献可以是按 `SocketSetup` 算一次的函数，缺 MemoryStore 时 memory 的工具与规则都不注册并告警一次。

### 教训
凡是"同一个值要在两处独立算出来并比对"的设计（configHash、签名、摘要），
两处必须调用**同一个纯函数**，绝不能各写一遍 —— 各写一遍的两份实现迟早分叉，
而且分叉的表现是"莫名其妙的校验失败"，最难查。

## 2026-09-08 模型把"先整理，然后做 X"这条指令一起折进摘要，整理完反问 X 是什么（来源：spikes/b2-compact-live/README.md / TASKS B2）

### 现象
B2 真模型核实（claude-opus-5，三段式任务）里的 `asked` 情形：用户在第二段开头明确要求
"先用 compact 折掉第一段并保留总重"。模型照做了，但它写的摘要只有
"Part 1 is complete... 接着做 part 2"，**把"然后做 part 2"这条还没执行的指令连同原文一起折没了**。
整理完模型反问"part 2 要做什么"，第三段也答不出 part 2 的结果。全程 HTTP 200，没有任何报错。

### 原因
模型无法复述一条它还没开始处理的指令 —— 它只能总结已经发生过的事。
而 compact 的切点是模型轮边界，最近一条用户消息正好落在被折叠的范围里。

### 修复
**最近一条用户消息由库缺省保住**：进 `pinsKept`，随 pin 一起在摘要之后重注入。
修复后同一情形模型整理完直接去查 4 / 5 号件，第三段答出 222 + 185 = 407。
同一次核实还确认了两件正面结论：模型给的 compact 入参三次全部合法；
整理后的请求形状（`user(摘要) → user(幸存的用户消息) → assistant(thinking+tool_use) → user(回执)`）
与阈值兜底摘要作首条 user 文本，真实 API 都接受。

### 教训
把上下文管理权交给模型时，库仍要守住模型**结构上不可能做对**的那几件事 ——
"还没执行的指令"就是其中一件，因为它不在模型的已知信息里。
判断规则：某项内容一旦丢失，模型是否有办法自己发现并补救？没办法的（未执行的指令、当前任务目标），库必须缺省保住。
另外，这类缺陷只在真实模型上出现，脚本化的假模型永远暴露不了 —— 机制正确性用单测，行为正确性必须真模型跑。

## 2026-09-08 pi-ai 没有 system 角色，注入的说明被当成用户消息发了出去（来源：spikes/s1-mid-system/README.md 与 spikes/README.md 的 S1 实测输出 / DECISIONS 2026-09-08 S1）

### 现象
进代码前的 S1 核实：把一条 `system_note` 交给 pi-ai 0.85.1 降级，
实际发出的请求里它是一条 `{"role":"user","content":"[[reins:system_note]]从现在起，..."}` ——
**以用户消息的身份发给了模型**。请求里唯一的 `role:"system"` 是 pi-ai 在 `supportsMidConvoEffort` 模型上
发的 effort 专用消息，content 为空。

### 原因
Anthropic 官方 API 已经支持带正文的中途 `role:"system"` 消息（Fable 5.1/5、Mythos 5.1/5、Opus 5/4.8，无需 beta 头；
Sonnet 5 及更早不支持），摆放规则是：不能是首条、必须紧跟 user 轮（含只带 tool_result 的 user）、
后接 assistant 或收尾，否则 400。但 **pi-ai 0.85.1 的 `Message` 类型里压根没有 system 角色**，
上游数据结构不支持，注入内容只能降级成 user。

### 修复
不 fork pi-ai，用它公开的 `onPayload` 钩子在支持的模型族上把带内部标记的 user 消息改写成 `role:"system"` 文本消息。
改写脚本第一版直接改写完就发，实测发现改写后的 system 后面紧跟着一条 user，**违反官方摆放规则**——
所以归位（挪到该 user 之后、下一条 assistant 之前）必须由降级层自己保证，不能指望改写就完事。
`capabilities.midConversationSystem` 按模型族声明，有损矩阵记录两种落点；第三方 Anthropic 协议上游
由宿主用 `ModelDefinition.midConversationSystem` 声明，缺省按不支持（发错了是 400，发保守只是有损）。

### 教训
"官方 API 支持某特性"与"我们用的那个客户端库支持"是两件事，进代码前必须用一段实测代码看**真正发出去的请求体**，
而不是读文档或看类型定义就下结论。
改写第三方库的请求体时，只做"格式转换"是不够的 —— 目标协议的**摆放 / 排列规则**也必须由改写方自己满足，
否则就是把 400 从一个地方挪到另一个地方。
