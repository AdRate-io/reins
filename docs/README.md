# reins 文档体系 —— 维护阶段怎么读、怎么写

> 2026-09-10 换代：项目从"创世"进入"维护"。文档按**什么时候会被读**分层，不按主题分层；活文档尽量少，历史一律沉淀为快照。

## 一、按阅读时机分层

| 时机 | 读什么 | 体积预算 |
| --- | --- | --- |
| 每次会话必读 | 根目录 `CLAUDE.md`（入口：身份、宪法、工作流、路由表、风险警示） | 红线 300 行 |
| 找活干 | `docs/TASKS.md`（只留未完成项与待 Boss 事项） | 50 行内 |
| 要全貌 | `docs/系统全景图.md`（包全景、事件模型、循环契约、脑子模块表、数据流） | ~300 行 |
| 深入某个包 | `docs/模块盘点/<包>.md`（架构概览 → 文件清单 → 核心流程 → 设计决策） | 每份 100～350 行 |
| 排查同类问题 | `docs/踩坑记录.md`（现象 → 原因 → 修复 → 教训，倒序） | 按事件检索 |
| 回溯"为什么这么定" | `docs/DECISIONS.md`（日期 / 决策 / 理由 / 可逆性，append-only） | grep 关键词，不整读 |
| 查接口与规格细节 | `docs/技术方案.md`（架构原则 P1~P9、事件模型、接口、脑子模块规格 + 每模块的实现记录） | **按 § 查阅，不整读**（88 KB） |
| 回溯需求 | `docs/PRD.md`（做什么、给谁、成功标准；状态头已确认） | 快照 |
| 翻旧账 | `docs/归档/`（调研报告、旧稿、已完成任务的完整记录） | 只作证据，不引用其中过期定位 |
| 上游行为核实 | `spikes/README.md`（每个核实脚本的结论与复跑方式） | 上游升级时复跑 |

## 二、活文档与快照文档

| 类型 | 文档 | 义务 |
| --- | --- | --- |
| **活文档**（过期即有害） | `CLAUDE.md`、`TASKS.md`、`系统全景图.md`、`模块盘点/*` | 改了代码就同步改，是提交的一部分 |
| **快照文档**（写完即冻结） | `DECISIONS.md` 各行、`踩坑记录.md` 各条、`PRD.md`、`技术方案.md` 的规格正文、`归档/*` | 只追加不回改；发现规格与代码不一致 → 在技术方案对应段落**追加**"实现（任务号）"说明，不改原文 |

技术方案是特例：它既是规格（快照）又持续追加实现记录。维护阶段的规则：**新增能力先写模块盘点与全景图，技术方案只在接口形状变化时追加一段**，不再把每个任务的完整实现记录堆进去。

## 三、写入路由表（收尾前的固定动作）

| 触发场景 | 写到哪 |
| --- | --- |
| 踩到坑（上游 API 行为与预期不符、静默失效、误判） | `踩坑记录.md` 新条目（四段式）+ 最普适的一条教训提炼一行进 `CLAUDE.md`「技术要点与风险」 |
| 做了设计 / 产品决策 | `DECISIONS.md` 追加一行；若改了接口形状，`技术方案.md` 对应 § 追加说明 |
| 新增 / 重构一个包或模块 | `模块盘点/<包>.md` 同步（文件清单必须准确）+ `系统全景图.md` 包表与数据流 |
| 新增事件类型、Socket 钩子、RunResult 状态 | `系统全景图.md` 对应表 + `技术方案.md` §4 / §7 |
| 改了缺省开关、硬约束、命令 | `CLAUDE.md` 对应节 |
| 完成任务 | `TASKS.md` 打勾 + 一行结论；里程碑收口后整段迁 `归档/` |
| 确认了但暂不修的问题 | `TASKS.md`「0.1 之后」（写清现象与方向；决定不修的写理由） |
| 需要 Boss 本人操作 | `TASKS.md`「待 Boss 本人操作」 |

## 四、各文档写法要点

- **CLAUDE.md**：概念锚点 + 特例补丁——知道概念名就能推出的一笔带过，字数花在推不出来的参数、字面值、反直觉处。自检："删掉这条，懂概念的人会怎么犯错？"答不上来就不配占行数。
- **模块盘点**：文件清单精确到"每个文件一句话职责"，这是它最大的价值——让"深入某模块"的成本从读代码降到读一个文件。重构后必须同步。
- **踩坑记录**：四段一环不缺，"教训"必须是可泛化的判断规则，不是"下次小心"。
- **DECISIONS**：一行一决策，理由列写"为什么不是别的选项"，可逆性列写"改起来要动什么"。
- **提交信息**：正文写根因与取向，不只写做了什么——本仓库的提交正文就是最细一级的实现记录（见 `git log` 已有风格）。
