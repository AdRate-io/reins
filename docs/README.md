# reins 文档体系规范 —— 维护期怎么读、怎么写

> 本文件是文档体系的使用手册。体系来自 Boss 的项目启动资产（从 AdRate 约 40 万行、两年迭代中提炼），按 reins 的实际做了裁剪：reins 是 TypeScript 库，不是 Web 应用，没有页面、数据库迁移与部署进程，技术栈与风险区以本仓库实际为准。
> 历程：2026-09-10 第一次换代（创世 → 维护，入口是 CLAUDE.md）；**2026-10-30 第二次换代**，对齐启动资产的最新规范：入口改名 `AGENTS.md`（多个 Agent 共读一份）、踩坑记录编号 + 三段式、待处理任务日期编号 + 搁置项、决策并入全景图「核心设计决策」、全景图加真源索引、PRD 与实施方案进目录并带状态头、AGENTS.md 行数棘轮。
> 本目录随仓库公开。它是维护者（AI 技术合伙人）的工作记忆，用中文写，面向自己而非用户；用户看各包英文 README。文中的 **Boss** 指产品所有者。

---

## 一、入口只有一份：`AGENTS.md`

Claude Code / Codex / Cursor 都读根目录 `AGENTS.md`，不再另设 CLAUDE.md（二者互相指向必然漂移）。reins 已经过了 v1.0，入口是**正式版**：描述已成型的系统，承载日常工作流。它与创世版的区别、换代仪式见启动资产，这里不重复。

正式版结构（从上到下按"每次会话必须知道"递减）：关于我和这套系统 → 两条宪法 → 工作原则 → 项目工作流 → 文档索引 → 文档维护规范 → 产品概述 → 技术栈 / 架构 / 代码结构 / 工程硬约束 → 鉴权与安全默认值 → 存储原则 → 关键脚本与发布 → 技术要点与风险 → 待执行迁移。

**体积上限 480 行**，由 `scripts/structure/agents-md-line-ratchet.test.ts` 钉死（只许调低，调高要 Boss 明确决定）；450 行起降级审视。

## 二、按阅读时机分层

| 时机 | 读什么 | 体积预算 |
| --- | --- | --- |
| 每次会话必读 | `AGENTS.md` | ≤ 480 行，棘轮守门 |
| 要全貌 | `docs/系统全景图.md`（包全景、事件模型、循环契约、脑子模块、**核心设计决策**、**真源索引**、核心导出索引、存储表） | ~500 行 |
| 深入某个包 | `docs/系统全景图_模块盘点/<包>.md` | 每份 100～350 行 |
| 排查同类问题 | `docs/踩坑记录.md`（`grep -n '^## '` 拿索引，只读命中节） | 按编号检索 |
| 找活 / 查已知问题 | `docs/待处理任务.md` | 活清单，只减不攒 |
| 回溯需求 | `docs/PRD/`（日期前缀 + 状态头） | 快照 |
| 回溯某个方案当时怎么想 | `docs/implementation-plans/`（进行中与近期）→ `docs/archive/implementation-plans/`（已完成，含 v1.0 技术方案） | 快照 |
| 翻旧账 | `docs/archive/`（调研、审查报告、任务记录、0.1～0.4 决策日志） | 只作证据，不引用其中过期定位 |
| 上游行为核实 | `spikes/README.md` | 上游升级时复跑 |

**历史引用的读法**：代码注释与旧文档里的「DECISIONS 2026-09-xx」指 `docs/archive/2026-10-30-决策日志DECISIONS-0.1至0.4.md` 当日的行；「技术方案 §x」指 `docs/archive/implementation-plans/2026-09-08-技术方案v1.0.md` 对应章节；「TASKS 某任务号」到 `docs/archive/*任务记录*` 里找。这些引用不批量改写——它们是快照的一部分，按文件名 grep 即可。

## 三、活文档与快照文档

| 类型 | 文档 | 义务 |
| --- | --- | --- |
| **活文档**（过期即有害） | `AGENTS.md`、`系统全景图.md`、`系统全景图_模块盘点/*`、`待处理任务.md` | 改了代码就同步改，是提交的一部分 |
| **快照文档**（写完即冻结） | `PRD/*`、`implementation-plans/*`、`踩坑记录.md` 各条、`archive/*` | 正文不回改；PRD 与方案的**状态行是唯一可变部分**；实施偏差写踩坑记录或全景图 |

活文档只有四个，每多一个都是持续的维护负债。目录或文件改名时可以机械更新快照里的路径，不改语义。

**状态头**（PRD 与实施方案标题下第一个引用块）：
- PRD：`📝 草稿` → `✅ 已确认（日期）` /（废弃）`❄️ 已搁置`
- 实施方案：`📋 待实施` → `🚧 实施中` → `✅ 已完成（日期）` / `❄️ 已搁置`
- 文件名 `YYYY-MM-DD-中文标题.md`，不带状态后缀；`✅ 已完成` 且 30 天无改动移入 `docs/archive/implementation-plans/`

## 四、写入路由表（收尾前的固定动作）

与 `AGENTS.md`「文档维护规范」是同一张表，以那边为准；这里补"为什么"：

- **决策只有一个落点**：全景图「核心设计决策」。0.4 之前的决策日志是一张 172 行的大表，决策与理由混在实现细节里，"为什么系统长这样"反而难找；现在每条决策一段话讲透，历史表冻结进 archive。重大决策链接实施方案。
- **真源只有一个落点**：全景图「真源索引」。AGENTS.md 只记真源之外的反直觉点。
- **完成的任务不留在任务板**：`待处理任务.md` 只放"确认了但还没做"的事；做完的结论进全景图 / 模块盘点 / 提交正文，git 历史即归档。
- **公开性规则**（2026-09-14 起，适用于一切文档）：第三方服务只记观察到的现象与复现方式，不写对其内部实现的推断；不写凭证、账号、真实业务数据（id、人名、客户名一律别名）；账号操作只写步骤不写账号；本地专用值走 gitignore 的文件或环境变量。

## 五、各文档写法

### 5.1 AGENTS.md

三条贯穿全文件的理念：

- **身份与经历是功能性组件，不是抒情。** 我每次会话都从这份文件醒来，把真实发生的合作具体写下来（真实功能名、真实攻坚战、真实数字），我才会以主人翁的状态工作。"关于我和这套系统"随每个版本交付追加一段，是共同经历的正史。
- **概念锚点 + 特例补丁。** 知道概念名就能推出八九成的一笔带过，字数花在推不出来的参数、字面值、边界、反直觉处。自检："删掉这条，懂概念的人会怎么犯错？"答不上来就不配占行数。
- **范式能推出的不逐条申明，守住即回收。** 「全局工程范式」能推出的不写；看似该统一却刻意不同的对子只进「刻意不对称清单」；刻意放行的只进「fail-open 例外登记表」；纯「X 的真源是 Y」只进全景图「真源索引」；被测试或 lint 机械守住的条目收缩成一句；条目不写溯源（日期、任务号归 git log 与全景图）。

"技术要点与风险"是最有价值的部分：只写凭直觉会误判的；每条 `**结论** — 原因 / 边界`，一到三行，高危加 ⚠️；字面值写到精确；最普适的那条踩坑教训提炼进来（那边是案卷，这边是警示牌）。

### 5.2 系统全景图

- AGENTS.md 放精简警示，全景图放详细描述，两边不重复长段。
- **核心设计决策是灵魂章节**：`**决策名**（日期） — 内容 + 为什么 + 边界`，一段话讲透；新决策落定当天就写。
- **真源索引**：域 / 真源文件或函数 / 口径，新建跨包共享的判定、派生、注册表即登记。
- 存储表清单带「保留策略」列；字段细节看 schema 代码。

### 5.3 模块盘点

固定四段：**架构概览 → 文件清单 → 核心流程 → 核心设计决策**。文件清单精确到每个文件一句话职责，这是它最大的价值。重构后必须同步。

### 5.4 踩坑记录

标题 `## <永久编号> [<域>] <可执行的结论>`，正文三段、封顶 10 行：

| 段 | 写什么 |
| --- | --- |
| 机制 | 为什么会这样，精确到文件 / 函数 / 字段；"无报错、静默失效"是关键信息 |
| 正确做法 | 下次怎么写；连带处理必须写 |
| 教训 | 这类场景下的判断规则，不写"下次小心" |

只写经验不写排查过程；编号只增不复用不重排，追加在文件末尾；域标签是闭合词表（见踩坑记录文件头），新增要明确决定。

### 5.5 待处理任务

编号 `OPT-YYMMDD-N` / `BUG-YYMMDD-N`（记录日期 + 当日序号），三章：待执行优化 / 待修复 Bug / 搁置项（写清理由与重启条件）。Bug 写 现象 → 根因 → 影响面 → 修复方向；优化写 背景 → 方案 → 优先级（含升级条件）。需要 Boss 拍板或本人操作的标 `【待 Boss 决策】` / `【待 Boss 操作】`。处理完即删除，有价值的经验迁进踩坑记录。

### 5.6 PRD 与实施方案

- **PRD**（`docs/PRD/YYYY-MM-DD-<名称>PRD.md`）是"做什么"的真源，不写实现；"非目标"必写；"开放问题"清空才能转 `✅`。需求变更走新 PRD 或修订章节。
- **实施方案**（`docs/implementation-plans/YYYY-MM-DD-<名称>.md`）：背景与根因 → 方案总览（**不动的部分也列出**）→ 具体设计 → 验证矩阵（读写两侧、正常与异常路径；行为类改动列真模型臂）→ 实施清单，最后一项固定是"按路由表更新文档"。
- 什么时候写：新增能力、改公开接口形状、跨两个包以上的改动写方案；Bug 修复与文案调整豁免，但验证与文档路由不豁免。

### 5.7 外部接口与上游行为

上游（厂商 API、pi-ai、TanStack AI、MCP SDK、宿主 CLI）的行为要写进代码的，先在 `spikes/` 写探针实证，结论写进全景图决策或踩坑记录。**缺了不猜**——凭记忆猜外部接口是最危险的失败模式。

### 5.8 提交信息

`type: 摘要`（`.githooks/commit-msg` 校验），正文写根因与取向，不只写做了什么——本仓库的提交正文就是最细一级的实现记录。

## 六、定期信息熵盘点

感到"同一件事要判断放哪"的次数变多时盘一次：同类东西有没有多种放置 / 命名 / 失败通道并存；守门机制有没有多套做法；AGENTS.md 有没有能抽成概念或下沉的散条目。每项归结成"统一成一个概念"，而不是加一条新规则。
