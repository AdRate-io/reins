> 审查时间：2026-09-10 下午
> 审查方式：6 路子代理并行（Bugbot 代码缺陷 + 安全审查 + 公开 API 与类型安全 + 架构合规与依赖健康 + 测试覆盖与边界条件 + 文档与代码一致性），关键发现人工交叉验证

## 总体结论

**0.1.0 可以发布，无 P0 阻塞项。** 有 4 个 P1 建议发前处理（或书面豁免），8 个 P2 建议处理但不阻塞，其余 P3 可发后再清。

## 一、发现清单

### P1 · 建议发布前修（4 项）

#### 1. handler 与 runLoop 对 `decisions` 校验不一致（子代理审批 HTTP 路径 409）

**来源**：Bugbot + 安全审查双方独立发现，人工验证确认

`runLoop` 分流 decisions：本会话的校验 pending，子会话的（带 `sessionId`）不校验、转发给 `ToolContext.decisions`：

```170:175:packages/core/src/loop/run-loop.ts
  const ownDecisions = (cfg.decisions ?? []).filter(
    (d) => d.sessionId === undefined || d.sessionId === sessionId,
  )
  const forwardedDecisions: readonly ApprovalDecisionInput[] = (cfg.decisions ?? []).filter(
    (d) => d.sessionId !== undefined && d.sessionId !== sessionId,
  )
```

但 `createAgentHandler` 对**全部** decisions 做父会话 pending 校验：

```461:466:packages/server/src/handler.ts
        for (const d of body.decisions ?? []) {
          if (!pendingIds.has(d.toolCallId)) {
            throw new RunStateError("unknown_tool_call", `审批结论指向的调用 ${d.toolCallId} 并不在等待中`, {
              toolCallId: d.toolCallId,
            })
          }
```

**影响**：`createAgent().run()` / 直接 `runLoop()` 下子代理审批冒泡可用；经 `agent.handler`（HTTP/SSE）发送子代理审批 → 409 `unknown_tool_call`，与 `asTool` 公开文档矛盾。

**建议**：预校验与 runLoop 对齐——仅对 `sessionId === undefined || sessionId === 当前会话` 的项做 pending 校验；并补 handler 集成测试。

---

#### 2. McpConnection close/connect 竞态（连接泄漏）

**来源**：Bugbot 发现

若在 `connect()` 尚未完成时调用 `close()`（如宿主热轮换 `mcpTools()` Socket），`close()` 只清 `this.client`（此时为 `undefined`），不影响正在进行的 `connecting` Promise。`ensure()` 完成后仍会把 `this.client` 设回新 Client → 连接泄漏、`onclose` 回调悬挂。

```90:94:packages/tools-mcp/src/connection.ts
  async close(): Promise<void> {
    const client = this.client
    this.client = undefined
    if (client) await client.close()
  }
```

**建议**：增加 `closed` / `abortConnecting` 标志，在 `ensure()` 完成路径上若已关闭则立即 `client.close()` 且不赋值。

---

#### 3. eval README 示例多处与真实 API 不符

**来源**：文档审查发现，人工验证确认

`packages/eval/README.md` 第 10-20 行的快速示例：

- `anthropicLowering` 不是本包或 lowering-pi 包的导出名称（应为 `anthropic(...)` 返回对象的 `.lowering`）
- `runEval` 缺少必填字段 `model: ModelRef`（见 `RunEvalOptions`）
- `maxResumes` 应在各 `EvalFixture` 上，不能放 `runEval` 顶层
- `checkGate` 的基线臂参数名是 `reference`，不是 `baseline`
- `compact()` / `perception()` 来自 `@reins/brain`，示例未写导入

**影响**：新用户按 README 编写的代码无法编译。11 个包 README 中唯一一段与代码明显脱节的快速开始。

**建议**：对照 `examples/eval/run.ts` 重写示例。

---

#### 4. lowering-pi 的 d.ts 仍暴露 pi-ai 类型给消费者

**来源**：公开 API 审查发现

`dist/index.d.ts` 顶部直接 `import { Model, Api, AssistantMessage, … } from '@earendil-works/pi-ai'`，且公开签名包含 `draftsOf(msg: AssistantMessage)`、`consumeStream`、`eventsToContext` 等带 pi-ai 类型的接口。

主路径 `anthropic()` / `openai()` + `PiLoweredPayload` 已用 opaque 设计隔离，但进阶 API 仍把 pi-ai 绑进消费者的类型解析链，与 CLAUDE.md 「pi-ai 类型不出 @reins/lowering-pi」约束不完全一致。

**评估**：若约束仅指「其它 @reins/* 包不依赖 pi-ai」则已达标（core/brain/server/reins 等确实无 pi-ai 类型）；若要求终端用户的 typecheck 也不涉及 pi-ai，则未达标。

**建议**：公开签名改为 reins 自有结构 / `unknown`，或进阶 API 移到未文档化的 `/internal` 子路径。0.1 可书面豁免——pi-ai 是 dependency，消费者安装时自动带上，不会导致类型解析失败。

### P2 · 建议处理但不阻塞（8 项）

#### 5. 运行时版本常量与 npm 版本不一致

**来源**：Bugbot + 公开 API 审查 + 文档审查三方发现

| 位置 | 值 |
|------|-----|
| 各包 `package.json` | `0.1.0` |
| `REINS_VERSION`（`@reins/core/src/index.ts:24`） | `"0.0.0"` |
| `REINS_MCP_CLIENT_INFO.version`（`@reins/tools-mcp/src/mcp-tools.ts:18`） | `"0.0.0"` |

MCP 握手、遥测、排错会暴露错误版本。建议统一到 `0.1.0`（或构建时注入）。

#### 6. CLAUDE.md 用例数过时

**来源**：文档审查发现，人工验证确认

CLAUDE.md 第 14 行写 **682** 个用例，实际 `pnpm test` 为 **695**。TASKS.md 与根 README 已正确。

#### 7. decisions[].sessionId 未走 SESSION_ID_RE

**来源**：安全审查发现

HTTP 入口对请求的 `sessionId` 走了 `SESSION_ID_RE`（可打印 ASCII 无空格），但 `decisions[].sessionId` 只校验 `typeof === "string"`，未走同一正则。风险低（该值不进 HTTP header，仅转发给子 run），但与 fail-closed 哲学不完全一致。

#### 8. server abandon 路径无测试

**来源**：测试覆盖审查发现

`handler.ts` 的 `pump().catch` 中对未 `begin()` 的 run 调用 `abandon()`，避免会话永久 409。全仓库无 `abandon` 断言，也无 "200 + SSE `error` 帧" 的用例。建议补 1-2 个用例验证该路径。

#### 9. adapter 应对 @tanstack/ai 声明 peerDependencies

**来源**：公开 API 审查发现

`@reins/adapter-tanstack-ai` 的 `package.json` 将 `@tanstack/ai` 放在 `dependencies`，未声明 `peerDependencies`。宿主若装两份 `@tanstack/ai`，`ChatMiddleware` 的引用同一性判断会失败（与 R7 审批中断检查同类风险）。

#### 10. dev 依赖链存在 high 级别 CVE

**来源**：架构合规审查发现（`pnpm audit`）

9 条告警（2 high、6 moderate、1 low），主要路径：`@reins/server` → miniflare（dev）→ undici/sharp。不进入 npm 发布 tarball，不影响运行时。建议升级 miniflare 或加 `pnpm.overrides`。

#### 11. 模块盘点多处小过时

**来源**：文档审查发现

- `docs/模块盘点/core.md` 写 lowering 无单测，实际 `trust.test.ts` 已存在
- `docs/模块盘点/adapter-tanstack-ai.md` 仍写版本 0.0.0、middleware 845 行（实际 0.1.0、928 行）
- `examples/minimal/agent.ts` 注释中存储 API 名称写 `sqliteStore("./agent.db")`，正确应为 `sqliteStores(openSqlite(...))`

#### 12. ui-agui README 示例参数命名易误导

**来源**：文档审查发现

`createAgentHandler(agent, ...)` 的第一参为 `AgentDefinition`，示例中的 `agent` 变量若由 `createAgent()` 产生则类型不匹配（需 `agent.definition`）。README 下方有说明 "`reins` package already uses `aguiEncoding()` as the default"，但快速示例仍可能误导。
