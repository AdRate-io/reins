# 嵌入式 Agent SDK 设计方案（讨论稿 v0.1）

> 日期：2026-09-07
> 状态：方向已对齐，接口为草案，待在独立 SDK 项目中定稿
> 来源：Boss 与技术合伙人在 adrate 会话中的讨论收敛，含对 DeepSeek Harness、pi、Vercel AI SDK、anima、OpenAI Responses 的实测核对

---

## 0. 一句话定位

**一个元基础优先、配置装配、可嵌入任意 Node 进程的 agent 运行时库。** 项目 import 它，它跑在项目自己的进程、数据库和鉴权上下文里。对外开放的是元基础（primitives），不是成品能力；成品能力由使用者组合元基础得到，库只附带少量配方（preset）。

它**不是**：
- 独立进程的 agent 应用（dsh、Claude Code 那一类）
- 面向 coding 场景的工具箱（文件系统、终端、沙箱不是默认世界观）
- 开放生态框架（第一版只服务我们自己的项目，不为陌生人替换内核付元框架成本）
- 只服务某一个项目的封装（能力真源复用之类的项目专属资产不进库）

## 1. 本轮已对齐的决策

| # | 决策 | 依据 |
| --- | --- | --- |
| D1 | 形态是库，不是框架、不是应用 | dsh 官方架构文档明确拒绝进程内挂载，唯一入口是 CLI；我们要的是 import |
| D2 | 内部真源是扁平、类型化、可扩展、带版本的事件流 | 借 OpenAI Responses 的 item 形状，但类型集合自己定义，不采用任何厂商 schema |
| D3 | 三层结构：事件日志 → 投影 → 降级 | AI SDK 不灵活的根源是把降级层的角色约束当成了真源；anima 的 Canonical 层同样犯了这个错 |
| D4 | 可插拔点是有限枚举的接缝（八个元基础），不是"万物" | dsh 的复杂度全部来自零特权内核 + Cordis 元框架，我们不需要 |
| D5 | 工具配置化直接接 MCP（stdio 对应命令行型、HTTP 对应远程调用型）+ 进程内函数 + OpenAPI 描述，不发明新协议 | 工具层的"标准化协议"已经存在 |
| D6 | 降级层（provider 适配）复用 pi-ai，隔离在自有接口后面，不自养 | pi-ai 覆盖 10 种线协议、149 个测试文件、reasoning/thinking 回放完整、维护极活跃（见 §3.2） |
| D7 | "上下文管理交给模型"不是对外能力，是内置配方 | 由 Projection 策略 + Tool + 提示词组合而成，用户可替换 |
| D8 | 模型自决类配方必须配 eval 一起做，否则不上 | Codex 压缩死循环烧额度是真实事故 |
| D9 | 第一版事件 schema 就带版本号与迁移约定 | 事件日志是持久化的，跨项目后改字段就是跨项目迁移 |

## 2. 元基础清单

八个元基础 + 一层装配。每个元基础只回答一个问题。

| 元基础 | 回答的问题 | 备注 |
| --- | --- | --- |
| Event | 发生了什么 | 一切的原子；类型化、可扩展、带 schema 版本 |
| EventLog | 事件存在哪、怎么读回 | append-only 接口；宿主用文件 / SQLite / Postgres 实现 |
| Projection | 这一轮模型应该看到什么 | 从完整日志算出模型上下文；压缩、预算提示、过滤都是它的策略 |
| Lowering | 怎么翻译成某家 API 的请求并把流式响应翻回事件 | provider 适配层；第一版包裹 pi-ai |
| Tool | 模型能调用什么 | 统一接口 + 三种来源适配（进程内 / MCP / OpenAPI） |
| Loop | 一轮怎么跑 | 带拦截点的循环：模型调用前后、工具执行前后、轮次结束 |
| Policy | 什么可以做、什么要先问 | 对工具调用和事件的守卫；审批、权限、配额都是它的实例 |
| Session | 这是谁的哪段对话 | 身份（principal）、分叉、交接（handoff） |
| Assembly | 以上怎么拼成一个 agent | 声明式配置 → 实例图；借 dsh 的 profile / bundle 思想，去掉元框架 |

### 2.1 数据流

```
                 ┌──────────────┐
  宿主输入 ──────▶│  EventLog    │◀──── 所有事件 append（含模型输出、工具结果、审批、压缩摘要）
                 └──────┬───────┘
                        │ 完整日志
                        ▼
                 ┌──────────────┐
                 │  Projection  │  策略链：过滤 → 折叠（压缩摘要替代原始段）→ 注入（预算提示等）
                 └──────┬───────┘
                        │ 模型上下文（仍是我们的事件类型）
                        ▼
                 ┌──────────────┐
                 │  Lowering    │  事件 → pi-ai Message[] → 某家线协议；流式响应 → 事件
                 └──────┬───────┘
                        ▼
                    Provider API
```

Loop 驱动整条链，Policy 挂在 Loop 的拦截点上，Tool 由 Loop 在 tool_call 事件处分派，Session 提供 principal 和日志的归属。

## 3. 参考对象实测结论

### 3.1 DeepSeek Harness（dsh）

- 完整 coding agent 应用，2026-08-13 开源，Developer Preview，官方声明会有破坏性变更
- 架构文档三条硬事实：① 唯一入口 `dsh` CLI + profile，有校验脚本拒绝进程内挂载；② 默认工具集以 fs / shell / terminal / sandbox 为中心；③ 嵌入 SaaS 只能子进程 JSON-RPC
- 值得借的两个思想：append-only session log 是模型上下文唯一真源；内置工具与外接 MCP 工具走同一条流水线受同样审批约束
- 不借的：Cordis 元框架、零特权内核、循环本体插件化

### 3.2 pi（earendil-works/pi）

**pi-ai（降级层，决定复用）**，`/tmp/pi-src/packages/ai` 实测：

- 2.4 万行，149 个测试文件，v0.85.1 发布于 2026-09-05，2026-09-07 仍有提交
- 线协议 10 种：`openai-responses` / `azure-openai-responses` / `openai-codex-responses` / `openai-completions` / `anthropic-messages` / `bedrock-converse-stream` / `google-generative-ai` / `google-vertex` / `mistral-conversations` / `pi-messages`（自有网关协议）
- Responses：`store: false` + `include: ["reasoning.encrypted_content"]`，加密推理条目回放；处理 reasoning 与 function_call 配对；Azure 漏字段修补
- Anthropic：thinking signature 逐块拼接回传、redacted_thinking 透传、adaptive thinking / effort 映射、cache_control 断点、会话中途 effort 切换、签名不匹配恢复
- 入站流式归一化 12 种事件：start / text_{start,delta,end} / thinking_{start,delta,end} / toolcall_{start,delta,end} / done / error
- OpenAI 兼容长尾厂商一张兼容开关表（`OpenAICompletionsCompat`），按 URL 自动探测
- 跨 provider 切换时自动降级图片、归一化工具调用 ID（`transform-messages.ts`）
- `registerApiProvider()` 可注册自定义协议
- **限制**：① 消息模型三角色 user / assistant / toolResult，`Context = { systemPrompt, messages, tools }`，无会话中途 system 消息、无自定义条目类型 → 我们的事件日志在其上，投影后降级成这三种角色；② 硬依赖 openai / @anthropic-ai/sdk / @google/genai / bedrock 四家官方 SDK（有 lazy 变体）；③ 0.x，0.85.0 有破坏性变更 → pin + 隔离

**pi-agent-core（循环层，待定）**，官方 README：

- `AgentMessage[]` 可通过 TS 声明合并扩展自定义消息类型（文档示例 `notification`）
- 钩子：`transformContext`（请求前对消息数组裁剪/注入，对应我们的 Projection）、`convertToLlm`（必需，转成 LLM 可懂形态，对应 Lowering 前半）
- 拦截点：`beforeToolCall`（可阻断）、`afterToolCall`（可改写结果）、`shouldStopAfterTurn`（优雅退出）；`steer()` / `followUp()` 两个队列
- 会话持久化是树形（id / parentId）jsonl，SQLite 后端拆独立包，核心运行时无关
- **待核实**：树形会话与"append-only 日志唯一真源"能否对齐；自定义消息类型能否携带我们的 schema 版本

### 3.3 Vercel AI SDK

Boss 判定不灵活：循环无法插入、协议写死、不兼容其他协议。根因是内部模型即 messages。不再考虑。

### 3.4 OpenAI Responses 与压缩范式

- Responses 以 item 为单位（message / reasoning / function_call / function_call_output 并排在一条时间线），一次调用可含多个动作。这是 D2 的形状来源
- OpenAI 实际发布的压缩是**服务端阈值触发** `compact_threshold`，返回加密不透明 compaction item，模型不参与决策。Codex CLI 也是阈值触发，曾出现压缩死循环
- "余量感知交给模型、模型自决"的范式存在于 Cline 的 condense 工具、Self-Compacting Agents 论文（arXiv 2606.23525）、Anthropic task budget（服务端注入模型可见的剩余预算 marker），以及我们自己的 anima

### 3.5 anima（`另一台电脑~/Desktop/技术合伙人能力研究_anima/anima/`）

我们自己做过的 AI 伙伴运行时，已实现 Boss 所说的第三点：

- `src/session/perception.ts`：每步算上下文使用率，70% 注入"上下文使用提醒"，90% 注入"紧急"并附 token 数，另有自动压缩安全网
- `src/session/prompt.ts` 的 `CONTEXT_MANAGEMENT_PROMPT`：教模型两种处置——话题告一段落用 `switch_session` 带摘要开新会话；长任务用 `<memory_trigger>` 写长期记忆。核心原则"用户不应感知上下文切换"
- `src/tool/switch-session.ts` v3：事务性切换、CAS 改通道映射、旧循环优雅退出、新会话自动续接、旧会话异步叙事归档。**但绑死 Slack / 飞书 DM 通道映射**
- `proposals/compressor-升级方案-v2.md`：工具结果处置权交给主模型，大块结果挂 hint，模型下一轮打 `useless / needs_compress / important` 标签；经 CC 审查与 Codex 确认，**未落地**
- 内核缺陷：Canonical 层"基于 OpenAI Chat 格式"，四角色，正是 D3 要反对的
- 压缩链新旧两条路径并存未收敛，即"没收尾"部分

## 4. 元基础接口草案

以下为草案，用于对齐语义，签名在 SDK 项目中定稿。

### 4.1 Event

```ts
interface EventBase {
  id: string                 // uuidv7，时间有序
  sessionId: string
  seq: number                // 会话内单调递增
  at: number                 // Unix ms
  type: string               // 命名空间化，如 "core.user_message" / "core.tool_call" / "ext.budget_notice"
  schemaVersion: number      // 该 type 的 schema 版本，见 §8 迁移约定
  actor: "user" | "model" | "tool" | "system" | "host"
  parentId?: string          // 分叉/因果链
  replay?: Record<string, unknown>  // 厂商专有回放数据（thinking signature / encrypted reasoning），不进通用字段
}
```

核心事件类型（`core.*`，库内置）：

| type | 载荷要点 |
| --- | --- |
| `user_message` | content parts（text / image） |
| `model_text` | text |
| `model_thinking` | text（可空）、`replay` 带签名 |
| `tool_call` | toolCallId、name、args |
| `tool_result` | toolCallId、content parts、isError |
| `system_note` | 宿主/系统注入的说明（预算提示、状态变更），**降级时按 provider 能力落到 mid-conversation system 或 user 角色** |
| `approval_request` | toolCallId、policyId、摘要 |
| `approval_decision` | toolCallId、approved、by |
| `compaction_summary` | coversSeq: [from, to]、summary、producedBy |
| `handoff` | toSessionId、triggerMessage、reason |
| `error` | 分类、message、retryable |

扩展事件（`ext.*`）由使用者声明，库只要求满足 `EventBase` 并登记 schema。

### 4.2 EventLog

```ts
interface EventLog {
  append(events: Event[]): Promise<void>          // 同会话内原子
  read(sessionId: string, opts?: { fromSeq?: number; toSeq?: number }): AsyncIterable<Event>
  tail(sessionId: string, n: number): Promise<Event[]>
  fork(fromSessionId: string, atSeq: number, toSessionId: string): Promise<void>
}
```

不变量：只 append，不 update、不 delete；压缩不删原事件，只追加 `compaction_summary`。

### 4.3 Projection

```ts
interface ProjectionStrategy {
  name: string
  apply(ctx: ProjectionContext): Promise<Event[]>   // 输入上一策略输出，输出本策略结果
}
interface ProjectionContext {
  events: Event[]            // 当前投影结果
  fullLog: EventLog          // 需要回看原始段时用
  session: SessionInfo
  budget: { contextLimit: number; estimatedUsed: number }
}
```

策略链顺序：过滤（权限/可见性）→ 折叠（用 `compaction_summary` 替代其覆盖的 seq 区间）→ 注入（`system_note` 预算提示等）。

### 4.4 Lowering

```ts
interface Lowering {
  toRequest(projected: Event[], tools: ToolSpec[], model: ModelRef): LoweredRequest
  stream(req: LoweredRequest, signal: AbortSignal): AsyncIterable<Event>   // 入站直接产出我们的事件
  capabilities(model: ModelRef): { midConversationSystem: boolean; thinkingReplay: boolean; parallelTools: boolean; ... }
}
```

第一版 `PiAiLowering` 实现：事件 → pi-ai `Message[]`（三角色）→ pi-ai `stream()`；pi-ai 类型不得出现在此接口之外。

### 4.5 Tool

```ts
interface ToolSpec {
  name: string
  description: string
  inputSchema: JSONSchema          // 统一 JSON Schema；进程内函数用 Zod 生成
  risk?: "low" | "medium" | "high" // Policy 的默认输入
  source: ToolSource
}
type ToolSource =
  | { kind: "inproc"; handler: (args, ctx: ToolContext) => Promise<ToolOutput> }
  | { kind: "mcp"; transport: "stdio" | "http"; server: string }     // 命令行型 / 远程调用型
  | { kind: "openapi"; spec: string; operationId: string; auth?: ... }
interface ToolContext { session: SessionInfo; principal: Principal; signal: AbortSignal; emit(e: Event): void }
```

### 4.6 Loop

拦截点（全部可注册多个，按序执行，任一返回 `block` 即中止该动作并产出事件）：

- `beforeModelCall(projected, req)` / `afterModelCall(events)`
- `beforeToolCall(call, ctx)` → `{ proceed } | { block, reason } | { defer: approvalRequest }`
- `afterToolCall(call, result)` → 可改写 result
- `onTurnEnd(turn)` → `{ continue } | { stop } | { handoff }`

### 4.7 Policy

```ts
interface Policy {
  name: string
  evaluate(input: { call: ToolCallEvent; tool: ToolSpec; principal: Principal; session: SessionInfo }):
    Promise<"allow" | "deny" | "ask">
}
```

`ask` 由 Loop 落成 `approval_request` 事件并暂停该调用；宿主通过 `resume(sessionId, approval_decision)` 续跑。审批协议因此是事件级的，可跨进程、可回放。

### 4.8 Session

```ts
interface Principal { userId: string; tenantId?: string; roles?: string[]; attrs?: Record<string, unknown> }
interface SessionInfo { id: string; principal: Principal; parentId?: string; createdAt: number }
interface SessionManager {
  create(principal, opts?): Promise<SessionInfo>
  fork(sessionId, atSeq?): Promise<SessionInfo>
  handoff(fromSessionId, triggerMessage, opts?): Promise<SessionInfo>   // 通用化 anima switch_session：库只负责建新会话 + 写 handoff 事件 + 停旧循环；重绑对话锚点交给宿主回调 onHandoff
}
```

### 4.9 Assembly（装配配置草案）

```yaml
# agent.yaml
schemaVersion: 1
model:
  provider: anthropic           # 交给 Lowering 解析
  id: claude-opus-5
  options: { effort: high }
store:
  eventLog: "@host/pg-event-log"          # 宿主实现的模块 id
projection:
  - "@sdk/visibility-filter"
  - "@sdk/compaction-fold"
  - { use: "@sdk/budget-notice", with: { warnAt: 0.7, criticalAt: 0.9 } }
tools:
  - { kind: inproc, module: "./tools/orders.ts" }
  - { kind: mcp, transport: stdio, command: "uvx", args: ["some-mcp-server"] }
  - { kind: mcp, transport: http, url: "https://tools.example.com/mcp" }
  - { kind: openapi, spec: "./openapi.json", operations: ["listCampaigns", "updateBudget"] }
policies:
  - { use: "@sdk/risk-gate", with: { ask: ["high"], deny: [] } }
hooks:
  - "@host/audit-hook"
presets:
  - "@sdk/model-driven-context"           # 见 §6
prompt:
  system: "./prompts/system.md"
```

装配器把配置解析成实例图，未知模块 id 直接报错（fail-closed），不做猜测。

## 5. 降级有损矩阵（草案，需逐项实测）

| 我们的事件 | OpenAI Responses | Anthropic Messages | Chat Completions |
| --- | --- | --- | --- |
| `user_message` | message(user) | user | user |
| `model_text` | message(assistant) | assistant text block | assistant content |
| `model_thinking` | reasoning item（encrypted_content 回放） | thinking block（signature 回放，绑定同模型） | 无原生位置：丢弃或降为 `<thinking>` 文本 |
| `tool_call` | function_call | tool_use（同 assistant 消息内可多个） | tool_calls[] |
| `tool_result` | function_call_output | tool_result（必须紧跟对应 tool_use 的下一条 user） | tool 角色消息 |
| `system_note` | message(developer / system) | mid-conversation system（模型支持时）否则 user | user（或 system 若厂商允许中途 system） |
| `approval_*` | 不下发；折叠进 `tool_result`（被拒时 isError + 说明）或 `system_note` | 同左 | 同左 |
| `compaction_summary` | message(user) 或 developer 说明 | user 说明 | user 说明 |
| `handoff` | 不下发（新会话首条 user 消息承载 triggerMessage） | 同左 | 同左 |

有损项必须在 `Lowering.capabilities()` 中声明，Projection 据此选择等价表达，禁止静默丢弃。

## 6. 内置配方（presets）

### 6.1 `model-driven-context`（模型自决上下文管理）

由三样组合，全部可替换：

1. **Projection 策略 `budget-notice`**：使用率越过阈值时注入 `system_note`（含百分比与绝对 token 数），每档只注一次；保留硬阈值自动折叠作为安全网
2. **Tools**：`compact`（模型给出保留要点，库产出 `compaction_summary`）、`handoff`（模型给出 triggerMessage，库走 `SessionManager.handoff`）；可选 `mark_tool_result`（anima compress_hint 协议：对大块工具结果打 `useless / needs_compress / important`）
3. **提示词片段**：迁移 anima `CONTEXT_MANAGEMENT_PROMPT` 的语义，去掉 anima 专有词

**上线前置条件（D8）**：eval 至少覆盖三项——① 与纯阈值压缩比任务完成率与总 token；② 压缩后关键信息召回；③ 无死循环（连续压缩次数上限告警）。

### 6.2 `approval-gate`

`risk-gate` Policy + `approval_request/decision` 事件 + 宿主 `resume()`。附一个最小 React 组件示意（不在核心包）。

## 7. 从 anima 迁移的资产

| 资产 | 迁移方式 |
| --- | --- |
| 70% / 90% 双阈值注入 | → `budget-notice` 策略，阈值可配 |
| `CONTEXT_MANAGEMENT_PROMPT` | → preset 提示词片段，去专有词 |

## 8. 事件 schema 演进约定（第一版即执行）

- 每个事件 type 独立 `schemaVersion`，从 1 起
- 只允许追加可选字段不升版本；改字段语义、删字段、改必填一律升版本
- 读取路径按 type + version 查升级函数表（`upcast(v_n → v_n+1)`），查不到即拒绝读取（fail-closed）
- 日志文件/表不做原地迁移，读时升级；提供离线批量重写工具用于归档

## 10. 与 pi 的取舍

| 层 | 决定 | 理由 |
| --- | --- | --- |
| pi-ai | **复用**，隔离在 `Lowering` 后 | §3.2；自养 2.4 万行厂商协议代码不划算 |
| pi-agent-core | **待定**，两方案并列 | 见下 |

方案 A：站在 pi-agent-core 上。事件即其可扩展 `AgentMessage`，Projection 走 `transformContext`，Lowering 前半走 `convertToLlm`，Policy 挂 `beforeToolCall`。优点省循环代码；缺点会话持久化是树形 jsonl，与 append-only 日志的关系要对齐，且循环拦截点受其版本约束。

方案 B：自写循环（三百行量级），只复用 pi-ai。优点事件日志与循环完全按我们的语义；缺点 steer / followUp 队列、并行工具执行、重试等要自己写。

倾向 B，除非核实后 pi-agent-core 的会话模型能直接映射为 append-only 日志。

## 11. 第一版验收标准

**一个新项目用一份 `agent.yaml` 加两个接口实现（EventLog、onHandoff 回调），就能跑起一个带审批、带回放、带 MCP 工具、可在 Anthropic 与 OpenAI Responses 间切换模型的 agent。**

拆解：
1. 三种工具来源各至少一个端到端用例
2. 审批流跨进程重启可续跑
3. 任意会话可从日志完整回放并在任意 seq 分叉
4. Anthropic ↔ Responses 切换后 thinking / reasoning 回放不丢
5. `model-driven-context` preset 附 eval 结果
