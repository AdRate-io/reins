## BUG-261125-2. MCP run 起步的握手与 `tools/list` 不接中止、没有本包超时，服务器挂住时停止要延后约 2 分钟生效

- **记录日期**：2026-11-25（全库审查 #80，严重度 low；第一波 tools-mcp 修复未做，返修时登记）
- **现象**：MCP 服务器连得上但不回应时，run 起步先在 initialize 握手等 SDK 缺省 60 秒请求超时，`tools/list` 再等 60 秒；这期间宿主中止 run（用户停止、丢租约）不生效，要等这一步返回或超时后 run 才看到中止。不会永久卡死。空闲会话的停止收尾 run 走同一个起步解析，也会被拖住（HTTP 停止请求本身回 JSON 不等 run，不受影响）。
- **根因**：`mcp-tools.ts` 的 `tools()` 调 `conn.listTools()` 不带 signal（`listTools(signal?)` 支持，但无从取得）；`connection.ts` 的 `client.connect()` 不带 timeout / signal；`callTimeoutMs` 只作用于 `tools/call`。上游原因是 core `SocketSetup` 不带 signal，runLoop 直接 `await resolveSocketContributions(cfg)`，不与 signal 赛跑。
- **影响面**：只在服务器"能连上但不回应"时触发，停止延后、不丢数据。所有用 MCP 的宿主（AdRate 的 TikTok MCP）。
- **修复方向**：跨包——core 给 `SocketSetup` 加 `signal`（或让 runLoop 起步解析与 signal 赛跑，中止即按暂停收尾），tools-mcp 把它传给握手与 `tools/list`；本包另可给握手与 list 一个超时（复用 `callTimeoutMs` 或新选项，缺省 60 秒与 SDK 一致时单独加超时没有收益，所以重点是 signal）。不在第一波做：改 core 公开形状超出 tools-mcp 任务包范围，需走方案（公开接口形状变更）。

- **注意**：2026-11-24 起公司中转站的 Gemini 上游是 agent 桥接（Boss 确认，谷歌改协议后的暂时状况）：视频存成文件由模型按需读，`budget_usage` 里的视频 token 与时长无关；整次请求超过约 110KB 时只保留首尾、中间静默丢掉。走这条线时感知与阈值会低估视频占用，11-05 `spikes/media-parts` 经中转站测到的"估算 / 真实 0.98～1.08"也不能照此复现；判断媒体占比用官方线性口径。
- **重启条件**：换到按真实 token 计视频的通道后，出现媒体占上下文主体、整理请求兜不住的样本。
