# run 输入多条草稿（OnSet 建议 7）

> 状态：✅ 已完成（2026-11-02）

## 背景与根因

OnSet 建议 7（`docs/archive/2026-10-30-OnSet反馈-compact与perception改进建议.md` 末节）：宿主每次 run 的输入一部分是"要你做什么"（同事 / Boss 的新消息），一部分是背景（待办、相关条目变更、经验库更新）。`LoopConfig.input` 是 `string | ContentPart[] | EventDraft`，一次只能一条，宿主只能把背景拼进 user_message——模型分不清哪句是同事在要求、哪句是系统在告知（OnSet 盘点 80 次 run，背景约占 15%）。

宿主自建 Socket 在首轮 `beforeModel` 里 `emit` system_note 能绕，但说明落在任务之后（顺序反了），宿主还要自己记"本 run 发过没"；凡有"背景 + 任务"结构的宿主都得重写一遍。时间线本就是一串事件（宪法二），一次 run 追加几条不该被限成一条。

## 方案对比

| | 做法 | 判断 |
| --- | --- | --- |
| A（选） | `input` 增加 `readonly EventDraft[]` 形态，按序写入，逐条过白名单，任一不合规整批拒绝 | 宿主自己定顺序；复用现有白名单与 trust 处理；一次 append 天然整批 |
| B | OnSet 原提议：数组里字符串 / 内容片段与草稿混排 | 否：同一件事两种写法（熵控）；宿主写 user_message 草稿只多一行 |
| C | 新字段 `context?: EventDraft[]`，固定排在 `input` 前 | 否：把"背景在前"写死成框架决定；与 `input` 两条路表达同一件事 |

## 具体设计

### 公开接口

```ts
// core LoopConfig
input?: string | ContentPart[] | EventDraft | readonly EventDraft[]
```

- `agent` 的 `RunOptions.input` 改为 `LoopConfig["input"]`（类型单源，不再手抄一份）。
- `server` 的 `AgentRequestBody.input` **不变**：网络形状不扩，草稿数组只给进程内宿主。

### 归一（core `inputDraft` → `inputDrafts`）

`inputDraft(input): EventDraft` 改为 `inputDrafts(input): EventDraft[]`。两者都是 `@reinsjs/core` 公开导出（`loop/index.ts` 的 `export *`），改名属破坏性变更，changeset 明写；仓内无代码 import 它，只有文档引用（见实施清单 7）。判别按元素的 `type` 与 `actor` 一起看（自定义类型守卫，`Array.isArray` 对 readonly 数组收窄不够）：

1. 字符串 → 一条 user_message。
2. 数组，逐个元素归类：
   - `type ∈ {text, image, tool_reference}` 且无 `actor` → 片段；
   - 带 `actor`，或 `type` 以 `core.` / `ext.` 开头 → 草稿；
   - 其余（无法归类）或两类混排 → `RangeError("input must be content parts or event drafts, got …")`。
   - 全是片段 → 一条 user_message（现状）；空数组沿用现状当片段，不在本次改变。
   - 全是草稿 → 草稿数组。漏写 `actor` 的 `core.*` 元素因此被判为草稿、在下一步被拒，而不是静默变成怪异的用户消息。
3. 单个对象 → 一条草稿（现状）。

每条草稿过 `INPUT_DRAFT_TYPES` / `ext.*` 白名单，并校验 `actor ∈ Actor`（现状单条路径不查，非法 actor 会让 `DEFAULT_TRUST[actor]` 取到 undefined，一并收紧）；**全部校验完再返回**，任一不合规抛 RangeError，此时尚未写任何日志（与现状同一位置）。

### 写入

`runLoop` 新输入一段：`append(drafts.map((d) => withResultTrust(d, baseTools)))`——一次 append，同一 `at`、连续 seq，仍在 `tools_bound` 之后。顺序完全由宿主定；推荐 `[system_note(kind: "host"), user_message]`，每批只放一条 user_message（compact 只保最后一条）。这与 handoff 开场 `[system_note(host), …opening, user_message]` 是同一写法（`run-loop.ts` handoff 段），不是新约定。

### 不动的部分（写进用例锁住）

- **压缩**：`compact/plan.ts` 的 `latestUser` 只认最后一条 `core.user_message`，同批的 system_note 照普通说明折叠；需要常驻的走 pins。truncate 把连续非 assistant 事件算一轮，同批不会被切开。
- **降级层，不改代码，但送达位置因线路而异（审查第 2 条，如实写进 README）**：
  - Chat / Responses：按原序，背景在任务前。
  - Anthropic 线 `midConversationSystem` 关（DeepSeek 的 Anthropic 端口、部分官方型号）：背景以带标签 user 文本与任务并进同一条 user，标签在前。
  - Anthropic 线能力位开（fetch 版 `anthropic/to-request.ts` 的 pendingNotes、pi 版 `system-note.ts` 同算法）：厂商规则不许 system 紧跟 assistant，说明攒到 user 之后放出，形状 `assistant → user(任务) → system(背景)`，落点 exact + moved。**接受**：OnSet 的主诉是"分不清谁在要求、谁在告知"，角色区分在这条线上照样成立；若要在此线也保"背景在前"，只能改降级层的说明归位规则，影响感知等全部说明，另行立项，不在本方案顺手做。
  - pending 期间追加的这批随用户消息一起后移，顺序不变（`ir.ts` deferred / pi 版 awaiting）。
- **directive**：背景是陈述类，用 `kind: "host"` 普通说明即可；要模型去做的才标 `directive`（踩坑 42 已验证身份与照做率的关系，不另做对照）。
- **configHash / 续跑**：输入不进 configHash；带 `resume` 时的输入照旧追加在 `run_resumed` / 结论之后。

### server：补一道数组校验（安全）

现状对数组是两层放行：`checkInput` 见数组直接放行（`handler.ts:161`），而且**不带 resume / decisions 的数组请求根本不进预校验块**（`inputIsDraft` 排除数组，`handler.ts:491`），`body.input` 原样交给 `runLoop`。循环层开始认草稿数组后，客户端就能经网络写进 system 信任的 system_note，或带 `trust: "system"` 的 tool_result（`withResultTrust` 尊重草稿自带 trust），与踩坑 10 同类。改为：

- **数组校验放在预校验块之外、无条件执行**（不读时间线，紧跟 `parseBody`）：必须 `isContentParts`（非空、只含 text / image），否则 400 `"input content parts must be a non-empty array of text or image parts"`，日志不变。
- **片段按白名单重建**：text 只留 `{ type, text }`、image 只留 `{ type, mime, data }`；`user_message` 草稿分支的 `payload.content` 同样重建。网络来的东西不可能带上 `actor` 等判别字段，与"壳字段一律由服务端定"同一约定。
- 顺带收紧：此前空数组、含 `tool_reference` 或畸形片段的数组会进日志变成空 / 怪异的用户消息，现在一并 400。网络形状不变，只拒原本就不该收的东西。
- README Security notes 补一句"草稿数组只经进程内 `runLoop` / `agent.run()`，不经 HTTP"；AGENTS.md「刻意不对称清单」登记一行（见实施清单 7）。

### 已核实不受影响

eval 的 `EvalFixture.task.input` 是 `string | ContentPart[]`、asTool 只传字符串任务、TanStack 适配器走"导入客户端消息"无 `LoopConfig.input`、examples 都是进程内字符串；全仓网络入口只有 `createAgentHandler`。

### 刻意不做

- 网络侧接受草稿数组（例如一次回填多个客户端工具结果）——没有真实需求，另记 OPT 再议。
- 字符串与草稿混排（方案 B）。
- 给"背景"另设事件类型或 `kind`：`kind: "host"` 已表达"宿主说明"。

## 验证矩阵（只用假模型；纯接线，不花真模型的钱）

| 用例 | 判据 |
| --- | --- |
| `[system_note(host), user_message]` | 两条按序落日志、连续 seq、同 `at`，都在 `tools_bound` 之后；模型请求里顺序一致 |
| 数组含 `core.approval_decision` / `core.compaction` | RangeError，日志条数不变（含 `tools_bound` 也没写） |
| 内容片段与草稿混排；无法归类的元素；漏写 `actor` 的 `core.*` 元素；非法 actor | RangeError，日志不变 |
| 字符串 / `ContentPart[]` / 单条草稿 / 空数组 | 与现状逐字相同（回归） |
| 数组里的客户端 tool_result 草稿 | 按工具表落 trust（与单条一致） |
| 带 `resume` + 草稿数组；日志里还有未完成 tool_call | `run_resumed`、结论在前，草稿随后；降级时两条一起后移、顺序不变 |
| compact 折叠覆盖该批 | 最后一条 user_message 幸存，同批 system_note 被折 |
| 降级 Chat / Responses（fetch 版） | 断言具体顺序：背景 → 任务 |
| 降级 Anthropic 线 `midConversationSystem` 关 / 开（fetch 版、pi 版各一组） | 关：并进同一条 user、标签在前；开：`user(任务) → system(背景)`，落点 exact + moved |
| server：**不带 resume / decisions** 的草稿数组；空数组；含 tool_reference；畸形片段 | 400，日志不变；合法内容片段数组照常 |
| server：片段带多余字段（如 `actor`） | 重建后落日志只剩白名单字段，按 user_message 处理 |
| `agent.run({ input: [draft, draft] as const })` | 类型测试通过、两条落日志 |
