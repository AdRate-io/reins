# MCP 按调用选凭据（AdRate 建议 14）

> 状态：✅ 已完成（2026-11-19）

## 背景与根因

AdRate 建议 14（`docs/archive/2026-11-05-AdRate给reins的优化建议.md`「多身份 MCP 建议」）：一个用户管着多个 TikTok 身份，每个身份是一份独立的 OAuth 凭据，连的是同一台 TikTok MCP 服务器，各身份拿到的工具表相同（同一份服务端目录），区别只在能看到哪些广告账户 / BC。二期要让会话不再绑定单个身份：模型只管"对哪个账户做什么"，用哪个身份由宿主按调用入参决定。

现状（核实 `packages/tools-mcp/src/mcp-tools.ts` / `connection.ts`）：

- `mcpTools()` 一个 Socket 一个 `transport`，构造时建一个 `McpConnection`，每个工具的 `execute` 都闭包在这条连接上（`conn.callTool`）。
- `McpAuth.token()` 无参，绑在传输配方上，不知道是哪次调用。

AdRate 列的三种绕法都不取：

| | 做法 | 判断 |
| --- | --- | --- |
| 1 | 每身份一个 Socket + `prefix` | 否。工具表 ×N；"用哪个身份"变成模型的选择，而它是宿主的权限边界（宪法一：边界归库 / 宿主，判断归模型） |
| 2 | 宿主在 `override` 包的 `execute` 里转发到别的 Socket | 否。宿主在 reins 外自建连接池与分派，被转发的连接不在库的生命周期管理内 |
| 3 | 一条连接、`token()` 按隐式上下文（AsyncLocalStorage）换令牌 | 否，不做实测。能否成立取决于服务器是否把 MCP 会话绑定到初始化时的令牌、并发请求是否按请求取令牌，客户端无法保证，换一台服务器或服务器升级就可能失效；401 时 `onUnauthorized` 刷新哪一把也说不清；AsyncLocalStorage 也不是 Web 标准 |

## 方案

在 `mcpTools` 上加可选的 `route`：工具表仍由 `transport`（目录连接）在 run 起步取一次；配了 `route` 时，每次 `tools/call` 先问宿主要一个凭据键，按键从本 Socket 的连接池取（没有就按 `transportFor(key)` 懒建）连接去调。

与 AdRate 草案的差异（都已在对话中与 Boss 对齐）：

1. **保留 `transport` 当目录连接**，不引入"目录键 / 从可用键取第一个"规则。不配 `route` 时行为逐字节不变。
2. **不设"返回 null 由宿主给文案"这一档**：宿主在 `keyOf` 里抛错即可，循环已有的 catch 会把它变成模型看到的 `Tool execution failed: <message>`（`core/loop/run-loop.ts` 执行处）。`keyOf` 返回非字符串或空串 → 抛错（fail-closed），**绝不回退到目录连接**——宿主 bug 时静默拿错身份去改别人的账户，后果不可接受。
3. **按键刷新不加接口**：每个键的配方自带自己的 `auth`，SDK 传输层的 401 → `onUnauthorized` → 重试一次天然只作用于这一把。

### 公开形状

```ts
// ---- tools-mcp types.ts ----
/** 一次要路由的调用：MCP 原名（不是给模型看的改写名）与入参（validate 之后、原样交给 tools/call 的那份） */
export interface McpRoutedCall {
  name: string
  args: unknown
}

/**
 * 同一台服务器、多份凭据：工具表仍由 `transport` 在 run 起步取一次，每次 `tools/call` 由宿主选走哪份凭据。
 * 前提是各凭据看到的工具表相同（同一份服务端目录）；某个键的服务器上没有该工具时由服务器报错，按现有规则成 isError。
 */
export interface McpRoute {
  /**
   * 这次调用走哪份凭据。必须返回非空字符串；返回别的、或抛错 → 本次调用不发出，模型看到 isError，
   * 抛错的 message 原样给模型（宿主可写"该身份未开通官方工具授权"之类的话），不回退到目录连接。
   * 每次 execute 调一次（审批续跑后在真正执行时才调）
   */
  keyOf(call: McpRoutedCall, ctx: ToolContext): MaybePromise<string>
  /**
   * 该键的传输配方。每个键在连接池里第一次被用到时调一次，之后连接懒建、跨 run 复用、断了按这份配方重建一次
   * （与 `transport` 同一套语义）；凭据换了配方要 `evict(key)` 才会重取。抛错 → 本次调用 isError、不入池
   */
  transportFor(key: string): McpTransport
}

export interface McpToolsOptions {
  // …既有字段不变
  route?: McpRoute
}

export interface McpToolsSocket extends Socket {
  readonly transport: McpTransport
  /** 关掉目录连接与连接池里的全部连接；之后再跑 run 按配方重建 */
  close(): Promise<void>
  /**
   * 移出某个键的连接（凭据撤销、到期、换了配方）：立即移出连接池（之后路由到该键的调用重新调 `transportFor`），
   * 等该连接上在途的调用全部结束再关，返回的 Promise 在关完时 resolve（最长约一个 `callTimeoutMs`）。
   * 不存在的键、或没配 route → 无操作
   */
  evict(key: string): Promise<void>
}
```

### 规则

- **构造期校验**：给了 `route` 但 `keyOf` / `transportFor` 不是函数 → `TypeError("route.keyOf must be a function, got …")`（`X must be …, got …`）。
- **execute**（配了 route）分"发出前"与"发出"两段：
  1. 发出前：`const key = await route.keyOf({ name: info.name, args }, ctx)`；`typeof key !== "string" || key === ""` → 抛 `Error("MCP route must return a non-empty credential key for tool <name>, got <typeof / \"\">; the call was not sent")`。
  2. 发出前出任何错（keyOf 抛错 / 返回不合规 / transportFor 抛错或返回不合规）且 `ctx.signal?.aborted` → **不抛，返回** isError 结果 `"The call was not sent: the run was stopped before it reached the MCP server."`。原因：MCP 工具缺省不可重放（`isReplayable` 只认 `risk: "low"`），循环已先写 `tool_started`，execute 在中止状态下抛错会被写成"结果未知"（`run-loop.ts` catch 分支），而调用实际没发出——告诉模型的要与事实一致。没中止时照常抛，循环写 `Tool execution failed: <message>`。keyOf 正常返回后再查一次 `ctx.signal?.aborted`，中止同样返回这条"没发出"。
  3. 取池（**从 `pool.get` 到在途计数 +1 之间不能有 await**，否则被 evict 的旧项会在池外被用上）：`pool.get(key)`；没有则 `transportFor(key)` → 校验返回值是 `McpTransport` 形状（对象、`create` 是函数、`label` 是字符串；不合规抛 `TypeError("route.transportFor must return an McpTransport, got …")`）→ `new McpConnection(...)` → 同步 set 进池。同一键的并发首调用共享一条连接（`McpConnection.ensure` 已合并并发建连）。抛错与不合规都不入池。
  4. 发出：池项在途计数 +1，`conn.callTool(info.name, args, { timeoutMs, signal })`，`finally` 计数 −1；若该项已被 evict 且计数归零则关连接。结果翻译与现在一致。
- **tools/list** 只走 `transport`，`optional` 语义只看它；`route` 不参与工具表，不进 configHash——换路由规则不算配置漂移，暂停中的审批照常续跑，续跑执行时按当时的路由选凭据。
- **evict(key)**：先从池中删除并标记，再等在途计数归零后关（审查应修 2：SDK `close()` 会中止在途 fetch 并以 "Connection closed" 拒掉，而此时 `ctx.signal` 没中止，循环写"失败"，写请求却可能已到服务器，模型重试即重复写）。删后新来的调用会建新连接，不会拿到待关的那条。
- **close()**：关目录连接 + 池中全部连接（`Promise.allSettled`，全部尝试后若有失败抛第一个），清空池。与现有 `close()` 同为"收摊"语义，不等在途调用（宿主进程退出或换配置时调）。
- **池不设上限**：键由宿主控制（AdRate 一个团队的身份数），淘汰由宿主 `evict` 驱动。按 README 现有建议，宿主按配置缓存 Socket；Socket 本身被丢弃前应 `close()`。
- **不记路由到时间线**：路由是宿主的权限映射，模型不需要看；要审计宿主在 `keyOf` 或 `override` 包装层自己记（AdRate 已这样记 MCP 写操作）。
- **`override` 包装照常组合**：路由在基础 `execute` 里，`withBusinessErrors` 这类包装调 `tool.execute` 时自然经过路由。
- **连接池跨会话、跨用户共享**（池只按键区分，Socket 通常被宿主按配置缓存）。所以 `keyOf` 是唯一的授权点：必须用 `ctx.principal` 判"这个人能不能用这个身份"；键要从所有涉及账户的入参推出；`transportFor` 只能由键决定、不得捕获请求级上下文（同一键只调一次）。这三条写进 README 新节。
- **审批时还不知道走哪个身份**（路由在执行时才定）：要让审批人看到身份，宿主在 approval 规则的 `summary` 里用同一个函数算一遍。README 写明。
- **目录凭据撤销**：没有单独淘汰目录连接的办法，宿主 `close()` 后重建 Socket（池一起丢，下次按需重建）。README 写明。
- **每个键一条常驻 SSE GET**：SDK 握手后自动开（2.0.0 已核实），池不设上限时宿主要知道这项资源开销。README 提一句。

### 不做

- 不做"一条连接按调用换令牌"（做法 3），也不给 `McpAuth.token()` 加上下文参数。
- 不按键分别取工具表、不校验各键工具表一致（"各键相同"是宿主声明的前提，写进 JSDoc 与 README）。
- 不做池上限 / LRU / 空闲回收（智慧取舍：键数量由宿主业务决定且很小，淘汰时机只有宿主知道）。
- 不改 stdio 传输；`transportFor` 返回任何 `McpTransport` 都行，但多凭据只在 HTTP 场景有意义，README 只写 HTTP。

## 验证矩阵（假模型 + 内存 / Streamable HTTP 服务器，花费 0）

服务端用 `createMcpHandler` + 自定义 fetch 垫片，垫片按请求记录 `(authorization, JSON-RPC method, tool name)`，并能对指定令牌回 401。

| 用例 | 断言 |
| --- | --- |
| 不配 route | 既有用例全绿（行为不变）；`evict` 无操作 |
| 基本路由 | `tools/list` 只带目录令牌；按入参路由到 A / B 的调用各带各的令牌；同一键第二次调用不再握手（initialize 次数按令牌计） |
| 并发首调用 | runLoop 串行执行工具，同批测不出：直接对同一个 Tool `Promise.all` 两次 `execute` → `transportFor` 只调一次、initialize 一次 |
| keyOf 抛错 | 模型看到 `Tool execution failed: <宿主文案>`、isError；没有任何 `tools/call` 发出 |
| keyOf 返回 undefined / "" / 非字符串 | isError；没有任何 `tools/call` 发出（目录连接上也没有） |
| keyOf 异步 + ctx | 拿得到 `sessionId` / `principal` / 原名（带 `prefix` 时 `name` 仍是原名）/ 入参 |
| keyOf 期间被中止 | 不发 `tools/call`；经真 runLoop 断言模型看到的是 "The call was not sent…"，不是"结果未知" |
| transportFor 抛错 / 返回不合规 | isError；不入池，下次调用重新调 `transportFor` |
| 两个 principal 共用 Socket | keyOf 拿到各自 run 的 principal；按它路由到各自的连接 |
| 按键 401 刷新 | B 的令牌回 401 → 只调 B 的 `onUnauthorized`，重试成功；A 的不调 |
| evict | evict 后下一次路由到该键重新调 `transportFor`、重新握手；其它键的连接不受影响 |
| evict 时有调用在途 | 在途调用正常拿到结果（不被 "Connection closed" 掐断）；evict 的 Promise 在它结束后才 resolve；期间新调用走新连接 |
| close | 目录连接与池中连接全部关闭；之后再跑 run 按配方重建 |
| 审批续跑 | destructive 工具暂停等审批 → `keyOf` 未被调；批准续跑后执行时才调一次 |
| override 组合 | `override` 包装的 `execute` 经过路由（`withBusinessErrors` 形态） |
| 构造期校验 | route 缺函数按 `X must be …, got …` 抛 |
| README 配方 | `multi-credential.recipe.test.ts` 与 README 逐字一致，含网关式 `tool_execute({ tool_name, params: { advertiser_id } })` 路由与"未开通身份"抛错文案 |
| 全量 | `pnpm check` 全绿；`pnpm check:dist`（tools-mcp 含 `/node` 子路径） |

不涉及模型行为（模型看到的工具表与结果形状不变，只是调用走哪条连接），不跑真模型。真 TikTok 多身份端到端只能由 AdRate 用自己的凭据验，发版后在建议文档里请他们核实。

## 方案审查（2026-11-19，独立子代理）

无阻断。5 条应修全部采纳，均由方案作者对照源码复核属实：
1. keyOf 期间中止会被循环写成"结果未知"（MCP 工具不可重放、已写 tool_started），改为 tools-mcp 返回明说"没发出"的结果；
2. evict 不能掐断在途写调用（SDK close 中止在途 fetch），改为先移出、等在途归零再关；
3. 并发首调用用例改为直接 `Promise.all` 两次 execute（runLoop 串行执行工具）；
4. `transportFor` 返回值入池前校验形状；
5. README 写明池跨用户共享、keyOf 是唯一授权点，并补两个 principal 共用 Socket 的用例。

建议全部采纳：审批时看不到身份、目录凭据撤销的处置、`pool.get` 到计数之间不能 await、每键一条 SSE GET、错误文案带 got、文档路由补三处（不对称清单、待处理任务 OPT、Expiring credentials 指向）。另把做法 3 的否决理由改为不依赖未核对的规范原文。
