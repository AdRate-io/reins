# run 进行中拉取新输入（OnSet 建议 13）

> 状态：🚧 实施中

## 背景与根因

OnSet 建议 13（`docs/archive/2026-10-30-OnSet反馈-compact与perception改进建议.md` 末节）：角色的 run 进行中，别的角色转向、Boss 拍板或私信只能在宿主投递表里排队，等 run 结束才被看到。实测 104 次 run 里 21 次中途来了新消息、平均晚 130 秒、最长 18 分钟；期间角色照旧信息写记忆、发文档、派活，再误导已转向的角色。

根因在 core：`runLoop` 一次 run 只在起步收一次 `input`；宿主绕开循环直接 `log.append` 会撞 `seq_conflict`（seq 只在循环内分配）；server 对进行中的会话回 409。没有任何"在轮边界把新输入交给模型"的入口。

OnSet 数据：时间几乎全花在模型上（两次工具调用间隔 1～3 分钟，工具毫秒级，一批通常一个调用），所以**每次调模型前**是关键空档；同批工具之间是次要的。

## 方案对比

| | 做法 | 判断 |
| --- | --- | --- |
| A（选） | **拉**：`RunOptions` / `LoopConfig` 的 `pullInput` 回调，循环在每次调模型前调用，返回的草稿写入时间线 | 宿主在塞的那一刻才组装输入（背景差量按游标算才准）；投递表仍是唯一真源，宿主看到写入事件再认领，与起步输入同一条路；reins 不持有收件箱状态，进程崩溃不丢 |
| B | 推：宿主往 run 的收件箱里塞，循环在空档取 | 否：输入提前组装会过时、同一条动态可能进两份；内存里多一份状态，崩溃即丢 |
| C | 先停再重开（11-05 停止语义） | 否：每条同步都掐掉正在生成的一轮、写工具落"结果未知"；停止留给用户真要叫停 |

拉模式由 OnSet 提出，采纳。与 11-06 对话里的初版提议相比，**保留**：调模型前塞入、走白名单、不靠先停再重开。**移出**：

- **收尾前再拉一次**（审查第 3 / 6 / 9 条）：它要在 `endTurn` 里推翻 Socket 给的 `"stop"`（破坏"第一个给意见的定"；OnSet 的 `end_run` 已把收尾发言发出去，改判继续就是"交差后又干活"），触顶 `maxTurns` 时会把 done 变成没人回答的 `paused(budget)`，与中止交织时又要另定语义。收益却接近零：run 一 done，宿主本来就立刻用排队的消息起新 run，同一上下文、同一缓存前缀；而且最后一次拉取到 run 结束之间总有空档，宿主无论如何都要在 run 结束后再查一次队列。
- **同批调用之间的空档与"因新消息到达未执行"收尾**：OnSet 一批通常一个调用（见「刻意不做」）。

## 具体设计

### 公开接口

```ts
// core LoopConfig（per-run 字段）
/**
 * run 进行中的新输入（拉）。循环在每次调模型前调用一次（补跑 pending 的那轮与触顶 maxTurns 时不调）；
 * 返回非空即写入时间线（一次 append），空数组表示没有。
 * 宿主须在处理到写入事件时（await 完）完成认领再继续迭代；没被拉走的留在宿主那里，下一个空档或下一个 run 再给。
 * run 结束后宿主仍须查一次队列（最后一次拉取到 run 结束之间来的消息不会自动进本 run）。
 */
pullInput?: (ctx: { sessionId: string; turn: number }) => MaybePromise<readonly EventDraft[]>
```

- `turn` = 将要进行的轮次（拉完后 `turns++` 得到的值）。中止信号宿主手上本来就有，不重复传。
- 返回类型只收草稿数组："没有"只有空数组一种写法。
- **per-run 字段**（审查第 2 条）：加进 server `AgentDefinition` 的 Omit 列表，`createAgent({ pullInput })` 类型上拒绝；只经 `agent.run({ pullInput })` / `runLoop` 传。否则 handler 的 HTTP run、停止收尾 run、asTool 子 run 都会继承父宿主的回调去拉父的队列。

### 拉取点（唯一一个）

主循环顶部，宿主中止检查之后、投影之前。条件：本轮时间线**没有 pending**（补跑那轮不问模型，拉了会把新输入夹在 tool_call 与补出的 tool_result 之间）且 **`turns < maxTurns`**（触顶即暂停，拉了没人回答）。两项都用本轮已读的 `timeline` 与 `turns` 判断，不多读时间线；写入后把 `timeline` 改成 `let`、整体重新绑定为 `[...timeline, ...written]`——本轮后面的投影、`ctx.timeline`（brain 的 `timelineSoFar` / stopAfter 读它）、`lastBudgetUsage`、`executeToolCalls` 的拼接都要看到拉进来的事件，只传给投影不够。现有 pending 判断在投影之后，实现时把 `pendingToolCalls(timeline)` 前移复用。

后果：拉到的输入排在本轮 beforeModel 说明（perception、pin 快照）**之前**。第 1 轮也拉（起步 input 已 yield、宿主已认领，不会重复）。

拉完先查 `signal`：已中止则**不写**、走现有"本轮开始前中止"的暂停路径（宿主没看到写入事件就不会认领，消息仍在队列）。

### 校验与失败

- **白名单比起步收窄**（审查第 1 条）：只收 `core.user_message` / `core.system_note` / `ext.*`。`core.tool_result` 不收——拉取点上没有可回答的 pending 调用，写进去就是孤儿或重复 id。`withResultTrust` 对这三类是空操作，不走。
- **校验顺序**（审查第 8 条）：是数组 → 逐条过收窄白名单与 actor / payload 校验（复用 `checkInputDraft` 的内核）→ 逐条查 `registry.has` → 全部通过才 append。
- **不合规**（含返回 `undefined` / 非数组、白名单外类型、未登记 `ext.*`）：宿主代码错误，fail-closed，走 `fail()`——落一条 `core.error`（`category: "input"`）、返回 `status: "error"`，这一批一条不写。与起步"抛 RangeError、日志不写"刻意不同：起步时 run 还没写任何东西，中途已有半个 run 的日志，用 error 结局收口才能让宿主与回放看到断在哪。登记「刻意不对称清单」。同一回调里"抛错放行、返回值不合规掐掉"也是刻意的：抛错多半是宿主读库之类的瞬时失败，返回值形状不对是确定性的代码错误。
- **回调抛错**：记一条 `core.error`（`category: "host"`、`retryable: true`、`detail: { phase: "pullInput" }`，模型不可见），当作这次没有、run 照跑。理由：后果只是"晚一个空档送达"，消息仍在宿主队列里；为一次旁路读失败掐掉长 run 不值。登记「fail-open 例外登记表」。这条不改变 run 结局，eval 不当失败统计。
- **回调挂住不返回会让 run 挂住**：README 写明由宿主自带超时（与 `onEvent` 同类提醒）。
- **重复返回同一批**（审查第 7 条）：循环不去重，每次照写。生成器有背压，宿主在 for-await 里 await 完认领就不会重复；推荐草稿带 `provenance.ref` 记投递 id，宿主可照日志幂等认领。崩溃于"已写入、未认领"之间会重投，与起步输入同一性质。

### 对现有模块的影响（核过，写进用例或登记）

- **降级层不改代码，但形状与起步输入不同**（审查第 4 条）：中途写入的前一条是 tool_result（user 角色）。Anthropic 线开 `midConversationSystem` 时背景成了真中途 system，攒到 user_message 之后、下一条 assistant 之前放出（exact + 位置备注）；起步时前一条通常是 assistant，背景退成 `<system_note>` user 文本。Chat / Responses 按原序。中转站对中途 system 的送达见踩坑 42，真模型臂单独核（见下）。README 写明。
- **compact**（审查第 5 条）：`plan.ts` 只保折叠区里最后一条 user_message。一个 run 有起步任务 + 中途附言时，若两条同在折叠区，只有附言原样幸存。起步任务的承接分两条路径：模型自己整理时靠它写的摘要；阈值兜底的机械摘要只摘被裁 user_message 的开头 120 字（`core/src/projection/truncate.ts`），一条都不原样保留（现状，非本次引入）。不改：幸存兜的是"还没执行的指令"，起步任务正在执行。加用例锁住现状，`docs/待处理任务.md` 记 OPT，范围覆盖两条路径（重启条件：出现起步任务被整理后丢失的样本）。
- **stopAfter**：拉取只在调模型前，模型选 `end_run` 时已看到之前拉到的一切；非补跑轮"本批之后的新 user_message"不会出现，不需要推广补跑轮那条判据。
- **handoff**：`triggerMessage` 取最后一条可见 user_message，中途有附言时会是附言（审查第 13 条）。写进 AGENTS.md 风险条目。
- **budget**：各维按 run 算，一个 run 承接多件事会更早 `paused(budget)`。README 提醒宿主重估上限（审查第 12 条）。
- **pins 快照 / perception**：按时间线算，拉到的输入在 beforeModel 之前写入，本轮读数已含它，无隐含前提。
- **缓存**：只在末尾追加，不打前缀。**configHash / 续跑签名**：不进。

## 刻意不做（记 OPT，写重启条件）

- **收尾前再拉一次**：理由见方案对比。重启条件：宿主样本里出现"run 结束后才起新 run"造成可度量的延迟或误导。
- **同批调用之间的空档与"因新消息到达未执行"收尾**：重启条件：宿主样本里出现多调用批次、新消息落在批中且后续调用造成了误导。
- **server 进行中 POST 改投递**：HTTP 宿主要的话在自己的 `pullInput` 背后接队列即可。重启条件：有经 HTTP 投递的宿主样本。
- **TanStack 适配器 / asTool 子 run**：前者引擎形状不同；后者的新任务由父工具调用传入。
