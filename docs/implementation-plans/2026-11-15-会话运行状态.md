# 会话运行状态（AdRate 建议 11 / 12）

> 状态：📋 待实施

## 背景与根因

AdRate 建议 12（`docs/archive/2026-11-05-AdRate给reins的优化建议.md`「会话运行状态建议」）：会话列表要标出每个会话的状态，包括正在跑、等人处理、出错、跑完没看。宿主现在只能在 run 登记表外包一层：订阅最终信号，自己写一张状态表。这样做碰到五个问题：假异常空档、新旧 run 互相覆盖、终态分类跟着版本漂、审批等待起点对不上、进程被杀后没有终态。建议 11 要的是 `RunLease` 提供只读的"是否持有中"查询，AdRate 删除会话前要靠它判断"运行中拒绝"。目前 AdRate 是直读 `reins_runs`、自己写 SQL 判据。

核实源码后发现，根因不像 AdRate 说的那样是"run 结局不在任何存储上"，而是**时间线上的终结记号不全**：

| 结局 | 时间线现状 |
| --- | --- |
| 暂停 | `core.run_paused`，一定是这个 run 的最后一条 |
| 交接 | `core.handoff` |
| 出错 | 有 `core.error`，但它不一定是最后一条：重试前那条（`detail.willRetry`）、`pullInput` 回调抛错那条（category `host`）写完后 run 还在继续 |
| 正常跑完 | 什么都不写 |
| 进程被杀 / 生成器抛错 | 什么都不写（也写不了） |

除此之外还缺三样：一是 `client_tool` 中断在时间线上分辨不出来（暂停原因记成 `host`）；二是"在跑"只能用 `acquire` 去探测；三是跨表读"租约 + 日志"在两次查询之间存在空档。

## 方案

| | 做法 | 判断 |
| --- | --- | --- |
| A（选） | 时间线补齐终结记号：每个 run 以恰好一条终结事件收尾。用一个纯函数按"租约 + 最后一条 run 标记"分类；store-pg 用一条 SQL 取同一时刻的快照 | 结局进时间线（宪法二），各条执行路径（handler、`agent.run()`、asTool 子会话、TanStack）都覆盖到；单条语句就是快照，没有空档；宿主不用迁移表结构 |
| B | AdRate 原形态：`reins_runs` 加列、不删行，释放租约时一并写结局 | 否：结局只存在于旁表，"跑完了"这件事不在时间线上；只有经 handler 且配了租约的 run 才会写，`agent.run()`、asTool 子会话、TanStack 都漏；宿主还要做 DDL 迁移 |
| C | 不加事件，按日志推断"跑完"（最后一轮没有工具调用且没有 pending） | 否：要靠启发式。Socket 在纯文本轮也可能 continue；终结错误要靠枚举"非终结 error"来认，以后每加一种 error 都要回来改 |

### 公开形状

```ts
// ---- core：新事件（模型不可见，运维事件）----
/**
 * run 的终结记号（暂停之外）。每个 run 恰好以一条终结事件收尾：暂停是 core.run_paused，其余三种结局是这条。
 * 暂停不写这条：续跑凭据、server 补发判"末尾是带状态的 run_paused"、state.lastSeq 都依赖 run_paused 是最后一条。
 */
export type RunEndedPayload =
  | { status: "done" }
  | { status: "handoff"; toSessionId: string }
  | { status: "error"; category: string }
// "core.run_ended": RunEndedPayload    （schemaVersion 1）

// ---- core：已有载荷加可选字段（只加可选字段，不升 schemaVersion）----
interface ToolsBoundPayload {
  // …
  /** 本 run 的写入方承诺以终结事件收尾（0.14 起 runLoop 与 TanStack 适配器都写 true）。没有这个字段就是老 run，判不出是否中断 */
  marksEnd?: true
}
interface RunPausedPayload {
  // …
  /**
   * 停住的调用中需要外部给答复的那些（只列 toolCallId ∈ state.pendingToolCallIds 的）。用户停止收尾后为 []。
   * TanStack 适配器写的 run_paused 不带（与 state 同）
   */
  awaiting?: AwaitingCall[]
}
export type AwaitingCall =
  | { kind: "approval"; toolCallId: string; name: string; /** 该调用最早一条 approval_request 的 at */ requestedAt: number }
  | { kind: "client_tool"; toolCallId: string; name: string }
  | { kind: "subagent"; toolCallId: string; name: string; childSessionId: string; reason: PauseReason }

// ---- core：分类真源 ----
/** 会话里"最后一个 run"的标记事件类型；store 查最后一条标记时按这张表过滤（store-pg 绑参数，不在 SQL 里另写一份） */
export const RUN_MARKER_TYPES: readonly ["core.tools_bound", "core.run_paused", "core.run_ended"]

export type RunStatus =
  | { state: "running" }
  | { state: "idle" }        // 没有任何 run 标记：新会话、交接目标会话还没起过 run
  | { state: "unknown" }     // 最后一个 run 是老版本写的（tools_bound 不带 marksEnd），或标记读不出（未来版本 / 形状不合规）
  | { state: "interrupted"; seq: number; startedAt: number }
  | { state: "done"; seq: number; endedAt: number }
  | { state: "handoff"; seq: number; endedAt: number; toSessionId: string }
  | { state: "error"; seq: number; endedAt: number; category: string }
  | { state: "paused"; seq: number; endedAt: number; reason: PauseReason; awaiting: AwaitingCall[] | undefined }

/** 纯函数。held 来自租约；lastMarker 是会话里最后一条 RUN_MARKER_TYPES 事件（原始行即可，函数内过注册表 upcast） */
export function runStatusOf(input: {
  held: boolean
  lastMarker: Event | undefined
  registry?: EventSchemaRegistry
}): RunStatus

// ---- core：RunLease 可选方法（建议 11 的批量形态；可选，第三方实现不破）----
interface RunLease {
  // …
  /** 此刻有人持有且未过期的会话（不论持有者是谁）。判定与 renew 的"未过期"同一表达式、同一时钟；只读，不承诺查询后状态不变 */
  held?(sessionIds: readonly string[]): Promise<Set<string>>
}

// ---- store-pg ----
/**
 * 一条 SQL 取租约与每个会话最后一条 run 标记，再交给 runStatusOf。单条语句看到的是同一时刻的快照，
 * 而终结事件一定写在释放租约之前，所以任何时刻都处于"在跑"或"有标记"之一。
 * 前提：run 经 leasedRunRegistry 登记（createAgent + pgStores 缺省即是）；没有租约的部署里在跑的 run 会被判成 interrupted。
 */
export function pgRunStates(client: PgClient, sessionIds: readonly string[]): Promise<Map<string, RunStatus>>
```

### 规则

**终结事件（core `runLoop`）**

- done：`endTurn` 判 stop、`flush()` 之后，append `run_ended { status: "done" }` 再返回。`RunResult.lastSeq` 自然包含这一条。
- error：`fail()` 一次 append `[core.error, run_ended { status: "error", category }]`，同批原子写入。非终结的 `core.error`（重试前那条、`pullInput` 抛错那条）不带 run_ended。
- handoff：旧会话 append `core.handoff`，新会话写入开场之后、调 `onHandoff` 之前，在旧会话 append `run_ended { status: "handoff", toSessionId }`。开场写失败时 run 抛错，旧会话没有终结事件，判成 interrupted，这与"交接没完成"的事实一致。
- paused：不变，仍然只写 `run_paused`。`pause()` 已经读了时间线来算 pending，这次顺带算出 `awaiting`：从 interruptions 里取 approval / client_tool / subagent 三种，过滤成 toolCallId ∈ pending；approval 的 `requestedAt` 取时间线里该调用最早一条 `approval_request` 的 `at`（runLoop 里不可能找不到，找不到就当实现错误抛出，有用例锁住）。
- 起步：`tools_bound` 带 `marksEnd: true`。起步时已中止的 run 不写 tools_bound，但会写 run_paused，标记照样完整。
- 生成器抛错（续跑校验不过、`seq_conflict`、存储故障、Socket 抛错）不写终结事件。续跑校验发生在 tools_bound 之前，此时最后一条标记还是上一个 run 的结局，判定正确，因为这次什么也没发生；起步之后才抛的判成 interrupted。不做"兜底 catch 补写"：`seq_conflict` 和存储故障本来就写不进去，补写只能覆盖一部分情况，反而让语义变模糊。
- 不变式用例：runLoop 的每个出口（done / 各暂停出口 / handoff / 每个 `fail()` 调用点）返回时，日志最后一条事件 ∈ {run_paused, run_ended}，并且本 run 内只有这一条。

**分类（`runStatusOf`）**

1. `held` 为真 → running，不看标记。原因是 acquire 先于 tools_bound 写入，这段时间里最后一条标记还是上一个 run 的结局。进程被杀时租约要等到期（缺省 30 s）才放开，之后才判 interrupted。
2. 没有标记 → idle。
3. 标记过注册表读不出 → unknown（fail-closed，不猜）。
4. `run_paused` → paused（`awaiting` 原样带出，老事件为 undefined）；`run_ended` → 按 status 分类；`tools_bound` 带 `marksEnd` → interrupted，`startedAt` 取它的 `at`；不带 → unknown。
5. `seq` 用来区分前后两个 run 的结局（同会话唯一）；`endedAt` 与事件 `at` 同一时钟（循环时钟）。

**租约与快照（store-pg）**

- `run-lease.ts` 抽出 `HELD_SQL = expires_at >= ${DB_NOW_MS}`，renew、`held`、`pgRunStates` 三处共用，acquire 的抢占条件是它的取反（不改写法，用例锁口径）。
- `pgRunStates`：`unnest($1::text[])` LEFT JOIN `reins_runs`，再 LEFT JOIN LATERAL 取最后一条标记（`type = ANY($2::text[])` 绑 `RUN_MARKER_TYPES`，`ORDER BY seq DESC LIMIT 1`，走主键 (session_id, seq) 倒序扫描），读 `data::text`。不加索引：终结标记通常就在末尾；被杀的长 run 要倒扫到它的 tools_bound，成本可以接受。
- 入参白名单：数组、1～500 个、每个都是非空字符串、去重，不合规按 `X must be …, got …` 抛错。结果 Map 包含每个入参 id，不存在的会话是 idle。
- READ COMMITTED 下单条语句看到的是语句开始那一刻的快照。终结事件的 append 先于 release 提交（release 在 `ActiveRun` 收尾钩子里，而收尾钩子在生成器返回之后），所以快照里只要租约已经不在，就一定能看到终结事件。

**TanStack 适配器**

- `tools_bound` 带 `marksEnd: true`；状态里记"本 run 已写终结事件"。
- `onFinish`：如果已经写过 run_paused（pause 决定、审批暂停那几处），什么都不写；做过 handoff 则写 `run_ended(handoff)`；否则写 `run_ended(done)`。
- `onError`：`core.error` 和 `run_ended(error)` 同批写入；`onAbort` 已经写 `run_paused(host)`，不变。
- run_paused 不带 `awaiting`，进「刻意不对称清单」（与它本来就不带 `state` 是同一原因）。

**各降级层与编码器**：`core.run_ended` 进 `DEFAULT_MODEL_INVISIBLE_TYPES`。各家的有损矩阵（fetch 三条线、pi、TanStack）都记 dropped("operational event")；ui-agui 映射成 `CUSTOM`。老版本降级层遇到它走 default 分支 dropped，向前兼容。

### 不做

- 不建状态表、不改 `reins_runs` 结构、不改 release 的删行语义；宿主不用迁移。
- 不提供 `startedAt` / `runId`：宿主不再写状态之后，不需要"起跑时刻"来做条件更新；区分前后两个 run 用终结事件的 `seq`。interrupted 带 `startedAt`，因为那是唯一能说明"哪次没跑完"的信息。
- 不管已读：已读是宿主的产品概念，宿主拿自己的 `last_read_at` 和 `endedAt` 比较。
- 不推送：宿主自己定轮询频率。
- 不给 store-sqlite / 内存存储做 `runStates`：它们没有跨进程租约，宿主是单进程，可以拿 `runs.get(id) !== undefined` 当 held，自己找最后一条标记，再调 `runStatusOf`。等有宿主要再加。
- 不在 `runLoop` 里兜底 catch 抛错去补写终结事件（理由见上）。
- 不在 `RunResult` 或 SSE 帧里加字段：live 信号本来就带结局。
