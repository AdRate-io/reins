# 停止语义、中断不重放、server 停止请求、续跑校验收窄（AdRate 建议 1～4）

> 状态：📋 待实施

## 背景与根因

AdRate 接入前对照 `main@11c160f` 提了四条建议（`docs/archive/2026-11-05-AdRate给reins的优化建议.md`）。AdRate 的写工具直接改用户的广告，**重复执行就是重复花用户的钱**。

根因是同一个："补齐 pending"这条路不区分 pending 是怎么来的。`pendingToolCalls`（`core/src/loop/state.ts:14`）只看"有 tool_call、没 tool_result"，下面几种情况都会在下一个 run 开头被执行：

| pending 的来源 | 现在 | 应该 |
| --- | --- | --- |
| 宿主中止（丢租约、进程迁移） | 补跑 | 补跑（不变） |
| **用户点停止** | 补跑，且排在用户新消息之后、模型读到新消息之前 | 不补跑，落"没执行"，由模型结合新消息决定 |
| 等审批 | 有结论按结论办，没结论再挂起 | 不变 |
| **执行途中进程死亡** | 重放 | 写工具不重放，落"结果未知"，由模型决定先查还是重发 |
| 客户端工具 | 等宿主回填 | 不变 |

核实时确认的现场：

- 中止后留下 pending 的有**三处**：一轮开头发现已中止（`run-loop.ts:395`）、模型回复中途被掐（`:574`，已完整的 tool_call 已入日志）、工具批中途中止（`:919`）。建议原文只点了两处。
- 等审批时用户不批、直接发新消息：新消息照常入日志，补跑时这个调用再次挂起审批，模型一直不回话。现有能力已经够用：宿主发 `decisions: [{ approved: false, reason }]`，模型就会看到。不改 core，只写进文档（验证见下）。
- 续跑的配置校验只在带 `resume` 时才做。只带 `decisions` 不带 `resume` 时，core 与 server 都放行，签名、`pendingDigest`、`configHash` 都不查。这与全景图"审批结论只走签名保护的 decisions"的说法不一致，另记 BUG-261105-2，不在本方案内。

## 真模型验证（先于方案，2026-11-05）

脚本 `spikes/stop-and-interrupt/probe.mjs`。实现还没写，所以第一段用脚本化降级层造出现场；由宿主把打算落的结果当 tool_result 草稿写进日志，位置与将来循环落的一致；之后换真模型接着跑，最多 4 轮。验证的是两句文案：

- 停止：`Not executed: the run was stopped by the user before this call started.`
- 中断：`Execution was interrupted before a result was recorded; the outcome is unknown. Check the current state before retrying.`

场景：任务是"A 改预算 200 + B 暂停"，改 A 时用户点停止，B 落"没执行"。

| 场景 | 判据 | DeepSeek `deepseek-flash` | Claude |
| --- | --- | --- | --- |
| stop-redirect：新话"B 先别停，看看花了多少" | 不暂停 B，查了 B | 5/5 | Sonnet 5/5 · Opus 2/2 |
| stop-continue：新话"误点了停止，接着做完" | 暂停 B 恰一次，不重做 A | 5/5 | Sonnet 4/4 |
| stop-unrelated：新话问 A 花了多少 | 不擅自暂停 B | 5/5（还主动提醒"B 没暂停成"） | Sonnet 4/4 |
| unknown-done：改 A 执行中进程死亡，上游其实已改成 | 先查 A，不再改 | 5/5 | Sonnet 4/4（2 条完整轨迹不重做）· Opus 3/3 |
| unknown-notdone：同上，上游其实没改成 | 先查 A，再改恰一次 | 5/5 | Sonnet 2/2（1 条完整轨迹）· Opus 4/4 |
| approval-moved：等审批时用户说"改成 150"，宿主 deny + reason | 提出 150，不提 200 | 5/5 | Sonnet 4/4 · Opus 2/2 |

**Claude 一栏只计看得到决策那一步的格。** Opus 5.5 走中转站，号池回 503 "No available accounts"。改走 CF 网关打 Sonnet 5，跑到一半统一计费余额不足，回 402。很多格在第一步工具调用之后才断：决策已经落进日志，后续请求失败。判据只看已经落下的那一步，没有数据的格不计。**全部可观察的格里，没有一次违反判据的行为。** DeepSeek 30/30 都是完整轨迹。花费：DeepSeek 可忽略；CF 约 3 万输入 + 2.8 千输出 token，不到 0.2 美元。

结论：

1. 两句文案在两家模型上都有效，不需要再给模型加规则提示。
2. 停止后，模型能按用户新话改主意，也能按"接着做"补上没做的，不会一刀切地不做。
3. "结果未知"时，模型总是先查再决定。
4. 等审批时改口，靠现有的 deny + reason 就够了。

中转站或 CF 恢复后，Claude 用 `cf-sonnet` / `claude` 臂补跑完整轨迹，一律用 5.5 系列（脚本缺省已改为 `claude-sonnet-5-5` / `claude-opus-5-5`）。这是可选项，不阻塞实施。

## 设计决策

> 2026-11-05 方案审查（有条件通过）之后修订：签名材料、停止落点、正在执行的调用、子代理识别、空闲时 STOP、连接阶段中止、TanStack、asTool 续跑判据、STOP 响应形状九处已并入。复核（有条件通过）提出的三条也已并入：已暂停子会话的收尾、空闲收尾 run 的驱动、`pendingToolsDigest` 的取数口径。

### 共同约定：`core.tool_started` 的含义是"这次调用已经开始动手"

新增事件 `core.tool_started`（payload `{ toolCallId }`，v1）。它模型不可见，加入 `DEFAULT_MODEL_INVISIBLE_TYPES`，所以不切批，`batch.ts` 同一口径。

它由循环里唯一分配 seq 的 `append` 写入，不另开写入口。两种情况写：

- **不可重放的工具在 `execute` 之前写。**
- **任何工具返回 `subagentPause` 之后补写。** 这时子代理已经动过手了。补写不靠它防重放（asTool 本来就可重放），只是让停止时能认出"做了一半"。

`isReplayable(tool)` = `tool.replayable ?? tool.risk === "low"`，是纯函数，登记进真源索引。`Tool` 新增可选字段 `replayable?: boolean`。

### D1 停止是中止的一种原因（建议 1）

- core 导出 `class RunStop extends Error`（`name = "RunStop"`）和 `isStopReason(reason)`。宿主写 `controller.abort(new RunStop())`。判据看 `name`，不看 `instanceof`，因为装了两份 core 时 `instanceof` 会失效。
- **收尾挂在 `pause()` 内部**：`isStopReason(signal.reason)` 为真时，先 `settleStopped()` 再写 `run_paused`。这样所有暂停出口一次覆盖：
  - 一轮开头 `:395`
  - 重试等待时 `:559`
  - 模型回复中途 `:574`
  - 工具批之后 `:608`（批里有调用挂审批或子代理冒泡、后面的调用执行时被停止，走的就是这里）
  - 补跑 `:422`
- `:919` 的 `break` 之后，若已因停止而中止，**跳过 `endTurn` 直接暂停**。否则 Socket 判出 handoff / done 时，pending 会被带进一个不是 paused 的结局。
- `settleStopped()` 对时间线里每个 pending 调用落 `tool_result(isError: true)`，按"有没有动过手"分三句：
  - 没有 started：`Not executed: the run was stopped by the user before this call started.`
  - 有 started、工具不可重放（上一个进程执行中死掉的）：同 D2 的"结果未知"文案。
  - 有 started、工具可重放（子代理做了一半）：`Interrupted: the run was stopped by the user while this call was in progress; it may have partly taken effect.`
- 返回仍是 `paused(host)`，不新增 RunResult 状态，interruption 的 note 写 "stopped by the user"。日志里不再有 pending，下一个 run 正常问模型。
- 其它中止原因（丢租约、`onDisconnect: "abort"`、宿主自己的 abort）维持现在的行为：留 pending，恢复时补跑。
- **正在执行的那一个**：
  - 不感知 signal 的工具，照常跑完、落真实结果。
  - 感知 signal 的工具（tools-mcp 会把 `ctx.signal` 传给 `callTool`）会被掐断。若工具**不可重放**、抛错、且此时已中止（任何原因），落"结果未知"，不落 `Tool execution failed`，因为写请求可能已经到了上游。可重放的照旧落失败。
- **连接阶段被中止**：lowering-fetch 的 `fetch` 被中止时抛出的是 `signal.reason`。`retry.ts` 的 `isDefinitelyPermanent` 只认 `AbortError`，于是走 `fail`，run 以 `error` 结束而不是 `paused(host)`（审查推断，普通 abort 可能也有）。改法：
  - 第 1 步先写用例复现；
  - 失败分支里只要 `cfg.signal?.aborted` 就改为暂停；
  - `isDefinitelyPermanent` 一并认 `RunStop`。
- **子代理**：linked 模式下，父的 signal（连同停止原因）传给子，子按停止收尾自己的 pending。detached 模式不传，子跑完。
- **asTool 续跑判据**（`as-tool.ts:112`）：从"子日志末条是 `run_paused`"改为"**父日志里本次 `ctx.toolCallId` 已有 `tool_started`**"。subagentPause 之后会补写 started，所以"父在补跑同一个调用"一定能识别出来。旧判据有两个问题：
  - 停止后子会话末条仍是 `run_paused`，同一位专家下一轮的新任务会被吞掉；
  - 子会话已经暂停时，父被停止（空闲 STOP，或新 run 一轮开头就被停），子收不到 signal，子会话的 pending 一直留着（复核 N1）。
- **新一轮遇到子会话有遗留 pending**：父这次是新调用（没有 started），但子会话里还有 pending。asTool 先用预中止的 `RunStop` 跑一次子会话，只收尾、不问模型，再带新任务开跑。子会话的遗留调用就按停止落结果，不会再挂起审批。

### D2 中断后写工具不重放（建议 2）

- 补跑时，`executeToolCalls` 开头和审批结论一样，从时间线建 `started` 集合。遇到"有 started、没 result、不可重放"的调用不执行，直接落：`Execution was interrupted before a result was recorded; the outcome is unknown. Check the current state before retrying.`（isError）。
- 可重放的照旧重放：只读工具；asTool（缺省就是 `risk: "low"`，同时显式声明 `replayable: true`，防宿主把它标成 medium / high 后子代理续跑被误判）。
- 缺省口径与 approval 的 byRisk 一致：没声明 risk 的算写工具，不重放。MCP 只有 `readOnlyHint` 时映射为 low、可重放；同时带 `destructiveHint` 时为 high。
- 客户端工具不写 started，因为本循环不执行它们。
- 丢租约接管的竞态：旧实例还在执行，新实例看到 started 就落"结果未知"；旧实例随后落结果时撞 `seq_conflict`，与现有多实例语义一致。
- 新事件类型要跟着改的地方：
  - core：`events/core.ts`、`registry.ts`、`projection/filter.ts`
  - lowering-fetch：`ir.ts`、`chat/loss-matrix.ts`（dropped）
  - lowering-pi：`loss-matrix.ts`
  - ui-agui：`map-event.ts`（CUSTOM）
  - adapter-tanstack-ai：`middleware.ts`、`loss-matrix.ts`、`messages.ts`
- **回滚风险**：0.9 版遇到未登记的事件类型会拒读（`registry.ts:112`），升级后写过 `tool_started` 的会话回滚到 0.9 就打不开。changeset 与发版说明要写明。

### D3 server 停止请求（建议 3）

- 形状：`POST { sessionId, stop: true }`。
  - 必须带 `sessionId`，没带回 400。
  - `stop` 只能是字面 `true`，且不能和 `input` / `resume` / `decisions` 同时出现，否则 400。
- 鉴权走同一个 `principal` + `authorizeSession`，`method: "STOP"`，`isNew: false`。`SessionAuthzInput.method` 扩为 `"GET" | "POST" | "STOP"`。按 `method === "POST"` 放行写操作的宿主会拒掉 STOP，这是 fail-closed，README 写明。
- 处理与响应（**不等 `run.done`**，免得被 detached 子代理或挂住的 `onEvent` 拖住）：
  - 本进程有正在跑的 run：`abort(new RunStop())`，立即回 `200 { status: "stopping", sessionId }`。结果帧照常从原来那条流推出。若该 run 已经先因别的原因中止（停止原因只认第一个），pending 不会被收尾，再按一次停止会走下面的空闲路径。
  - 没有正在跑的 run、但日志里有 pending（等审批、丢租约留下的）：经 `runs.create` 起一个 signal 已是 `RunStop` 的 run。它在一轮开头就进入暂停、只收尾不问模型，回 `200 { status: "stopping", sessionId }`。撞上 409 `run_in_progress` 照常回 409。
    - 这个 run 没有流来驱动：STOP 路径要自己调 `run.drive(runLoop(...))`（同样经 `observed` 包 `onEvent`），并且 `ctx.waitUntil(run.done)`，否则 Workers 上收尾 run 可能被回收。
  - 没有正在跑的 run、也没有 pending：回 `200 { status: "idle", sessionId }`，重复按也安全。
- 多实例：`runs.get` 只认本进程。跨实例停止记 OPT-261105-5，`status` 字段已为它留了位置。

### D4 续跑校验收窄到"待执行调用相关"（建议 4）

- 当初的理由是"暂停时模型看到的工具集就是它做决定的依据"。P1（`tools_bound` + 工具变化说明）之后这个理由站不住了：工具表一变，模型下一轮就会被告知。真正要守的是**被批准的那次调用，执行时还是同一个工具**。
- 现在的校验既太严又太松：新增一个工具，所有等审批的会话都 409；同名工具改了 schema 反而查不出来。
- `SerializedRunState` 加两个可选字段，`v` 仍是 1：
  - `modelDigest`：模型引用的摘要。
  - `pendingToolsDigest`：pending 调用涉及的每个工具名，按名排序后取 `[name, description, inputSchema]` 的摘要；工具不在表里记 null。**取数口径是基础工具表**（runLoop 的 `baseTools`，即 server 预校验用的 `contributions.tools`），不取被 lazy-tools 等 beforeModel 补丁改过的本轮工具表。
- **签名材料**：`signingMaterial`（`state.ts:81`）是固定字段列表，不会自动带上新字段。新字段在场时**追加**进签名数组；旧状态的签名材料保持不变。`assertRunStateShape` 补新字段的类型校验。
  - 用例：给一份合法旧状态塞入新字段后验签失败。不这样做，伪造 `pendingToolsDigest` 就能绕开 `configHash` 校验（审查阻塞项）。
- `validateResume`：
  - 状态里有新字段时，只比对模型和 pending 工具定义，其余变化放行（模型会从工具变化说明里得知）。
  - 旧状态没有新字段，仍按 `configHash` 比对，兼容不破。
  - `allowConfigDrift` 语义不变。
  - 错误码仍是 `config_mismatch`，message 点名是模型变了，还是哪个 pending 工具变了。
- 适用面：runLoop 与 server 预校验调同一个 `validateResume`，后者已有跨包用例锁同口径。**TanStack 路径本来就不做续跑校验**（`middleware.ts:400` 只为 `tools_bound` 算 `configHash`），本方案不改，登记进「刻意不对称清单」。

### TanStack 路径

- 停止：TanStack 引擎自己处理中止与中断，D1 的"停止时收尾 pending"在它的边界上做不到对等，登记不对称清单。
- started：工具在 TanStack 引擎里执行，`bridge.emit` 是攒着、到 `onAfterToolCall` 才落日志。第 5 步先核实能不能在执行前直接 append 并同步 seq。做不到就登记不对称，再记 OPT，不硬凑。

## 不做的事

- 不给"停止"新增 RunResult 状态或模型可见的说明事件：没执行的结果已经告诉模型发生了什么，验证证明够用。
- 不改"等审批 → 批准 → 执行"这条正常路径。
- 等审批时用户改口，不在 core 里自动拒绝：交给宿主的 deny + reason，验证 4/4、5/5。
- 跨实例停止（OPT-261105-5）与"只带 decisions 不带 resume"（BUG-261105-2）不在本方案内。
