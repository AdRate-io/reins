# 本批可见与同轮收口（OnSet 建议 9 / 10）

> 状态：🚧 实施中

## 背景与根因

OnSet 第五轮效率盘查（`docs/archive/2026-10-30-OnSet反馈-compact与perception改进建议.md` 建议 9、10）提了两件事：

- **建议 9**：协作规则改成"互不依赖的动作一次回复里调"以省轮次后，出现"`board_update` 置待确认失败，后面的 `chat_send` 照样把'已交请看'发出去并唤醒对方"。希望同一批里前一个调用失败时，可选地拦下后面的。
- **建议 10**：`fork_done`、`end_run` 都是"调了某工具，本轮结束即停"，宿主自写"工具 + onTurnEnd Socket"时撞了四个坑。

四个坑逐条核实（2026-11-02）：

| 坑 | 源码事实 |
| --- | --- |
| 1 `onTurnEnd` 看不到本轮调用与结果 | `TurnContext` 在本轮开头构造（`run-loop.ts` ctx 段），`events` / `timeline` 是本轮前的快照 |
| 2 `afterTool` 不全 | 审批被拒、block、未知工具、入参不合法的结果直接落日志，不经 `afterTool`（`executeToolCalls`） |
| 3 补跑遗留调用后也走 `endTurn` | `run-loop.ts` 补齐 pending 段调 `endTurn(ctx, "continue")`，Socket 分不出是补跑 |
| 4 第一个给意见的 Socket 说了算 | 设计如此，只能靠注册顺序。OnSet 说 compact 请求会在 onTurnEnd 返回暂停，不准确：到线请整理在 `beforeModel` emit，compact 的 onTurnEnd 只在连续整理达上限时 pause |

**根因是同一个**：Socket 契约里没有"这一批工具调用"这个视角——模型这次发了哪些调用、已落了哪些结果、哪些被挂起、这是不是补跑。坑 1～3 都是它的表现；建议 9 做不成 Socket 也卡在这里。OnSet 现在在 runLoop 外按事件流自己维护一份，每个想要这类模式的宿主都得重来一遍。

## 方案对比

| | 做法 | 判断 |
| --- | --- | --- |
| A（选） | core `TurnContext` 加 `batch`（本批调用 / 已落结果 / 被挂起的 / 是否补跑，随落随更）；两个行为做成 brain 里两个 opt-in Socket | 补的是契约缺口，坑 1～3 一次消掉；runLoop 只多几行登记，不加行为分支；行为可拆、按需装 |
| B | OnSet 原提议：`LoopConfig.toolCallFailure: "continue" \| "skipRest"` + `Tool.endsTurn` | 否：runLoop 多两条行为分支（违背"几百行可整个复制"）；`endsTurn` 要"压过所有 Socket"，打破 onTurnEnd"第一个给意见的定"这条唯一规则；且没解决坑 1～3 |
| C | 只做 `batch` 字段，两个行为留给宿主 / README 配方 | 可行但浅：两个模式都通用，宿主各写一遍仍会踩补跑、审批续跑、排序的细节 |

**宪法核对**：`stopAfter` 是模型自己调某工具决定收尾，决策权在模型；`haltOnFailure` 是宿主给的边界（缺省不装），调用顺序仍由模型排——属"模型结构上做不对的事"：一次回复里，模型无法让后一个调用以前一个的结果为条件。两者都不改日志形状，被拦的调用照样有 isError 结果，历史完整。

## 具体设计

### 1. core：`TurnContext.batch`

字段名不用 `turn`：已有 `ctx.session.turn`（轮次数字）与 `ctx.budget.turns`，且补跑轮并没有模型请求。

```ts
/**
 * 本批工具调用的活动（2026-11-02）。同一个对象在本轮内持续变化（循环随落随更），不要拿快照比较；Socket 只读。
 * "一批" = 一段连续模型输出里的 tool_call，与 replay 切轮（isModelOutput）同口径
 */
export interface ToolBatch {
  /** 本批调用，按执行顺序。模型输出前为空；补跑时是遗留调用所在那批的全部 tool_call */
  readonly calls: readonly ToolCallEvent[]
  /** 本批已落日志的 tool_result（afterTool 替换后、真正落日志的那条），按落下顺序；补跑时预置上次已落的（含宿主经 input 回填的客户端工具结果） */
  readonly results: readonly ToolResultEvent[]
  /** 本批已处理但被挂起、没落结果的 toolCallId（等审批 / 等客户端回填 / 子代理暂停） */
  readonly held: readonly string[]
  /** 本批是续跑补齐上次遗留的调用（没有新的模型输出） */
  readonly resumed: boolean
}

export interface TurnContext {
  // …现有字段
  batch: ToolBatch
}
```

- 新增导出类型 `ToolResultEvent = CoreEventOf<"core.tool_result">`；同一提交把 `brain/src/compact/recall.ts` 与测试里的本地别名换成它。
- **必填**：宿主自己复制的旧 runLoop 靠类型报错发现（fail-closed）。手造完整 `TurnContext` 字面量的仓内只有 `perception.test.ts` 的 `fakeCtx`，一并补；changeset 点名"手造 TurnContext 的宿主要补 `batch`"。
- **登记**（runLoop `executeToolCalls`）：落日志后对 `type === "core.tool_result"` 的事件推进 `results`——审批被拒路径（`append`）与其余路径（`settle`）都包一层"落后登记"，**不改** flush 语义；`settle` 也被 `approval_request` 用，按类型过滤。审批、客户端工具、子代理暂停三处 push interruption 时同时登记 `held`。
- **正常轮**：模型输出后、`afterModel` 前写入 `calls`。
- **补跑轮**：`toolBatchOf(timeline, pending)` 纯函数定批——复用 core `isModelOutput` 切段，跳过模型不可见的运维事件（与 lowering-fetch IR"运维事件不打断 assistant 分组"同口径，防 TanStack 里 `budget_usage` 夹在同一次输出中间）；pending 跨多批时取第一批并 `warn` 一次（正常流程不出现，fork / 混用两种循环才可能）。runLoop 与 TanStack 共用，登记真源索引（与 replay 切轮同口径）。
- **TanStack 适配器**：`buildTurn` 时定 `calls` / `resumed`；`results` 在 `afterTool` 与 `toolPhaseComplete` 落结果时推进；`held` 留空——defer 让整批暂停，批准后的新 chat 重新跑 `beforeTools`，自然按序。其 `beforeTools` 边界对整批一次性跑 `beforeTool`，此时同批无结果，所以 `haltOnFailure` 在该路径**只看得见补跑预置的失败**——登记进「刻意不对称清单」。

### 2. brain：`haltOnFailure()`（建议 9）

```ts
export interface HaltOnFailureOptions {
  /** 哪些失败结果算数；缺省任何 isError */
  counts?: (result: ToolResultEvent) => boolean
  /** 哪些后续调用要拦；缺省全拦。例：只拦 risk !== "low" 的，让同批只读查询 / pin / recall 照跑 */
  applies?: (call: ToolCallEvent, tool: Tool | undefined) => boolean
  warn?: (message: string) => void
}
export function haltOnFailure(opts?: HaltOnFailureOptions): Socket
```

- `beforeTool(ctx, call, tool)`：**按 toolCallId** 在 `ctx.batch.calls` 定位（前面的 Socket 可能 rewrite 出新对象）；找不到则不表态并告警一次。看排在它前面的调用：
  - 有结果且 `counts` 为真 → block；
  - 在 `held` 里 → block（runLoop 上，前一个等审批就不该先发"已交"；代价是批准后模型要重发，真模型验证这一点）；
  - 否则无意见。
- 文案点名**最初那个**失败 / 挂起的调用（不是前一个被拦的）：`An earlier call in this batch (<name>, <id>) failed, so this call was not run. Handle that first, then call again if still needed.`；挂起版说 `is still waiting (approval / client)`。
- 被拦的调用走现有 block 路径：落 isError `tool_result`（toolCallId 一一对应），不执行、不计 `ctx.budget.toolCalls`；`budget_usage.payload.toolCalls` 仍按模型发出的条数记（本来就是"本轮模型发了几个"，不改）。
- 推荐注册在最前（block 短路，后面的 Socket 看不到被拦调用）；不在最前也正确，只是前面的 Socket 先看到。
- `ctx.batch` 为 undefined（宿主装出了两份 core，旧循环不填）→ 抛 `haltOnFailure requires a loop that fills TurnContext.batch (@reinsjs/core >= 0.8.0)`。
- 不给模型加规则提示：拦下时的结果文案自带解释，也不动缓存前缀。

### 3. brain：`stopAfter()`（建议 10）

```ts
export interface StopAfterOptions {
  /** 调成功即收尾的工具名 */
  tools: readonly string[]
  warn?: (message: string) => void
}
export function stopAfter(opts: StopAfterOptions): Socket
```

- `onTurnEnd(ctx)` 返回 `"stop"` 的条件全部成立：
  1. `ctx.batch.results` 里有名单工具的成功结果（以落日志的那条为准）；
  2. 同批没有 isError 结果、`held` 为空、`calls` 每条都有结果；
  3. 补跑轮额外要求：本批之后时间线上**没有新的 `core.user_message`**（坑 3 的真判据是"别让遗留收尾吞掉新输入"，不是"补跑一律不算"——`[action 需审批, end_run]` 批准续跑、无新输入时照样收尾，与 handoff 的 R2 从日志重建意图同理）。补跑时 `ctx.timeline` 已含本次 run 起步追加的输入，Socket 自己扫。
  否则无意见。
- 同批有失败：让模型下一轮看到再决定（宪法一）。`haltOnFailure` 把 `end_run` 拦下时它就是 isError、不停——这正是想要的组合，写成 README 配方。
- **注册顺序：handoff → stopAfter → compact / budget**。排在 handoff 前会让 `[handoff, end_run]` 吞掉交接：模型已收到 "Handoff scheduled"，框架却不兑现，下次 run 也重建不回来。budget 本就要求排在 handoff 之后，两者一致。
- 与 compact 的交互（写进 README）：模型在被请整理的那轮直接收尾，run 以 done 结束，那一级请求按"每段每级一次"已用掉，下一个 run 不再请——可接受，阈值兜底仍在。
- 构造期校验 `tools` 非空、元素为非空字符串（`X must be …, got …`）；`beforeModel` 对照 `ctx.tools`（不用 `SocketSetup.tools`，后者看不到注册在后面的 Socket 贡献）发现名单工具不在表里，按 brain 惯例告警一次。
- `ctx.batch` 缺失同 `haltOnFailure` 抛错。
- `fork_done` / `end_run` 的"把 note 当最后发言"留在宿主工具里，本模块只管停。

### 4. 不动的部分

- budget 的 `afterModel` + WeakMap、compact 的 `hadToolCall`：与读 `ctx.batch` 等价，不顺手改写法。
- 并发执行（OPT-260921-1）维持不做；在该条补一句"`haltOnFailure` 依赖串行顺序，是并发的约束之一"。

### 刻意不做

- `Tool.endsTurn` / `LoopConfig.toolCallFailure`（方案 B）。
- 让模型在一次回复里声明调用间依赖（无厂商协议支撑）。
- 给 `beforeTool` 加"挂起等前一个"的新决定（要动 core 语义；拦下已比现状的"抢先执行"好）。

## 验证矩阵

| 用例 | 判据 |
| --- | --- |
| core：六种结果路径（拒绝、block、未知工具、入参不合法、执行成功 / isError、执行抛错） | 落日志后 `batch.results` 都含它，顺序与日志一致 |
| core：审批请求经 `settle` 落日志 | 不进 `results`，进 `held`；客户端工具、子代理暂停同样进 `held` |
| core：beforeTool 处理第 k 个 | `results` 只含前 k-1 个已落的 |
| core：正常轮 / 补跑轮 | 正常轮 `calls` = 本批全部、`resumed: false`；补跑轮 `resumed: true`、`calls` = 原批全部、`results` 含上次已落与 input 回填的 |
| core：批中途中止 | 正常路径 `endTurn` 看到缺结果的批；下一轮开头暂停 |
| `toolBatchOf` | 同批连续定位；运维事件夹在输出中间不切段；多批历史只取遗留那批；pending 跨批取第一批并告警 |
| TanStack：`[A, B, C]` 全正常 + 装 `haltOnFailure` | 三个都执行（回归锁） |
| TanStack：`[X 需审批, A]` | 批准后 A 按序执行 |

| haltOnFailure：`[F, A, B]` | A、B 各一条 isError、未执行、`ctx.budget.toolCalls` 不计；B 的文案点名 F |
| haltOnFailure：`[成功, A]`、单个调用 | 不拦 |
| haltOnFailure：`[X 需审批, A]`（runLoop） | A 被拦（still waiting）；批准续跑后 X 执行，A 不再执行 |

| haltOnFailure：排在 rewrite 的 Socket 之后；不在首位且前面 Socket 先 defer | 按 toolCallId 定位正确；defer 照常 |
| haltOnFailure：`counts` / `applies` | 排除的失败不触发；`applies` 为假的后续调用照跑 |
| haltOnFailure / stopAfter：`ctx.batch` 缺失 | 抛可读错误 |
| stopAfter：`[动作, end_run]` 都成功 | done；先于 budget 的意见 |
| stopAfter：`[失败动作, end_run]` / end_run 自身 isError / 被 haltOnFailure 拦 | 不停 |
| stopAfter：`[action 需审批, end_run]` 批准续跑、无新输入 | done |
| stopAfter：遗留 `end_run` + 新 user_message 续跑 | 补跑轮不停，新输入照常被处理 |
| stopAfter：`[handoff, end_run]` 同批、推荐顺序 | handoff |
| stopAfter：名单工具不在工具表 | 告警一次 |
| README 配方：`haltOnFailure` + `stopAfter` 组合 | `*.recipe.test.ts` 逐字一致 |
| **真模型（DeepSeek 直连，从决策现场单次请求，各并发 5 次）** | ① `board_update` 失败 + `chat_send` 被拦：看模型是否先修前一个再重发；② `[X 已批准执行, A 以 still waiting 被拦]`：看模型是否重发 A。合计 < ¥1，跑前报数 |
