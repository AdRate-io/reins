# HTTP 进行中投递（AdRate 建议 6）

> 状态：📋 待实施

## 背景与根因

AdRate 建议 6（`docs/archive/2026-11-05-AdRate给reins的优化建议.md` 第三批）：浏览器宿主的消息都从 HTTP 进来，会话的 run 正在跑时再 `POST { sessionId, input }`，handler 在 `runs.create` 撞 `RunConflictError`，回 409 `run_in_progress`。用户想在 run 进行中补一句话（"只看 A 账户""预算别超过 100"），只能等 run 结束（模型可能已在错的方向上多走几轮、发出待审批的写调用），或者先停止再发（排队的只读查询一起作废，模型要重新规划）。

core 0.11 的 `pullInput` 已解决"什么时候交给模型"：每次调模型前拉、有 pending 不拉、中止后不写。缺的是 HTTP 一侧"消息怎么送到正在跑的 run"：

- `createAgentHandler` 用 `withoutPerRunFields` 剥掉定义里的 `pullInput`（`packages/server/src/handler.ts:705`），起 run 时也不传（`handler.ts:612`），`HandlerOptions` 没有别的入口。
- 宿主要用，只能绕开 handler 自己起 run，补发与实时流拼接、心跳、编码器、增量、`onEvent`、续跑校验全部重写一遍——正是建议 3 当时要避免的两份实现。

**更正**：`pullInput` 方案把此事记为 OPT-261106-3「维持不做」，理由"HTTP 宿主可在自己的 `pullInput` 背后接队列"不成立（上面两点）。本方案取代那条记录。

## 方案对比

| | 做法 | 判断 |
| --- | --- | --- |
| A（选） | handler 为每个 POST run 开一个**内存信箱**，`pullInput` 从信箱取；进行中的 POST 入信箱回 202 | 复用 handler 的流、观测、鉴权、登记表；reins 只多一份与 run 同生同灭的内存状态 |
| B | `HandlerOptions.pullInput(ctx)` 让宿主自供回调 | 否：宿主仍要自己做"跨请求定位 run"与进行中 POST 的接收（handler 还是回 409），等于只挪了一半 |
| C | 持久化信箱（存储新表） | 否：送达判据放在时间线上就够（见下），进程死只丢未送达的，客户端可见、用户重发一次；不值一张表 |

与 AdRate 建议形态相比，**保留**：每 run 一个内存信箱、仅普通 POST run 有信箱（停止收尾 run、asTool 子 run 没有）、202 JSON 不开流、只收用户消息、`resume` / `decisions` / `tool_result` 打在忙碌会话上仍 409、跨实例仍 409、不持久化、不自动起下一个 run、不改预算、handler 选项开启缺省 409、草稿带 `provenance.ref = deliveryId`。**改了三处、补两处**：

1. **取出不删，写进日志才删**（建议原文未明说何时出箱）。core 规则是"宿主看到写入事件再认领"，拉完发现已中止则不写；取出即删会让被停止那一刻的消息凭空消失。
2. **result 帧不带未投递列表**，送达判据只有一条：时间线里出现带该 `deliveryId` 的 `core.user_message`。进程死、连接断时客户端本来就只能靠这条，再加一份列表是两套判据，还要改 `RunResult` 与 AG-UI 收尾帧形状。日志是唯一真源（宪法二）。
3. **鉴权沿用 `method: "POST"`**，不新增 `"INPUT"`。STOP 单列是为了让"只认 POST 的旧宿主"缺省拒掉停止；这次已有 opt-in 开关表达宿主同意，再单列等于两个开关管一件事；且"往会话补一句"与"往会话发消息"是同一种权限。**前提是补一道发起人校验**（下一条）。
4. **补：投递者必须是 run 的发起人**（审查第 1 条）。run 的 principal 在起步时定死（`handler.ts:619`），工具拿到的是它。若会话里另一个已授权的主事人 B 能往 A 的 run 里投递，B 的话会以 A 的身份被执行、审计也记在 A 头上——今天 B 只能以自己身份另起 run。所以投递时比 `principal?.id`（匿名即 undefined，两边都匿名算同一人），不同就落回原路径 409。
5. **补：ui-agui 在 `core.user_message` 上带出 `provenance`**。`createAgent` 缺省 AG-UI 编码，而 `metadata.reins` 现在只有 `seq` / `eventId` / `type`（`packages/ui-agui/src/map-event.ts:82`），缺省编码下客户端拿不到 `deliveryId`，功能不可用。只给 user_message 带，不扩到全部事件：所有 `tool_result` 与 brain 写的事件都带 provenance，全量带出会改变线上每条 `TOOL_CALL_RESULT` 的形状（审查第 4 条）。

## 具体设计

### 公开接口

```ts
// server HandlerOptions
/**
 * run 进行中到达的用户消息交给正在跑的 run（AdRate 建议 6）。缺省 false：进行中再 POST 回 409 `run_in_progress`（现状）。
 * 开启后，会话的 run 正在**本进程**跑、由普通 POST 起、且投递者与发起人是同一主事人时，只带用户消息的 POST 入这个 run 的信箱、
 * 回 202 `QueuedResponse`；run 在下一次调模型前把它写进时间线（core `pullInput` 语义），
 * 草稿带 `provenance: { source: USER_DELIVERY_SOURCE, ref: deliveryId }`。
 * 送达判据：时间线里出现这条消息。流结束时仍没出现即未送达，信箱随 run 丢弃。
 */
midRunInput?: boolean

// server AgentRequestBody 新增
/**
 * 这条用户消息的投递 id（可选，幂等键）。只能与用户消息形态的 input 同用（字符串 / 内容片段 / user_message 草稿），
 * 与 tool_result 草稿、stop 同用回 400；规则同 sessionId（可打印 ASCII 无空格）且不超过 128 字符。
 * 给了就原样作为 provenance.ref，**普通路径起 run 时也带**——客户端对每条消息只用一种判据；没给由服务端生成（uuidv7）。
 */
deliveryId?: string

// server 请求应答
export interface QueuedResponse {
  status: "queued"
  sessionId: string
  deliveryId: string
}

/** 带 deliveryId 的用户消息的 provenance.source */
export const USER_DELIVERY_SOURCE = "reins.delivery"

// ui-agui ReinsMetadata 新增可选字段（只在 core.user_message 的 TEXT_MESSAGE_START 上出现）
provenance?: { source: string; ref?: string }
```

- **`deliveryId` 允许客户端给**（审查第 2 条，推翻初稿的"只由服务端生成"）：202 在网络上丢了时客户端会重试，没有客户端侧的 id 就无法去重，靠内容对账不可靠；客户端也能在发出前就开始对账，"事件先于 202 到达"不再需要缓冲。风险面：ref 只进 provenance，模型看不到（降级层只对 untrusted 事件读 `provenance.source` 做标注，`core/src/lowering/trust.ts:33`，user_message 是 user 信任不走那条），不进 configHash；同一客户端写自己会话里的一个标签，不跨主事人。
- 选项名沿用 AdRate 提的 `midRunInput`。`createAgent` 的 `handler` 选项透传 `HandlerOptions`，agent 不改代码。

### 用户消息重建（一份）

`checkInput` 里的 `user_message` 重建（`handler.ts:214-226`）抽成 `userMessageDraft(input, deliveryId?)`：字符串 / 已重建的片段 / `user_message` 草稿 → `{ type: "core.user_message", actor: "user", payload: { content }, provenance? }`，壳字段一律服务端定；内容不合规返回 400。普通路径与投递分支都调它（审查第 7 条）。内容不合规时**先 400**，不落回原路径——与今天"先 400 后 409"的顺序一致。

普通路径带 `deliveryId` 时，起步 input 改为这份草稿（多一个 provenance）；不带时 input 原样不动，日志与现状逐字相同。

### 投递分支（`handlePost`）

位置：`parseBody` 与 `denyBySessionAuthz`（`method: "POST"`、`isNew: false`）之后，现有续跑预校验之前。条件全部满足才进入：

- `midRunInput === true`；
- `body.sessionId` 给了，`body.input` 给了，`body.resume` / `body.decisions`（含空数组）都没给；
- `input` 是用户消息形态，且 `userMessageDraft` 重建成功（失败直接 400）；
- `runs.get(sessionId)` 有 run，handler 为它开过信箱、信箱未关闭；
- `run.controller.signal` 未中止；
- 投递者 `principal?.id` 等于信箱记下的发起人 id。

任一不满足就**落回现有路径**，行为与今天相同：信箱已关（run 刚结束）→ `runs.create` 成功、按普通 POST 起新 run（SSE 200）；`tool_result` 草稿、带 resume / decisions → 照旧校验或 409；run 已中止（停止中、丢租约、`onDisconnect: "abort"` 后）→ 409（它不会再拉取，收下就是必丢）；别的实例的 run → 租约登记表 409；停止收尾 run 没有信箱 → 409；发起人不同 → 409；别的 handler 起的 run（共用 `runs`）没有本 handler 的信箱 → 409。

进入后：

1. `deliveryId` 已在本信箱见过（未写入或已写入）→ 回 202、不再入箱（幂等）。
2. 未写入条数已达上限 16 → 429 `mailbox_full`，不收。理由：一个已授权客户端在长工具批期间可无限塞带图片的消息，内存无界；上限远高于真人打字速度。条数之外的单条体积由宿主在网关限请求体（这个缺口今天就有，README 提醒）。写入一条就腾出一格。
3. 入箱 `{ deliveryId, draft }`，回 202 `QueuedResponse`（JSON，不开流）。`lastSeq` 在这条路上无意义，接受并忽略（客户端可统一带）。

**原子性**（审查第 6 条）：从 `runs.get` 到入箱之间**不得有任何 await**——鉴权、JSON 解析、草稿重建都在 `runs.get` 之前完成，`uuidv7` 与 Map 操作都是同步的。否则 run 可能在空隙里结束，消息入一个已关的箱。用例锁住"run 结束同一刻的投递要么 202 且被拉到、要么落回普通路径"。

### 信箱与 run 的绑定

- 信箱是 handler 内部状态：`WeakMap<ActiveRun, Mailbox>`，**不加到 `ActiveRun` 公开形状上**。`ActiveRun` 是公开导出、宿主自定义 `RunRegistry` 也会构造它；信箱只对"由这个 handler 驱动的 run"有意义。
- `Mailbox` 记：发起人 `principal?.id`、未写入草稿（到达顺序）、本 run 见过的 deliveryId 集合、是否已关。
- 开箱：`midRunInput` 开启时，普通路径在 `await runs.create` 返回后同步开箱。登记表登记与开箱之间隔着 await（租约登记表多一层），这个空隙里到达的投递会 409——安全、可接受，README 不承诺"run 一登记就收"，用例锁住（审查第 5 条）。补发期间、`begin` 之前到达的消息在第 1 轮拉到，排在起步 input 之后（起步 input 在进循环前写入，`run-loop.ts:433`）。`handleStop` 起的收尾 run 不开。
- 关箱：`run.onFinish` 里关闭并丢弃。`finish` 同步跑收尾钩子、同步删登记表项（`runs.ts:154-172`），关箱后的 POST 一定落回普通路径。
- `pullInput: () => mailbox.snapshot()`：返回当前全部未写入草稿的副本，**不删**。
- **认领**：在 `drive` 外包一层生成器（与 `observed` 同一手法）：每 yield 一条 `core.user_message` 且 `provenance.source === USER_DELIVERY_SOURCE`，按 `ref` 从未写入表删除。core 在 append 后紧接着逐条 yield 写入的事件、中间不查中止（`run-loop.ts:494-495`），`ActiveRun.drive` 广播后才调下一次 `next()`（`runs.ts:136-143`），所以一批写入必然全部认领、下一次拉取一定在认领之后。
- 拉完已中止 → core 不写 → 不认领 → run 结束关箱 → 未送达。符合判据，无需特判。

### 客户端约定（写进 server README 并配方化）

每条要发的消息先生成 `deliveryId`，**任何时候**都带着它与 `lastSeq` POST（审查第 3 条），按应答分四种：

| 应答 | 含义 | 客户端做什么 |
| --- | --- | --- |
| 202 `queued` | 入了当前 run 的信箱 | 在挂着这个 run 的流里等这条消息；流以 result / error 结束仍没见到 → 未送达。若收到 202 时流**已经结束**，立即判未送达 |
| SSE 200 | run 恰好刚结束，这条消息起了新 run | 按普通 POST 接流；消息就是新 run 的起步 input（带同一 provenance） |
| 409 `run_in_progress` | 停止中 / 别的实例 / 别的发起人 / 开箱前的空隙 | 稍后重发，或提示用户 |
| 429 `mailbox_full` | 信箱满 | 稍后重发 |

- 投递方必须有一条挂着这个 run 的流（发起 POST 的流，或 `GET ?sessionId&lastSeq` 重连）。
- 202 丢失后的重试带同一个 `deliveryId`：同一 run 内幂等；run 已结束则先在已收到的事件里查这个 ref，见到就是已送达、别再发。
- **判未送达前若流是以 error 帧结束**（如写入撞 `seq_conflict`、存储提交超时），写入是否落库不确定：先 `GET` 补发核一次有没有这个 ref，再决定放回输入框（审查第 9 条）。
- 未送达的典型情况：最后一次拉取之后才到；run 以 paused（审批 / 预算 / 停止 / 触顶 `maxTurns`）或 error 结束；拉完发现已中止；run 以 **handoff** 结束（会话换了，要发去 `toSessionId`）；续跑起步的补跑轮不拉，若补跑后模型即收尾也来不及。
- run 停在等审批时，未送达的那句按建议 1 口径与 `decisions` 拒绝一起重发——只有宿主知道怎么拼，handler 不自动起 run。
- 吸收中途消息的 run 更长，`maxTurns` 与预算更早触顶，宿主照实调。

### 对现有模块的影响（核过）

- **core**：不改。拉取点、白名单（`PULLED_DRAFT_TYPES` 含 user_message、不含 tool_result）、中止不写、回调抛错语义沿用。handler 的回调不抛、只回合规草稿。
- **onEvent**：拉进来的 `user_message` 是 live 事件，照常观测；`EventObserverInput.principal` / `request` 仍是发起 run 的那个 POST（投递者与发起人已保证同一主事人；投递请求的 header 不进观测上下文，README 写明）。
- **`SessionAuthzInput.method` 注释**补一句："开 `midRunInput` 时 POST 也可能是对进行中 run 的投递（不起新 run），按 POST 计 run 配额的宿主会把投递算进去"（审查第 11 条）。
- **AG-UI**：`core.user_message` 已映射成 `TEXT_MESSAGE_*`（role user），`encoder.ts:140` 遇 user_message 清 `parentMessageId`，中途出现无额外假设。provenance 只经 `mapEvent` 的 user_message 分支带出；`encoder.ts:146` 的 `metaOf`（CUSTOM 帧）不经 `reinsMetadata`，不受影响。
- **compact**：一个 run 多条 user_message 时只原样保最后一条（OPT-261106-4），本功能会让它更常见；不改，OPT 补重启条件"HTTP 进行中投递上线后，宿主样本里出现起步任务被整理后丢失"。
- **handoff**：`triggerMessage` 取最后一条可见 user_message，中途附言会成为交接触发语（`pullInput` 方案已登记，不新增）。

## 验证矩阵（假模型，不花钱）

机制全部用 `ScriptedLowering` + 一个靠闸门挂住的测试工具（让 run 停在工具批里，测试控制何时放行）。模型怎么对待中途消息已在 `pullInput` 方案用 OnSet 真样本验过，本方案只改送达通路，不跑真模型。

| 用例 | 判据 |
| --- | --- |
| 缺省（未开 `midRunInput`）进行中 POST | 409 `run_in_progress`，与现状逐字一致（回归） |
| 未开、不带 `deliveryId` 的普通 run | 日志与请求与改动前逐字相同 |
| 普通路径带 `deliveryId` | 起步 user_message 带 provenance，其余不变 |
| 开启、工具批中 POST 字符串 | 202；放行后该消息排在 tool_result 之后、下一次模型请求里可见；provenance = `{ source: USER_DELIVERY_SOURCE, ref }`；发起流与 GET 观看者都收到 |
| 不带 `deliveryId` | 服务端生成、202 里回出、与事件 ref 一致 |
| 内容片段数组 / `user_message` 草稿（客户端带伪造 actor、trust、provenance） | 重建后写入，壳字段为服务端值 |
| 不合规的 `user_message` 草稿打在忙碌会话上 | 400，信箱无变化 |
| `deliveryId` 不合规 / 与 tool_result 草稿或 stop 同用 | 400 |
| 同一 `deliveryId` 投两次（入箱前后各一次、写入后再一次） | 都回 202，日志里该 ref 恰一次 |
| 同一空档连发三条 | 一批写入、连续 seq、到达顺序 |
| 认领 | 后续拉取不再出现已写入的消息 |
| `begin` 之前（补发期间）到达 | 第 1 轮拉到，排在起步 input 之后 |
| `runs.create` 登记后、开箱前的空隙 | 409（锁现状） |
| run 结束同一刻的投递 | 要么 202 且被拉到，要么落回普通路径起新 run；不出现"202 却入了已关的箱" |
| 最后一次拉取之后到达、模型随即收尾 | 202；流以 result 结束、日志无此 ref；之后同会话 POST 起新 run（SSE 200） |
| run 暂停在审批 / 触顶 `maxTurns` / 以 handoff 结束 | 信箱里的消息不写 |
| 停止请求之后、run 结束之前 POST | 409 |
| 拉取期间被停止 | 用注入的 `pullInput` 包装在快照返回前触发 abort：不写、run 停止收尾、日志无此 ref |
| `onDisconnect: "abort"` 发起方断开后投递 | 409 |
| 停止收尾 run 进行中 POST | 409（无信箱） |
| 两个 handler 共用 `runs`，打到另一个 handler 起的 run | 409 |
| 投递者 principal 与发起人不同（含一方匿名） | 409，信箱无变化；两边都匿名 → 202 |
| 忙碌会话上带 `resume` / `decisions` / `decisions: []` / `tool_result` 草稿 | 与现状相同（409 或原有校验错误） |
| 没带 `sessionId` | 走新会话路径 |
| `authorizeSession` | 收到 `method: "POST"`、`isNew: false`；拒绝回 404、信箱无变化 |
| 信箱满 | 第 17 条 429；写入一批后再投递恢复 202 |
| 拉进来的写入撞 `seq_conflict`（存储注入） | 流以 error 帧结束；客户端约定的 GET 核对路径可走通 |
| 租约登记表：本进程的 run → 202；别的实例持租约 → 409 | |
| `onEvent` | 观测到拉进来的 user_message 恰一次 |
| `createAgent({ handler: { midRunInput: true } })` | 透传生效 |
| ui-agui | user_message 带 provenance 时 `TEXT_MESSAGE_START.metadata.reins.provenance` 原样带出；tool_result 等其余事件输出逐字不变（用带 provenance 的 tool_result 样例锁住） |
| README 配方 | 客户端四种应答的处理片段进 `*.recipe.test.ts`，逐字一致 |

## 刻意不做

- **跨实例投递**：会话的 run 在别的实例上照常 409；与跨实例停止（OPT-261105-5）同一类，一起排。
- **result 帧带未投递列表 / 自动起下一个 run**：理由见方案对比第 2 处与客户端约定。
- **持久化信箱**：见方案对比 C。
- **新消息重置或延长 run 预算**：预算是宿主的边界，宿主照实调。
- **单列 `method: "INPUT"`**：见方案对比第 3 处。
- **跨 run 的 `deliveryId` 去重**：只在同一 run 内幂等；跨 run 靠客户端先查时间线里的 ref。服务端跨 run 去重要扫日志或另存索引，不值。
- **TanStack 适配器**：它不走 handler。
