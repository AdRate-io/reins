# 图片引用并发读取，HTTP 预校验只读元信息（AdRate 建议 18）

> 状态：✅ 已完成（2026-11-24）（实施前经独立审查修订一版，修订要点见文末）

## 背景与根因

AdRate 建议 18（`docs/archive/2026-11-05-AdRate给reins的优化建议.md` 末节）。core 0.16.0 的图片引用形态在读取上有三处是串行或多读的（已逐行核对源码）：

1. **换回逐张串行**：`hydrateImageRefs` 对视野内每个没进缓存的引用逐个 `await blobs.get`（`core/src/loop/media-refs.ts` `loadImage`）。
2. **写入校验逐张串行、读整份字节**：`checkImageRefs` 逐个 `await blobs.get`，判定只用 `meta`（归属、mime）。
3. **同一张新图读两遍**：server 预校验（`rejectImageRefs`，每次新建 `cache: new Map()`）与 runLoop 起步校验（run 级 `imageCache`）各读一次整份字节；换回复用后者的缓存。

一条带 N 张新图的 HTTP 消息，起跑前串行读 2N 次整份字节，视野内的旧图再串行读一遍。方案 `2026-11-24-媒体引用形态.md` 当时把第 3 点记为"不加 `BlobStore.stat`，多读一次可接受，有量再加"。

**样本**：AdRate 生产机（欧洲）读 Cloudflare R2，10 个 250～460KB 对象：串行冷连接 7.7s、串行热连接 4.3s、10 张并发 0.38s；单流约 1MB/s，并发几乎不叠加延迟。AdRate 每条消息上限 10 张，按现状首字前多等 10 秒以上；之后每条消息，视野内的图每张再多 0.4～0.8 秒。凡是 `BlobStore` 背后是对象存储或网络存储的宿主都会碰上。

## 方案选择

| | 做法 | 判断 |
| --- | --- | --- |
| A（选） | 读取并发（固定上限）+ `BlobStore` 加可选 `stat?(id)`，**只给 server 预校验用**；循环内的写入校验照旧 `get`、字节进 run 缓存供换回 | 每张新图只读一次字节；写进日志前的最终裁决与发给厂商的字节出自同一次 `get`；缓存形状不变 |
| A′ | 循环内写入校验也优先 `stat` | 否（审查第 1 条）：新图马上要换回，`stat` 一波再 `get` 一波反而多一次往返；且判定依据（宿主登记表）与发出的字节（对象存储）不是同一份，登记表写错时校验放行、厂商每轮 400、会话卡死（踩坑 54 同类） |
| B | 只做并发 | 否：HTTP 消息的新图仍读两遍整份字节 |
| C | handler 预校验读到的字节传进 run 的缓存 | 否：要给 `LoopConfig` 加跨层公开字段；预校验改读元信息后收益近零 |
| D | reins 做跨 run 的字节缓存 | 否：生命周期与内存上限是宿主的事；字节不可变，宿主在自己的 `BlobStore` 里缓存是安全的 |

## 公开形状

```ts
// ---- core store/types.ts ----
export interface BlobStore {
  put(...): Promise<{ id: string }>
  get(id: string): Promise<{ bytes: Uint8Array; meta: BlobMeta }>
  slice?(...): Promise<Uint8Array>
  /**
   * 可选：只取元信息、不读字节。不存在必须抛 StoreError("not_found")（不能返回 null），与 get 同一语义；
   * 返回值必须与 get(id).meta 一致。目前只有 server 的 HTTP 预校验用它（最终裁决仍由循环按 get 做）
   */
  stat?(id: string): Promise<BlobMeta>
}

// ---- core loop/media-refs.ts ----
export interface CheckImageRefsContext {
  // ……现有字段不变
  /** 只判归属与 mime、不留字节：有 stat 用 stat，否则退回 get。server 预校验用；循环内不传 */
  metaOnly?: boolean
}
```

`ImageRefCache` 形状不变（`Map<string, { data: string; meta: BlobMeta }>`）。`checkImageRefs` / `hydrateImageRefs` 签名与错误语义不变。

## 规则

### 并发读取（内部一个工具，两处共用）
- **上限固定 16，不开配置**：AdRate 一条消息最多 10 张，16 一波读完还有余量；同时防止长会话视野里几十张图一次全打出去。超过后端能力的部分由后端排队（pg 连接池缺省 10、postgres.js 的 `max`、Workers 同时 6 个连接都只是排队，不死锁；审查已核）。要更低上限的宿主在自己的 `BlobStore` 里限流。有真实样本再开配置。
- **池而不是分批**：一个读完立刻补下一个。
- **去重**：同一 blobId 在一次调用里只读一次。
- **等全部落定**（allSettled），返回 `Map<blobId, 落定结果>`，调用方只消费这张表，不再为同一 id 二次读取。
- **fail-closed 的返回值检查**：`get` / `stat` 返回的不是对象（宿主照 R2 `head()` 写成返回 `null`）一律当 `not_found`。否则 `meta.sessionId` 抛 TypeError 被当存储故障，HTTP 对"存在但不归我"回 400、对"不存在"回 503，客户端就能分辨别的会话的 blob 是否存在（审查第 2 条）。
- **实现要点**：按方法调用（`blobs.stat(id)`，SQLite / PG 实现靠 `this`）；每次读取包一层 `Promise.resolve().then(() => …)`，宿主同步抛错也变成一个落定的失败，不冲出池子。

### 写入校验（`checkImageRefs`）
- 先收齐本批片段里未缓存的去重 blobId，并发读完，再**按片段顺序逐个判、报第一个问题**：读取 `not_found` → 返回统一那句；读取抛其它错误 → 原样抛出；读到了 → 先归属后 mime，不过返回统一那句。与完成先后无关；全部合规时结局与串行逐个判完全一致。
- 循环内（不传 `metaOnly`）：照旧 `get`，读到的 `{ data, meta }` 进 run 缓存，换回直接用。缓存命中照判归属与 mime（踩坑 54 规则不变）。
- server 预校验（`metaOnly: true`）：有 `stat` 用 `stat`，否则 `get`；不往缓存里放（那份缓存用完即弃）。stat 与 get 不一致时，预校验放行的引用会在循环那道（按 get）被拒，结局从 400 变成 200 + error 帧——判定以字节那份为准，不会写进日志。
- 循环三入口合批：起步 input 把全部草稿的片段按原顺序合成一批、`pullInput` 同理（不再逐条草稿串行）；工具结果先对整条结果的引用一次并发预读，再逐段用落定表判定（逐段替换、存储错误归因与现状一致）。

### 换回（`hydrateImageRefs`）
- 先收齐视野内未缓存的去重 blobId，并发 `get`，读完按原顺序换回。
- `not_found` 与没配 BlobStore 照旧留引用、不进缓存；其它错误按视野顺序抛第一个（在 `toRequest` 那个 try 里，走模型调用失败与重试判定，不变）。成功的照样进缓存，重试只重读失败的。

### 存储实现
- 内存 / SQLite / PG 三份实现 `stat`：SELECT 不取 `bytes` 列，与 `get` 共用同一个行转换（`metaOf`），口径不会分叉。
- 一致性套件加一条："实现了 `stat` 的：与 `get(id).meta` 逐字段相等；未知 id 抛 `not_found`（不返回 null）"。已在内存、SQLite、PG（PGlite 与设了 `REINS_PG_URL` 时的五个真库后端）上跑。

### 行为变化（写进 changeset 与回复）
- 同一条工具结果里同一张图出现两次、读取瞬断：现状第二段会自己再读一次、可能成功；去重后两段都回 "storage error"。
- 视野里同一张不存在的图出现多次：现状每次出现读一次，去重后只读一次。
- 第一个问题之后的引用也会被读（并发），失败场景下的读取次数比串行多；全部合规时次数不变。

### 其它
- **不碰 `fetch_blob`**：它要的就是字节；没有样本。
- **中止**：`BlobStore` 方法不收 signal，并发不改变这一点；一波读取最长一次对象存储往返。
- **回滚**：不改事件与版本号，新旧版本混跑安全；宿主不实现 `stat` 时只差"并发"。

## 不做

- 并发上限配置项、跨 run 缓存、handler 与 run 共用缓存、循环内用 `stat`（见方案选择）。
- `BlobStore` 方法加 `signal`；`fetch_blob` 改用 `stat`。

## 验证矩阵

全部假模型与假存储，**不花真钱**。并发效果用带延迟的计数存储测（每次 get / stat 延迟 D 毫秒、记录在途峰值），判据是"耗时 < 2D"与"在途峰值"，不是墙钟绝对值。

| 项 | 断言 |
| --- | --- |
| 换回并发 | 视野内 10 张未缓存的图：总耗时 < 2D；40 张：在途峰值 = 16；换回后与内联写法逐字节相等（现有等价用例保留） |
| 去重 | 视野内同一 blob 出现三次、一条消息引用同一 blob 两次、视野里同一张不存在的图出现两次：各只读一次 |
| 读取次数 | HTTP 发 N 张新图、存储有 `stat`：handler `stat` N 次、循环 `get` N 次、换回 0 次；无 `stat`：`get` 2N 次（与 0.16.0 相同，只是并发）；进程内 `agent.run()`：`get` N 次、`stat` 0 次 |
| 校验顺序 | 第 3 段 `not_found`、第 1 段存储抛错且后完成：抛第 1 段的错；第 1 段越权、第 2 段 `not_found`：报第 1 段那句 |
| 返回 null | `stat` / `get` 对不存在的 id 返回 null：HTTP 回 400 统一那句，不是 503；与"别的会话的 blob"同一应答 |
| stat 与 get 不一致 | `stat` 报 image/png、`get` 报 image/jpeg：预校验放行、循环按 get 拒绝，日志里没有这条引用 |
| 换回错误 | 两张同时失败、后面那张先失败：抛视野里靠前那张的错；成功的进缓存，重试只重读失败的；一张 `not_found` 一张成功：前者占位、后者换回 |
| 合批入口 | 起步 input 三条草稿各带图、`pullInput` 拉到两条带图：读取在一波内并发完成，文案与结局与串行一致 |
| 工具结果 | 一条结果三个引用：并发预读；逐段替换与存储错误归因与现状一致；同一张图出现两次且瞬断：两段都回 storage error、只读一次 |
| 一致性套件 | 内存 / SQLite / PG `stat` 与 `get().meta` 相等、未知 id 抛 `not_found` |
| 统一文案 | 四入口文案逐字不变、缓存命中仍比 mime（现有用例保留） |
| 门禁 | 改完先 `pnpm build` 再 `pnpm check`（踩坑 55） |

## 修订要点（2026-11-24 独立审查后）

初版让循环内的写入校验也优先 `stat`、缓存改成"元信息必有、字节可选"。审查指出：新图马上要换回，循环内用 `stat` 反而多一次往返；且判定依据与发出的字节不是同一份，宿主登记表写错时会卡死会话。改为 `stat` 只给 server 预校验（`metaOnly`），缓存形状不变。另采纳：`stat` / `get` 返回非对象当 `not_found`（防探测）；工具结果预读后只消费落定表；验证矩阵区分全部合规与失败场景、补 null 返回与 stat/get 不一致两格；改动清单补 changeset、server、README、真源索引、`REINS_VERSION`；实现要点（按方法调用、同步抛错兜底）。审查同时发现 `examples/minimal/replay.ts` 在 v0.20.0 有一处类型错误，已单独修复（踩坑 55、OPT-261124-1）。
