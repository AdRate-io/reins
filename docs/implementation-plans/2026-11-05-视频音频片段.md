# 视频 / 音频内容片段（OnSet 建议 12）

> 状态：📋 待实施

## 背景与根因

OnSet 建议 12（`docs/archive/2026-10-30-OnSet反馈-compact与perception改进建议.md` 末节）：要让 Gemini 主脑（公司中转站 `gemini-3.8-flash-high`）直接看片子，而不是把视频交给看片助手、只拿回文字结论。导演看节奏、剪辑看切点，转述一道就会失真。

OnSet 已在中转站实测：Chat / Responses / Messages 三条线都能收视频，放法分别是 `image_url` 的 data URI、`input_image`、`image` 块（填视频 mime）。视频按约 95 token/秒计（Gemini 低分辨率档）。前置的签名问题已核实（`spikes/gemini-relay-signature/`，三线两遍 6/6），不用补签名回放。

现状只有 `text` / `image` / `tool_reference` 三种片段，能力位只有 `images`。宿主把 `video/mp4` 塞进 `ImagePart` 能跑，但有三个问题：

1. **估算失真**：每张图固定按 1600 token 估，72 秒视频实际 6.8k，整理与兜底的时机跟着失准。
2. **能力位误放行**：`images: true` 的模型不一定收视频（例如 DeepSeek），视频会以图片身份发出去，换回上游报错。按"有损必须声明"，这时本该落成文字占位并记 lossy。
3. **每轮重发**：视频进了历史就每轮整段重发。不在本方案内，理由见「刻意不做」。

## 方案对比

| | 做法 | 判断 |
| --- | --- | --- |
| A（选） | 两种独立片段 `video` / `audio`，两个能力位 | 每个消费点必须对新类型表态；能力位与片段一一对应 |
| B | 一种 `MediaPart`，按 mime 大类分派 | 否：mime 是自由字符串，漏判的消费点会悄悄落进"当图片"的分支，正好重演问题 ② |
| C | 不加类型，只给 `ImagePart` 加 `durationSec` 并按 mime 估算 | 否：能力位仍然只有 `images`，问题 ② 不解；"图片"片段装视频，名不副实 |

**A 的诚实边界**：TypeScript 只在 `switch` / 判别式收窄写全的地方报错。现有不少消费点写成"不是 text、不是 tool_reference，就是 image"的 else 兜底，加新成员后**照样编译通过、悄悄当图片处理**。所以本方案把下面清单里的每一处改成显式分支，末尾用 `const _exhaustive: never = p` 收口，以后再加片段类型时这些地方才会编译不过。

## 具体设计

### 公开接口（core）

```ts
export type ContentPart = TextPart | ImagePart | VideoPart | AudioPart | ToolReferencePart

export interface VideoPart {
  type: "video"
  /** 必须以 "video/" 开头 */
  mime: string
  /** base64 编码的文件字节 */
  data: string
  /** 时长（秒，有限正数）；估算用，缺省按字节折算 */
  durationSec?: number
}

export interface AudioPart {
  type: "audio"
  /** 必须以 "audio/" 开头 */
  mime: string
  data: string
  durationSec?: number
}

// LoweringCapabilities
/** 模型收不收视频 / 音频片段；缺省 false（没写 = 不收，降级层落文字占位） */
video?: boolean
audio?: boolean
```

- 两个能力位用**可选**字段：宿主自写的 `Lowering` 不用改就能编译，没写按不收处理（fail-closed）。`images` 保持必填不动。
- 视频里的音轨算视频的一部分，不要求 `audio: true`；纯音频文件才是 `AudioPart`。
- **不升 schemaVersion**：`user_message` / `tool_result` 的 `content` 只是新增联合成员，旧日志照常可读。反方向（新日志给旧版本读）会读到不认识的片段，在 changeset 里写明。

### 形状校验（三道白名单同步）

- `core/src/loop/run-loop.ts`：`CONTENT_PART_TYPES` 加 `video` / `audio`；`isContentPartList` 校验 `mime` 前缀、`data` 为字符串、`durationSec` 缺省或为有限正数。校验不过整条输入拒绝，不写日志。
- `core/src/loop/tools.ts`：工具结果片段的同一组校验。两处是同一个值的两次比对，抽成 core 内部的一个纯函数 `isContentPart`，登记全景图真源索引（现状是两份手写）。
- `server/src/handler.ts`：`rebuildContentParts` 放行 `video` / `audio`，按白名单重建字段（`type` / `mime` / `data` / `durationSec`），形状同上；报错文案从 "text or image parts" 改为列出四种。

mime 前缀校验只给新类型加，`ImagePart.mime` 维持现状不校验（收紧它是另一个破坏性变更，没有真实需求）。

### 估算（core `projection/estimate.ts`）

| 片段 | 有 `durationSec` | 没有时长 |
| --- | --- | --- |
| video | `ceil(秒 × 100)` | 字节按 1 Mbps 折成秒（`bytes / 125_000`）再 × 100 |
| audio | `ceil(秒 × 32)` | 字节按 64 kbps 折成秒（`bytes / 8_000`）再 × 32 |

- 100 来自中转站实测（约 95/秒，取整往高）；32 是 Gemini 公开的音频费率。字节 = base64 长度 × 3/4。
- 没有时长时按偏低的码率折算，宁可估高（高码率短片会被高估几倍，代价是整理提前，不会溢出）。宿主有时长就该给；OnSet 读文件时能拿到。
- 宿主要别的费率（例如以后开高分辨率档）就注入自己的 `TokenEstimator`（包一层 `roughTokenEstimate`），**不另加开关**。感知按上一请求的真实用量校准，估算误差在第二轮起会被修正。
- 常量不导出，只在 `estimate.ts` 头注释写明来源。

### 降级层 fetch 版

三条线遵循同一条规则：**能力位为 true 时放进该线的图片槽位（mime 原样）；为 false 时落文字占位、事件记 lossy**。现有的图片占位就是这样记的，落点粒度是事件不是片段，所以 OnSet 原文写的 "dropped" 在这里是 lossy。

| 线 | 能力位 true | 能力位 false |
| --- | --- | --- |
| Chat | `image_url` data URI；工具结果里的照图片规则上浮到同批之后的 user | `[video omitted: this model does not accept video (video/mp4, 72 s)]`；tool 消息内同理 |
| Responses | `input_image` data URI（user 与 `function_call_output` 数组） | 同上占位 |
| Anthropic | `image` 块，`media_type` 填视频 / 音频 mime（user 与 `tool_result.content`） | 同上占位 |

- **落点 exact，矩阵 note 写明方言**：内容完整送达，没丢信息；但这是中转站转换层认的写法，三家官方端点都不收。矩阵 note 写 "relay dialect: the official endpoint rejects it; only declare video/audio for endpoints that take it"。内置模型表一律不开这两个能力位，只能由宿主对自己的中转站模型声明。
- **纯音频的槽位要先实证（P0）**：OnSet 只测了带音轨的视频。纯音频文件放进图片槽，中转站认不认，没人测过。Chat 线另有官方的 `input_audio`（只收 wav / mp3）。P0 探针决定每条线的音频落点；某条线两种放法都不认时，该线的音频恒落占位，并在矩阵里声明 "the line has no audio landing"，`audio: true` 在该线不生效。
- **Chat 线上浮泛化**：`toolContent` / `liftedAttachment` 的 `images` 改为媒体（image / video / audio）。**只有图片时的输出逐字节不变**：指路文字、标题行、`image n:` 标签都照旧，已有快照与缓存前缀不受影响。混有视频 / 音频时，标签按类型写（`video 1:`），编号全批连续；标题行改为 "N attachment(s)"。
- 占位文案常量放在共用层（与 `IMAGE_OMITTED` 并列），三条线共用。现状三份 `IMAGE_OMITTED` 各写一份，本次一并收成一份。
- `capabilitiesOf` / `ModelOptions` / `FetchModel` 加 `video?` / `audio?`，`definitionOf` 照 `images` 的覆盖逻辑处理。

### 降级层 pi 版

pi-ai 0.85.1 只有 text / image 两种内容，没有视频 / 音频落点：`toPiContent` 一律落占位，事件记 lossy。矩阵在 `core.user_message` / `core.tool_result` 下声明 "pi-ai has no video/audio content; replaced with placeholder text"。`capabilities` 不设两个能力位。

### 刻意不做

- **旧媒体自动折叠**（OnSet 可选项）：折哪段、留哪段是框架替模型做决定，按宪法一不能做成缺省；无 eval 也不能缺省开。现有 compact 折叠工具结果并配 `recall`，已能处理"看过的片子不再每轮重发"。记 OPT，等 OnSet 的真实用量。
- **Gemini 原生第四条线**：只有原生协议能开高分辨率档和原生思考，但工作量最大。等低分辨率确认不够用再立项。
- **媒体外溢到 BlobStore**：片段 `data` 直接进日志（与图片相同）。改成 blob 引用要动片段形状与三道白名单，没有真实需求。
- **`ImagePart.mime` 校验收紧**：见上。

## 风险

- **日志体积**：一段 72 秒视频的 base64 约数 MB，按 append-only 永久留在事件表里。字节上限是宿主的事（OnSet 已计划设时长与字节上限），README 写明。pg `json` 列与 SQLite 都能存，不加库侧上限。
- **方言依赖**：视频走图片槽位是中转站的行为，不是协议约定。上游换转换层可能失效，落点会从 200 变成 400。P0 探针留在 `spikes/` 里，中转站升级时复跑。

## 实施清单

0. **P0 探针**（`spikes/media-parts/`，写代码前）：用 ffmpeg 与 `say` 本地生成两段素材——6 秒视频（画面上是随机暗号、口播另一个暗号）与 6 秒纯音频（口播暗号，wav 与 mp3 各一份）。中转站 Gemini 三条线 ×（user 消息 / 工具结果）×（视频 / 音频）× 候选槽位（图片槽；Chat 另测 `input_audio`）。判据是模型复述出暗号，不看状态码。另跑一臂：DeepSeek（`images: true`）把视频放进 `image_url`，记下上游实际返回什么，作为问题 ② 的现象证据。结论登记 `spikes/README.md`，并确定矩阵里的音频落点。
1. core：类型、`isContentPart` 纯函数及两处调用、估算、truncate 摘录、能力位；单测覆盖校验边界（mime 前缀、`durationSec` 为 0 / 负数 / NaN / 缺省）与估算两条路径。
2. server：`rebuildContentParts` 与报错文案；网络往返用例（合规放行、字段被重建、坏形状 400）。
3. lowering-fetch：三条线编码、Chat 上浮泛化、占位常量合一、能力位、矩阵；矩阵测试覆盖四格（true / false × user / tool_result）；**图片单独的快照逐字节不变**这一条单列一个用例锁住。

5. adapter-tanstack-ai、ui-agui、tools-mcp：按上表。
6. 文档：core / lowering-fetch / tools-mcp README（新片段、能力位声明方式、方言提示、日志体积）；全景图（§3 片段表、核心设计决策、真源索引 `isContentPart`）；模块盘点；AGENTS.md「降级层 fetch 版」加一条警示（视频 / 音频走图片槽是方言，官方端点 400；只有图片时上浮输出逐字节不变）。
