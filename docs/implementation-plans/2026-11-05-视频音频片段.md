# 视频 / 音频内容片段（OnSet 建议 12）

> 状态：📋 待实施（2026-11-05 写成；同日 P0 探针全部跑完，下文的槽位、费率、形状都是实测值，实施时不用再验）

## 背景与根因

OnSet 建议 12（`docs/archive/2026-10-30-OnSet反馈-compact与perception改进建议.md` 末节）：要让 Gemini 主脑（公司中转站 `gemini-3.8-flash-high`）直接看片子，而不是交给看片助手、只拿回文字结论。导演看节奏、剪辑看切点，转述一道就会失真。

现状只有 `text` / `image` / `tool_reference` 三种片段，能力位只有 `images`。宿主把 `video/mp4` 塞进 `ImagePart` 能跑，但有三个问题：

1. **估算失真**：每张图固定按 1600 token 估，30 秒视频实际 2730，72 秒约 6.6k，整理与兜底的时机跟着失准。
2. **能力位误放行**：`images: true` 的模型不一定收视频。实测 DeepSeek `deepseek-flash` 收到放在图片槽里的视频或音频，回 **400 "unsupported image"**，整个 run 失败。按"有损必须声明"，这时本该落成文字占位、记 lossy、run 照跑。
3. **每轮重发**：视频进了历史就每轮整段重发。不在本方案内，见 OPT-261105-3。

前置已核实：Gemini 经中转站多轮工具调用不需要回放签名（`spikes/gemini-relay-signature/`，三线两遍 6/6）。

## P0 实测结论（`spikes/media-parts/`，2026-11-05，主组跑两遍结果一致）

素材每次现做（暗号法）：视频画面上是随机 6 位码，音轨口播两个随机词；纯音频只有口播。判据是模型复述出暗号，同时看输入 token 有没有涨。

| 问题 | 结论 | 证据 |
| --- | --- | --- |
| 视频放哪 | 三条线都放**图片槽**：Chat `image_url` data URI、Responses `input_image`（`detail: "auto"`）、Anthropic `image` 块，mime 原样填 | 三线 × user / 工具结果 6/6 ×2 遍 |
| 纯音频放哪 | **同样放图片槽**，mp3 与 wav 都行；Anthropic `document` 块也行，但统一用 `image` | 三线 × user / 工具结果 × mp3 / wav 12/12 ×2 遍 |
| `input_audio` 能不能用 | **不能**。Chat / Responses 上回 200，输入 token 与纯文本基线完全相同，说明音频被静默丢掉，模型还会编出没说过的词 | 0/8 ×2 遍；踩坑 45 |
| 一条结果里混放 | 图 + 视频 + 音频放进同一条工具结果，三条线都能逐个认出；Chat 上浮标签按类型写、编号连续（`image 1:` / `video 2:` / `audio 3:`，标题 "3 attachment(s)"） | X 组三线 3/3 |
| 缓存断点 | Anthropic 线 `cache_control` 打在视频 / 音频块上，或打在含媒体的 `tool_result` 上，都接受 | C 组 4/4 |
| 文件大小 | 7.7 MB、19.3 MB 的高码率视频（base64 后约 26 MB 请求体）照收；更大的没测 | L 组 4/4 |
| 视频费率 | 每秒 **91 token**（含音轨）。6 / 20 / 30 秒、静态画面与 5 Mbps 运动画面完全一致，与码率和内容无关 | 845−299=546（6 秒），3029−299=2730（30 秒），big8 1820 / 20 秒 |
| 音频费率 | 每秒 **25 token** | 449−299=150（6 秒），1049−299=750（30 秒） |
| 码率跨度 | 同样 30 秒的视频，静态合成片约 75 kbps，运动画面 5 Mbps，相差约 60 倍；64 kbps mp3 恰好每秒 8 KB | 素材字节数 |
| DeepSeek（问题 ② 的现象） | `deepseek-flash`：图片正常；视频 / 音频放图片槽回 400；`input_audio` 回 422（"unknown variant"） | D 组 |
| 内置表错误（顺带发现） | `deepseek-v4-pro` 官方只收文字，带图请求回 200 但图被静默丢掉；内置表写的是 `images: true` | P 组；BUG-261105-1 |
| TanStack 形状 | `@tanstack/ai` 0.53.0 有 `VideoPart` / `AudioPart`，`{ type, source: { type: "data", value, mimeType } \| { type: "url", … }, metadata? }`，与图片同形；没有时长字段 | `dist/esm/types.d.ts` |
| MCP 形状 | MCP client 2.0.0 的 audio 块是 `{ type: "audio", data, mimeType }`；没有 video 块 | SDK schema |

## 方案对比

| | 做法 | 判断 |
| --- | --- | --- |
| A（选） | 两种独立片段 `video` / `audio`，两个能力位 | 每个消费点必须对新类型表态；能力位与片段一一对应 |
| B | 一种 `MediaPart`，按 mime 大类分派 | 否：mime 是自由字符串，漏判的消费点会悄悄落进"当图片"的分支，正好重演问题 ② |
| C | 不加类型，只给 `ImagePart` 加 `durationSec`、按 mime 估算 | 否：能力位仍只有 `images`，问题 ② 不解 |

**A 的诚实边界**：TypeScript 只在写全了的判别式收窄处报错。现有不少消费点写成"不是 text、不是 tool_reference，就是 image"的 else 兜底，加新成员后**照样编译通过、悄悄当图片处理**。所以下面清单里的每一处都改成显式分支，末尾用 `const _exhaustive: never = p` 收口，以后再加片段类型时这些地方才会编译不过。

## 具体设计

### 公开接口（core）

```ts
export type ContentPart = TextPart | ImagePart | VideoPart | AudioPart | ToolReferencePart

export interface VideoPart {
  type: "video"
  /** 必须以 "video/" 开头 */
  mime: string
  /** base64 编码的文件字节 */
  data: string
  /** 时长（秒，有限正数）；估算用，没有时按字节折算 */
  durationSec?: number
}

export interface AudioPart {
  type: "audio"
  /** 必须以 "audio/" 开头 */
  mime: string
  data: string
  durationSec?: number
}

// LoweringCapabilities
/** 模型收不收视频 / 音频片段；没写 = 不收，降级层落文字占位 */
video?: boolean
audio?: boolean
```

- 两个能力位是**可选**字段：宿主自写的 `Lowering` 不改也能编译，没写按不收处理（fail-closed）。`images` 保持必填不动。
- 视频里的音轨算视频的一部分，不要求 `audio: true`（实测视频费率已含音轨）；纯音频文件才是 `AudioPart`。
- **不升 schemaVersion**：`user_message` / `tool_result` 的 `content` 只是新增联合成员，旧日志照常可读。反方向（新日志给旧版本读）会遇到不认识的片段，在 changeset 里写明。

### 形状校验（三道白名单同步）

- `core/src/loop/run-loop.ts`：`CONTENT_PART_TYPES` 加 `video` / `audio`；`isContentPartList` 改为调用新的纯函数。
- `core/src/loop/tools.ts`：工具结果片段校验同样调用它。现状两处各手写一份，抽成 core 内部纯函数 `isContentPart`（不导出），登记全景图真源索引。新类型的规则：`mime` 以对应前缀开头、`data` 是字符串、`durationSec` 缺省或为有限正数。不合规整条拒绝，不写日志。
- `server/src/handler.ts`：`rebuildContentParts` 放行 `video` / `audio`，按白名单重建字段（`type` / `mime` / `data` / 有则 `durationSec`），形状规则同上。报错文案从 "text or image parts" 改为列出四种。server 不依赖 core 的内部函数，所以这是两份实现，靠一条跨包用例锁住（同一组坏形状两边都拒），与 decisions 预校验同一处理办法。

`ImagePart.mime` 维持现状不校验（收紧它是另一个破坏性变更，没有真实需求）。

### 估算（core `projection/estimate.ts`）

| 片段 | 有 `durationSec` | 没有时长 |
| --- | --- | --- |
| video | `ceil(秒 × 100)` | 秒 = `max(字节 / 125_000, 30)`，再 × 100 |
| audio | `ceil(秒 × 32)` | 秒 = `max(字节 / 8_000, 30)`，再 × 32 |

- **费率**：实测视频 91、音频 25；取 100 / 32 留余量（宁高勿低）。32 也是 Gemini 公开的音频费率。字节数 = base64 长度 × 3/4。
- **没时长时的折算**：码率实测相差约 60 倍，单靠字节估不准，所以按偏低码率折算（视频 1 Mbps、音频 64 kbps），**再设 30 秒下限**。按实测素材核对：5 Mbps 的 30 秒片估 15.4k（实际 2.7k，偏高）；75 kbps 的 6 秒静态片若不设下限只估 0.45 秒、严重偏低，设了下限估 3000（实际 546，偏高）。偏高的代价是整理提前，偏低的代价是溢出，所以选偏高。宿主有时长就该给：OnSet 读文件时拿得到，MCP 与 TanStack 的路径拿不到，只能走字节折算。
- 宿主要别的费率（例如以后开高分辨率档），就注入自己的 `TokenEstimator`（包一层 `roughTokenEstimate`），**不另加开关**。感知按上一请求的真实用量校准，第二轮起误差会被修正。
- 常量不导出，在 `estimate.ts` 头注释写明来源（本方案 P0）。

### 降级层 fetch 版

三条线同一条规则：**能力位为 true 时放进该线的图片槽（mime 原样）；为 false 时落文字占位、事件记 lossy**。现有的图片占位就是这样记的：落点按事件记，不按片段记，所以 OnSet 原文写的 "dropped" 在这里是 lossy。

| 线 | 能力位 true（实测槽位） | 能力位 false |
| --- | --- | --- |
| Chat | `image_url` data URI；工具结果里的照图片规则上浮到同批之后的 user | `[video omitted: this model does not accept video (video/mp4, 72 s)]`（没时长就不写秒数）；tool 消息内同理 |
| Responses | `input_image`（`detail: "auto"`），user 与 `function_call_output` 数组都一样 | 同上 |
| Anthropic | `image` 块，`media_type` 填视频 / 音频 mime，user 与 `tool_result.content` 都一样；缓存断点照常打（实测接受） | 同上 |

- **绝不用 `input_audio`**：中转站回 200 却静默丢弃，比报错更糟（踩坑 45）。代码注释写明原因，防止以后有人"改成官方写法"。
- **落点 exact，矩阵 note 写明方言**：内容完整送达，没丢信息；但这是中转站转换层认的写法，三家官方端点都不收。矩阵 note 写 "relay dialect: video / audio travel in the image slot; official endpoints reject this, so declare video / audio only for endpoints that take it"。内置模型表一律不开这两个能力位，只由宿主对自己的中转站模型声明。
- **Chat 线上浮泛化**：`toolContent` / `liftedAttachment` 的 `images` 改为媒体（image / video / audio）。**只有图片时输出逐字节不变**：指路文字、标题行 "N image(s)"、`image n:` 标签都照旧，已有快照与缓存前缀不受影响。混有视频 / 音频时，标签按类型写、编号全批连续（`video 2:`），指路文字同样按类型写（`[video 2 attached in the next user message]`），标题行改为 "N attachment(s)"。这正是 X 组实测的形状。
- **占位文案合一**：现状三条线各有一份 `IMAGE_OMITTED`，本次收进共用层一份，视频 / 音频占位也放在那里，三条线共用。
- `capabilitiesOf` / `ModelOptions` / `FetchModel` 加 `video?` / `audio?`，`definitionOf` 沿用 `images` 的覆盖逻辑。
- **BUG-261105-1 一起修**：内置表 `deepseek-v4-pro` 改 `images: false`（官方 `/models` 只收文字，实测图片被静默丢掉）。

### 降级层 pi 版

pi-ai 0.85.1 只有 text / image 两种内容，没有视频 / 音频落点：`toPiContent` 一律落占位，事件记 lossy；矩阵在 `core.user_message` / `core.tool_result` 下声明 "pi-ai has no video / audio content; replaced with placeholder text"。`capabilities` 不设两个能力位。

### 刻意不做

- **旧媒体自动折叠**：OPT-261105-3（宪法一；现有 compact + `recall` 已能让模型自己收起看过的片子）。
- **Gemini 原生第四条线**：只有原生协议能开高分辨率档（`mediaResolution: HIGH`）和原生思考，但工作量最大，等低分辨率确认不够用再立项。
- **媒体外溢到 BlobStore**：片段 `data` 直接进日志（与图片相同）；改成 blob 引用要动片段形状与三道白名单，没有真实需求。
- **`ImagePart.mime` 校验收紧**：见上。
- **`input_audio` / Anthropic `document` 块等官方写法**：前者实测被静默丢弃；后者能用，但与 `image` 块没有差别，统一一种写法（熵控）。

## 风险

- **日志体积**：72 秒视频的 base64 有数 MB，按 append-only 永久留在事件表里，每轮还整段重发。字节上限由宿主定（OnSet 已计划设时长与字节上限），README 写明；19.3 MB 已实测能发，更大的没测。不加库侧上限。
- **方言依赖**：视频 / 音频走图片槽是中转站的行为，不是协议约定。上游换转换层可能失效，落点会从 200 变成 400，或者更糟，变成静默丢弃（踩坑 45 的形状）。`spikes/media-parts/` 留着，中转站升级时复跑，判据包含输入 token 对照。
