Image references are read concurrently. Checking a batch of references (initial `input`, everything one `pullInput` returns, a whole tool result) and swapping the images in view before a model call each read the uncached blobs in one wave — up to 16 at a time, each id once — then judge them in their original order, so the first problem reported is the same as before. On object storage, ten new images now cost one round trip instead of ten. `BlobStore` gains an optional `stat(id): Promise<BlobMeta>` (metadata without bytes; must throw `StoreError("not_found")` for an unknown id and equal `get(id).meta`); the in-memory store implements it and `blobStoreConformance` checks it. `checkImageRefs` takes `metaOnly: true` to use `stat` when present and keep nothing in the cache — the HTTP handler uses it; the loop still decides with `get`. A `get` or `stat` that returns a non-object is treated as not found. Behaviour changes: when the same image appears twice in one tool result and the read fails transiently, both parts now get `storage error` (it is read once); after the first problem in a batch the remaining references are still read, so failing batches may read more than before. Successful batches read the same number of blobs as before.
