# @reinsjs/core

## 0.18.0

### Minor Changes

- 729f892: The conformance suites in `@reinsjs/core/testing` now test real concurrency: two concurrent `EventLog.append` calls with the same seq must land exactly one and reject the other with `seq_conflict`; eight owners acquiring a free `RunLease` at once must produce exactly one winner; and `BlobStore.put` must store a copy, so mutating the caller's buffer afterwards does not change the blob. A check-then-write backend used to pass. The old serial duplicate-seq case is renamed, as it never tested a concurrent writer. **Third-party backends that passed before may now fail these new cases** — that is the point: they flag real contract violations.
- e04c188: The EventLog conformance suite in `@reinsjs/core/testing` now checks that every shell field round-trips verbatim — `parentId`, `provenance`, nested `replay` (thinking signatures, reasoning item ids), non-ASCII and large payloads, a non-current `schemaVersion` and `ext.*` types — through `read`, `tail` and `fork`. A backend that stored only some columns used to pass the suite while silently breaking reasoning replay. New helper `makeRichEvents(sessionId, startSeq?)`. **Third-party backends that passed before may now fail these new cases** — that is the point: they flag real contract violations.
- 4a2f5b6: `decisions` now only accept calls that are waiting for approval: pending, with a `core.approval_request` and no decision yet. A decision for a pending call that never asked for approval (for example one left over after the run was aborted mid-batch), or two decisions for the same call in one request, throws `RunStateError("unknown_tool_call")` before anything is written. Before, such a decision skipped `needsApproval`, the approval policy's `defer` and its `ttl`. The check is exported as `assertDecisionsAwaitApproval` so the HTTP handler can share it. To drop a pending call that is not waiting for approval, stop the run instead.
- 6eb8b09: `visibilityFilter` (and so the default projection) now drops `ext.*` events. No lowering sends them to the model, yet they stayed in the projected view and were counted in `stats.estimatedTokens`, the perception reading and the budget fallback — a large host extension event could trigger compaction or trimming while the real context was far from full. To show an extension event to the model, build the chain with `defaultProjectionChain({ filter: { keepExtEvents: true } })`, insert a strategy of your own right after the filter (its first element) that translates the event into a core event (a `core.system_note`, for example), and pass the result as `projection.strategies` to `runLoop` / `createAgent`.
- cf87a07: `runLoop` no longer yields the new session's opening events on a handoff; it yields only events of its own `sessionId`. Before, the summary note and trigger message written into the new session were yielded to the old session's consumer, so `createAgentHandler` streamed them on the old session's SSE stream (ids going back to 1, 2 before the old session's `run_ended`), AG-UI clients showed the trigger message in the old thread, a reconnect with that `Last-Event-ID` replayed most of the old session, and `onEvent` reported them under the old `sessionId`. The opening is still written to the log; read it from `toSessionId`. The TanStack adapter likewise no longer passes them to `onEvent`.
- 53c5561: Handoff now records who really wrote each opening event of the new session. The summary note used to be a host note (`actor: "host"`, system trust) and the trigger message a user message (`actor: "user"`, principal trust), even when the model wrote both — so a `triggerMessage` the model was talked into by a tool result showed up in the new session as the user's own instruction. Now the summary is recorded as `intent.by` (default `"model"`), and so is the trigger message unless it repeats one of the old session's user messages word for word, in which case it keeps that message's `actor` and trust (the user's stays the user's, a host-written one the host's) and `provenance.ref` points at that message. The summary and self-written trigger messages carry `provenance: { source: "handoff", ref: <core.handoff event id> }`. The shape is built by the new export `handoffOpeningDrafts`, shared by `runLoop` and the TanStack adapter. Event types, payloads and what the model sees are unchanged; code that filtered the new session by `actor` (for example "the user's first message") should read the event type or `provenance` instead.
- afcc7b7: Image parts must now use one of `image/jpeg`, `image/png`, `image/gif` or `image/webp`, inline or by reference. `isContentPart` rejects every other type, so an SVG or HEIC image from a tool can no longer enter the log and make every later request fail with a provider 400. The whitelist is exported as `SUPPORTED_IMAGE_MIMES` / `isSupportedImageMime` for other entry points to share. Breaking for hosts that wrote other image types: in a tool result, such a part (well formed apart from its type) is replaced by a sentence naming the type (`unsupportedImageText`) while the other parts are kept; `input` containing one throws `RangeError`. `@reinsjs/adapter-tanstack-ai` checks imported parts with `isContentPart`, so a client image of another type is now imported as its `[image(<mime>) part could not be imported …]` placeholder and listed in `dropped`.
- 5703a3e: A `core.tool_result` draft in the initial `input` must now answer a call that is still pending and not waiting for approval: same `toolCallId` and `name`, at most once per batch. Otherwise `runLoop` throws `RangeError` before anything is written. Before, a host that submitted the same client-tool result twice, or a result for an unknown call, wrote a duplicate or orphan result that was replayed to the provider on every later request; and a result for a call still waiting for approval skipped the approval. Breaking for hosts that relied on either: pass the decision in `decisions` first, then the result. The HTTP handler already answers `409 unknown_tool_call` / `409 approval_pending` for these cases; unlike it, in-process `input` may still fill in a result for a server-side tool.
- 6cd00cd: `project()` now rejects a bad context window or reserve with a `RangeError`: `contextLimit` must be a positive finite number, and `reserveTokens` must be a non-negative finite number below `contextLimit`. Before, a `NaN` or `0` window, or a reserve not below the window, made the threshold fallback fold everything but the last turn and write that compaction into the append-only log for good, and with `NaN` it did not even report `overBudget`. `runLoop` runs the same check on the model's `contextWindow` and `projection.reserveTokens` before it writes anything. The check is exported as `resolveReserveTokens`, which also returns the default reserve.
- 7e4f674: When the host aborts a model response (a dropped connection or a lost lease, not a user stop) after some of its tool calls were already logged, the run now settles those calls with an `isError` result (`MODEL_INTERRUPTED_NOT_EXECUTED_TEXT`) before pausing as `paused(host)`. This covers both a response that ends with `stopReason: "aborted"` and a stream that throws after the host aborted. Before, the calls stayed pending, and the next run executed them, possibly with arguments cut off mid-stream, after the user's new message but before the model had read it. A user stop is unchanged: those calls get the usual stop text. Behavior change for hosts that relied on resuming such a call: the model now sees that it was dropped and decides whether to call again.
- bdfdc7c: `MemoryStore.list(prefix)` on Postgres and SQLite now matches prefixes containing characters outside the BMP (emoji, CJK extension B). The prefix length was bound as UTF-16 code units while the database counts characters, so such prefixes always returned an empty list. The MemoryStore conformance suite in `@reinsjs/core/testing` gains a case for it. **Third-party backends that passed before may now fail these new cases** — that is the point: they flag real contract violations.
- 5c36bfd: `PgEventLog.read` and `PgBlobStore.slice` now clamp bounds to the integer column range, matching the in-memory and SQLite stores: `toSeq: Number.MAX_SAFE_INTEGER`, `end: Infinity` and similar "to the end" values read to the end instead of throwing a raw Postgres error. The EventLog and BlobStore conformance suites in `@reinsjs/core/testing` gain cases for these bounds. **Third-party backends that passed before may now fail these new cases** — that is the point: they flag real contract violations.

### Patch Changes

- 3830f23: `budget_usage.contextEstimate` now estimates the view actually sent to the model, after `beforeModel` patches and the notes injected during `beforeModel`. Before, it was the projection estimate taken before injection, so a large injected note (such as a pins snapshot at a segment start) was counted as fixed overhead and then counted again on the next turn once it was in the timeline. That made the next turn's perception reading, compact's soft-line requests and the threshold fallback all overestimate the context, and could fold old turns while real usage was far below the line.
- 60b6052: An abort that lands in the middle of a tool batch now ends the run paused instead of calling `onTurnEnd`. This applies to any abort, such as a dropped connection or a lost lease, not only a user stop. Before, a Socket deciding `handoff` or `stop` in `onTurnEnd` could end the run as `handoff` or `done` while calls from that batch were still pending. What the pause says depends on the abort: a user stop (`RunStop`) closes the pending calls as before, with the note `stopped by the user`; any other abort keeps them pending for the next run, and when nothing else in the batch interrupted the run the pause is `paused(host)` with the note `host aborted during the tool batch`. If the batch also has a call waiting for approval or for a client result, that interruption sets the reason as usual.
- 9856645: A host abort in the middle of a tool batch now always adds the host note to `run_paused`, even when the batch already has another interruption (an approval request, a client tool, a paused sub-agent). The pause reason is unchanged (approval still comes first). Before, such a pause had no note, so `@reinsjs/server` treated the calls after the abort, which were never evaluated, as ready to be filled in, and a client-side tool that needs approval could be answered without approval (`409 call_not_evaluated` now applies as intended).
- b4de7f3: When a resumed run locates the batch of leftover tool calls, an `ext.*` event between two calls of the same model response no longer splits the batch, matching how the lowerings group that response (extension events do not break an assistant turn there).
- 040768e: `ext.*` events a socket writes during `beforeModel` no longer join that turn's view. They are not sent to the model, but they were counted in the estimate of what was sent, so the calibrated fixed overhead (`contextOverheadOf`) came out too low. "Hidden from the model by default" now has one definition, exported as `isModelInvisibleByDefault` (the operational event types plus the `ext.` prefix), used by `visibilityFilter`, `runLoop` and the TanStack AI middleware.
- da6250a: A `needsApproval` function that throws no longer crashes the run. The call is treated as denied: it is not executed and gets an `isError` result `Approval check failed: …`, and the cause is logged for the host as a model-invisible `core.error` (category `host`, `detail.phase: "needsApproval"`). Before, the generator threw without a closing event and every later run hit the same error while completing the pending call.
- b086f75: When a resumed run settles a pending call whose tool is no longer in the base tool table (for example a tool that a `beforeModel` patch added only for that turn), the model now gets `Tool not available on resume: <name> …` instead of `Unknown tool: <name>`. The call is still not executed. Tools that need approval or client execution should come from a Socket's static `tools`.
- 9291394: When a model response fails after some of its tool calls were already logged (the stream breaks, or ends with `stopReason: "error"`), the run now settles those calls with an `isError` result (`MODEL_FAILED_NOT_EXECUTED_TEXT`) in the same batch as the `core.error` and `run_ended(error)` events. Before, the calls stayed pending, and the next run executed them, possibly with truncated arguments, after the user's new message but before the model had read it.
- 9d47f4d: `runLoop` now keeps tool call ids unique within a session. When a provider or relay reuses an id from an earlier call (such as `call_0` on every turn) or sends an empty one, the call is logged under a fresh `reins_<id>` and the original goes into `payload.meta.originalToolCallId`. Before, the later call took over the earlier call's approval, denial or "already started" record. In practice it could run without approval, be rejected, or be reported as an unknown outcome without running.

  The fresh id is built from `newId` and normalized to `^[A-Za-z0-9_-]{1,64}$`, so a custom `newId` cannot produce an id a provider rejects. Hosts that fill in client-tool results must use the `toolCallId` from the logged `core.tool_call` (or `run_paused.awaiting`). The TanStack adapter writes its own tool calls and does not rewrite ids.

- 01b9440: `markUntrusted` now escapes `tool_reference` parts too. An untrusted tool result's reference is expanded into text inside the `<untrusted>` wrapper, but its name, description and input schema were passed through as is, so a description containing `</untrusted>` closed the wrapper early and the rest read as trusted text. Every string in the reference (schema keys included) now gets the same `<\/untrusted` escape as text parts, and the result reports `escaped`, so the lowering layers record the landing as lossy. References that need no escaping are returned unchanged.
- 7a7fbe4: `ctx.budget.wallMs` is now refreshed right before `onTurnEnd`, so it includes the time the turn's tool batch took. Before, it was last updated after the model call, so a slow tool batch was only counted after the next model call and a `budget({ limits: { wallMs } })` limit let one extra turn (a model call plus a whole tool batch) run past the limit, with a stale `used` value in the pause note.
- 1c6fc8c: The folded-results list, `recall`'s answer for a spilled result and the `recall` tool description now say the same thing about spilled outputs: read them with `fetch_blob` "if that tool is in your tool list". The list used to state it unconditionally, though a run may not have `fetch_blob` (`spill({ tool: false })`, or spill removed later).
- 246c457: When the list of folded tool results (or of folded user messages with media) exceeds `maxItems`, it now keeps the most recent entries and collapses the older ones into a single `…N earlier (seq a–b)` line under the heading. It used to keep the oldest, so after a few compactions the results the model most likely wanted back were reduced to a bare seq range.
- 252764c: Wording made consistent about getting folded content back. The default threshold summary no longer says removed events "can be recovered by the host"; it states that they remain in the session log, and the module that provides a recall tool says how to use it (with `compact()`, `recall`). `recall` on a tool result whose output was spilled now returns a normal (non-error) result pointing to the blob and `fetch_blob` "if that tool is in your tool list", so `haltOnFailure` no longer holds back the rest of the batch.

## 0.17.0

### Minor Changes

- 420e0f7: Image references are read concurrently. Checking a batch of references (initial `input`, everything one `pullInput` returns, a whole tool result) and swapping the images in view before a model call each read the uncached blobs in one wave — up to 16 at a time, each id once — then judge them in their original order, so the first problem reported is the same as before. On object storage, ten new images now cost one round trip instead of ten. `BlobStore` gains an optional `stat(id): Promise<BlobMeta>` (metadata without bytes; must throw `StoreError("not_found")` for an unknown id and equal `get(id).meta`); the in-memory store implements it and `blobStoreConformance` checks it. `checkImageRefs` takes `metaOnly: true` to use `stat` when present and keep nothing in the cache — the HTTP handler uses it; the loop still decides with `get`. A `get` or `stat` that returns a non-object is treated as not found. Behaviour changes: when the same image appears twice in one tool result and the read fails transiently, both parts now get `storage error` (it is read once); after the first problem in a batch the remaining references are still read, so failing batches may read more than before. Successful batches read the same number of blobs as before.

## 0.16.0

### Minor Changes

- c47e62b: Images can be stored by reference: `{ type: "image", mime, blobId }`, with the bytes in the `BlobStore` and only the id in the log. Right before each model call `runLoop` swaps the references in view for inline images (`hydrateImageRefs`, at most one read per blob per run), so lowerings see exactly what the inline form would give; folded images are not read. References are checked before anything is written — initial `input` (`RangeError`), `pullInput` (run ends with a `core.error` of category `input`), tool results (only the offending part is replaced; the rest is kept) — and every rejection reads `Blob <id> not found in this session`. A blob that no longer exists is passed on as a reference and becomes `[image unavailable]` in the lowering; other storage errors fail the model call like a network error. New exports: `isImageRef`, `mediaRefsOf`, `blobUsableBy`, `checkImageRefs`, `imageRefNotFound`, `hydrateImageRefs`, `bytesToBase64`, `ImageInlinePart`, `ImageRefPart`; `ImagePart` is now a union of the two, so code reading `.data` must check `isImageRef` first. `core.user_message` and `core.tool_result` are written as schema v2 (v1 upgrades unchanged): sessions written by this version cannot be read by 0.15 or earlier — upgrade every instance together.
- 12d9343: Folded media in user messages is now listed: new exports `foldedUserMedia(removed)` and `renderFoldedUserMedia(items, { heading, maxItems })` pick the user messages that carried images, video or audio out of a folded range, by `seq`. The default threshold summary (`defaultThresholdSummary`) appends such a list when the removed range contains one; summaries without media are unchanged.

## 0.15.0

### Minor Changes

- f8a3550: Pause codes: a socket’s `onTurnEnd` may now return `{ pause: { reason, code, note } }`. The `code` (your own identifier such as `acme.credits_exhausted`, format `PAUSE_CODE_RE`) and the note are written into `core.run_paused`, the code is on the live `Interruption` and on `RunStatus.paused.code`, so a later request or another process can tell why a run paused. reins never branches on it and it is not part of the resume state. The loop’s own `maxTurns` pause carries `reins.max_turns`. A code that does not match the format is dropped: the run still pauses, and a model-invisible `core.error` (category `input`, `detail.phase: "onTurnEnd"`) is logged before the `core.run_paused`. A `reason` other than `"budget"` / `"host"` is handled the same way and pauses with `host`. New exports: `PAUSE_CODE_RE`, `isPauseCode`, `MAX_TURNS_PAUSE_CODE`, `resolveSocketPause`, `pauseDetailOf`. Note: `core.run_paused` now also records the `note` of loop-originated pauses (aborts, user stop, `maxTurns`), so code that compares that payload for exact equality sees a new optional field.

## 0.14.0

### Minor Changes

- 884c840: Session run status. Every `runLoop` run now starts with `core.tools_bound` (carrying `marksEnd: true`) and ends with exactly one end marker: `core.run_paused` as before, or the new model-invisible `core.run_ended` with `status: "done" | "handoff" | "error"`. `core.run_paused` gains `awaiting` (the pending calls waiting on an approval — with `requestedAt` —, a client tool or a sub-agent) and `stopped: true` for a user stop. A `core.error` the loop retries past, or one recorded for a throwing `pullInput`, gets no `run_ended`; an error that ends the run is written together with its `run_ended`.

  `runStatusOf({ held, lastMarker })` classifies a session as running / paused / done / handoff / error / interrupted / idle / unknown from a lease flag and `lastRunMarker(timeline)`. `@reinsjs/store-pg` adds `pgRunStates(client, sessionIds)`: one SQL statement reads the leases and each session's last marker, so a session list never sees a gap between "lease released" and "outcome written". "Running" is only known for runs started through the server handler with a lease registry (`createAgent` + `pgStores`).

  Log shape changes: on a resumed run `core.tools_bound` now comes before `core.run_resumed` / `core.approval_decision`, and `RunResult.lastSeq` of a done or handoff run points at its `run_ended`. Live streams carry one more event (a `CUSTOM` frame in AG-UI). The TanStack adapter writes `run_ended` too, but its `tools_bound` carries no `marksEnd` and its `run_paused` no `awaiting` / `stopped`. Lowerings drop `run_ended` like other operational events.

  **Rolling upgrade:** `@reinsjs/core` 0.13 and earlier reject sessions that contain `core.run_ended` (unknown event type). Upgrade every instance to the same core version at once, and do not roll back past 0.14 once such sessions exist. Sessions whose last run finished before the upgrade read `unknown`.

## 0.13.0

### Minor Changes

- fba2410: "The outcome is unknown" results now end with the time the call started: ` This call started at <ISO UTC with milliseconds>.`, taken from the call's `core.tool_started` event. With identical parameters, the model can only tell what this call created from an earlier object by its creation time, and it had no anchor for that. The time is added only when the tool is known and not replayable (its `tool_started` is written before `execute`); "may have partly taken effect" and "not executed" texts are unchanged.

## 0.12.0

### Minor Changes

- e820efb: A paused run can now be resumed from a replay, not only from the stream that saw it pause. The signed resume state is written into the `core.run_paused` event (`payload.state`, model-invisible — the same object as `RunResult.state`), and a replay-only stream whose session ends at that pause carries it in the `end` frame (`state`); with `@reinsjs/ui-agui` it is `RUN_FINISHED.result.state` next to `status: "replayed"`. A page reloaded, reopened or opened on another device can therefore still approve or reject. The state is the one signed at the moment of the pause — never recomputed when read — so configuration drift is still caught. The frame carries the state of the latest pause whatever its reason (approval, budget, abort, stop); decide whether to show an approval card from `state.pendingToolCallIds` and the replayed `core.approval_request` events — after a stop the list is empty. New helper `pausedStateOf(lastEvent)` in `@reinsjs/core` returns the state when the given (last) event is such a pause.

## 0.11.0

### Minor Changes

- b79d193: Add `pullInput` for input that arrives while a run is going. The loop calls it before every model call (not on a turn that only finishes leftover tool calls, not once `maxTurns` is reached) and appends the returned drafts ahead of that turn's socket notes. Only `core.user_message`, `core.system_note` and `ext.*` are accepted; a malformed return value ends the run with `status: "error"` (`core.error` category `input`) and writes none of the batch; a throwing callback is recorded as a model-invisible `core.error` (category `host`) and the run carries on; drafts pulled after an abort are not written. `agent.run()` passes it through. It is per run: `AgentDefinition` (and so `createAgent` options) now omits `pullInput`, so the HTTP handler and `asTool` sub-agents never pull.

## 0.10.0

### Minor Changes

- 45bfc8d: Stop semantics, no replay of interrupted writes, a stop request in the server, and narrower resume validation.

  - **Stop is a kind of abort.** `controller.abort(new RunStop())` makes every pause point close the pending tool calls with an error result ("Not executed: the run was stopped by the user…"; calls that had already started get "outcome unknown" or "interrupted"), so the next run asks the model directly instead of re-running what the user stopped. Approval-pending and client-tool calls are closed too. The result is still `paused` / `host` with the note `stopped by the user`. `new RunStop("host")` is for a host closing calls left by an interrupted run: the same closing, but the texts say an earlier run was interrupted instead of blaming the user (`stopTextsOf`). A run whose signal is already aborted when it starts no longer writes `core.tools_bound` or the tool-change note. Other abort reasons keep the old behaviour (pending calls are replayed on resume). An abort that lands while the request is still connecting now ends as `paused(host)` instead of `error`.
  - **Interrupted writes are not replayed.** New `Tool.replayable` (default: only `risk: "low"` tools) and `isReplayable()`. Non-replayable tools get a model-invisible `core.tool_started` event before `execute`; on resume, a started call without a result is closed with "outcome unknown, check the current state before retrying" instead of running again. A signal-aware write tool cut off by an abort gets the same result instead of "Tool execution failed". Tools that do not declare `risk` now write one extra event per call.
  - **Server stop request.** `POST { sessionId, stop: true }` answers JSON `{ status: "stopping" | "idle", sessionId }` without waiting for the run. `SessionAuthzInput.method` gains `"STOP"` — hooks that allow writes only for `"POST"` will refuse stop requests until they accept `"STOP"`.
  - **`asTool`** declares `replayable: true`, resumes a child only when the parent already recorded `tool_started` for that call (a stopped expert's next task is no longer swallowed), and closes a child's leftover pending calls with `RunStop("host")` before starting a new task.
  - **Narrower resume validation.** `SerializedRunState` gains optional `modelDigest` / `pendingToolsDigest` (included in the signature when present). States carrying them only check the model and the definitions of the tools behind the pending calls, so adding an unrelated tool no longer makes paused sessions answer `409 config_mismatch`; older states still compare the whole configuration hash.
  - Lowerings and the AG-UI encoder declare landings for `core.tool_started` (dropped / `CUSTOM`). The TanStack adapter writes `tool_started` in `onBeforeToolCall` and applies the same no-replay rule; stop handling and resume validation stay out of its scope.

  **Rollback risk:** sessions that contain `core.tool_started` cannot be read by `@reinsjs/core` 0.9 or earlier. Sessions paused inside a sub-agent before upgrading resume the child as a new task after upgrading; let them finish first.

## 0.9.0

### Minor Changes

- 179f891: Video and audio content parts.

  - core: `ContentPart` gains `VideoPart` (`type: "video"`) and `AudioPart` (`type: "audio"`): `mime` must start with `video/` / `audio/`, base64 `data`, optional `durationSec` (finite, positive). `LoweringCapabilities` gains optional `video` / `audio`; absent means the model does not take them. Token estimates follow duration (100 / s for video, 32 / s for audio); without `durationSec` the byte size is converted at 1 Mbps / 64 kbps with a 30-second floor. `isContentPart` checks the new parts and is now also what `runLoop` uses to validate input — which also means `runLoop` input now rejects a `tool_reference` part whose `inputSchema` is an array (tool results already did). A tool returning an array of video / audio-shaped parts now yields media parts instead of JSON text. The budget-truncation summary writes `[video]` / `[audio]` / `[tool <name>]` instead of `[image]` for non-image parts. No `schemaVersion` bump: existing logs read unchanged, but a log containing video or audio parts cannot be read by an older version.
  - lowering-fetch: new `video` / `audio` model options (default `false`, including every built-in model). When on, video and audio travel in each protocol's image slot — a relay dialect official endpoints reject; `input_audio` is deliberately not used. When off, they become placeholder text and the event is `lossy`. Chat lifts video / audio from tool results like images; a result with images only lowers byte-for-byte as before. Fix: `deepseek-v4-pro` is text-only (`images: false`) — the built-in table and `deepseek()` used to claim images, which the provider silently dropped.
  - lowering-pi: video / audio parts become placeholder text (`lossy`); pi-ai has no such content.
  - server: the HTTP whitelist accepts `video` / `audio` parts with the same shape rules as core.
  - adapter-tanstack-ai: data-sourced video / audio parts translate both ways (TanStack has no duration field). URL-sourced parts are now reported in `dropped` as `audio(url)` / `video(url)` instead of `audio` / `video`, and data parts whose mime type does not match their kind as `video(<mime>)` / `audio(<mime>)`. Imported client parts are now checked with core's `isContentPart`: a malformed one (missing `mimeType`, non-string `value`, non-string text) becomes a placeholder reported in `dropped` instead of throwing or reaching the log.
  - ui-agui: video / audio parts become `[video <mime>]` / `[audio <mime>]` placeholders, recorded in `dropped`.
  - tools-mcp: MCP `audio` blocks and `video/*` / `audio/*` embedded resources become audio / video parts instead of descriptions.

## 0.8.0

### Minor Changes

- 54fed37: Sockets can now see the current tool batch. `TurnContext.batch` (`ToolBatch`) lists the batch's tool calls, the results logged so far (in `beforeTool`, only those of earlier calls), the ids left waiting for approval, a client result or a paused sub-agent, and `resumed` when the batch is one a previous run left unfinished. It is one object updated in place during the turn. core also exports `ToolResultEvent` and `toolBatchOf(timeline, pending)`, which locates the batch of leftover calls. **`batch` is a required field**: a host that builds `TurnContext` objects itself (for example in socket unit tests) or runs its own copy of `runLoop` must fill it.

  brain adds two opt-in sockets. `haltOnFailure({ counts?, applies? })` holds back the later calls of a batch once an earlier one failed or is still waiting: each gets an error result naming that call, and nothing runs. Register it first. `stopAfter({ tools })` ends the run (`done`) at the end of a turn in which the model successfully called one of `tools`, when nothing else in the batch failed or is pending. A batch resumed after an approval also ends the run, unless the resumed run brought new user input. Register it after `handoff()` and before `compact()` / `budget()`.

  adapter-tanstack-ai fills `ctx.batch`. Because the engine checks a whole batch before running any of it, `beforeTool` sees no results from the same batch and `held` stays empty. A resumed batch gets no `onTurnEnd` on this path.

## 0.6.0

### Minor Changes

- a2ee718: `input` accepts an array of event drafts, appended in order in one write: e.g. a host briefing as `system_note(kind: "host")` followed by the `user_message`, so the model can tell what it is asked to do from what it is told. ## 0.5.0

### Minor Changes

- 0455c28: Deliver `compact`'s request as a directive and ask twice. `SystemNotePayload` gains an optional `directive: true` for notes that ask the model to act; `@reinsjs/lowering-fetch` (all three protocols) and `@reinsjs/lowering-pi` send those as a framed `<system_note>` user message even when the model accepts mid-conversation system messages, and record the landing as `lossy(user-role)`. Measured on a pooled DeepSeek relay, the same request was ignored 4 of 4 times as a mid-conversation system message and followed 5 of 6 times as a framed user note; the official DeepSeek endpoint followed it 6 of 6 either way. Other notes (perception, pins) keep their current landing, and notes already in a log keep theirs, so cached prefixes do not change on upgrade. `compact({ force })` now asks at two lines by default (`at: [0.75, 0.8]`; a single number still works), uses blunter wording on the second request (`CompactRequestInfo.attempt`), skips the turn right after a compaction until the model has acted, and marks requests as directives unless `force.directive` is `false`.
- 24ba407: Ask the model to compact before the mechanical fallback kicks in. When the real context passes a soft line (`compact({ force: { at } })`, default `0.75` of the window) and nothing has been compacted since the last request, `compact` appends one runtime note at the end asking the model to call `compact` before doing anything else. A compaction made after such a request is recorded as `decidedBy: "forced"` (new value on `CompactionPayload.decidedBy`: the harness picked the timing, the model wrote the summary). The request is made once per segment; if the model ignores it, threshold truncation still folds mechanically at `contextLimit - reserveTokens`. Appending at the end keeps the prompt cache intact, unlike forcing `tool_choice` or narrowing the tool list. Pass `force: false` to turn it off (the default rules then drop the sentence that promises the request); `force.render` customizes the wording. `@reinsjs/eval` counts the new value separately (`CompactionCounts.forced`). The default `COMPACT_RULES` text gains one line, so sessions paused under an older version see a config change on resume.
- 4a57a7a: Threshold truncation now cuts down to a lower watermark instead of just under the trigger line. Once the context passes `contextLimit - reserveTokens`, `budgetTruncate` removes the oldest turns until the context fits within `contextLimit × cutToRatio` (new option, default `0.6`; values above the trigger line fall back to it). Previously each truncation landed just under the line, so the next tool result pushed it back over: a sliver was cut almost every turn, the prompt cache prefix was invalidated each time, and summaries nested deeper. Pass `defaultProjectionChain({ truncate: { cutToRatio: 1 } })` to restore the old behavior.

## 0.4.0

### Minor Changes

- fb032c1: core: the projection's threshold fallback now compares the calibrated context size — the estimate plus the fixed overhead the estimate cannot see (system prompt, tool definitions, thinking), measured from the last `budget_usage` — against `contextLimit - reserveTokens`. Before, it compared the raw estimate, so perception could report "≥85%, the harness auto-folds at 85%" while no fold happened, and a system prompt plus tool table larger than the reserve could overflow the window before the fallback ever fired. `contextOverheadOf` moves to core (brain still re-exports it) and returns 0 when the last usage record yields a non-finite value, so a malformed `budget_usage` cannot fail the run at start; `ProjectionStats.overheadTokens` is new; `project({ budget: { overheadTokens: 0 } })` restores the old comparison. ### Minor Changes

- 49d5dea: New store interface `RunLease` (`acquire` / `renew` / `release`) and optional `Stores.runLease` — a lease table that lets the "one run per session at a time" guard span processes. Expiry is judged by the store's own clock, `acquire` is idempotent for the same owner, and none of the three methods throw on contention (they answer with a boolean). `InMemoryRunLease({ now })` is the reference implementation (not included in `memoryStore()`, which stays single-process), and `runLeaseConformance` joins the other suites in `@reinsjs/core/testing`.

  - `BeforeModelPatch.deferredTools?: string[]` — a socket names which tools of this turn's table are deferred; `runLoop` translates it through the new `deferredToolSpecOf(tool, deferred)`. `toolSpecOf` keeps its single parameter on purpose (it is commonly passed to `map`).

## 0.1.0
